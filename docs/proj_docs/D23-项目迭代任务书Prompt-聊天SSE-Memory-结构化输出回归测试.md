## 3. 需求分解与设计要求

| 需求编号 | 范围 | 必须验证的行为 |
|---|---|---|
| D23-R01 | 同步聊天 | 正常请求/响应、参数校验、异常映射、现有响应契约及既有行为兼容 |
| D23-R02 | SSE 流式聊天 | 正常分块输出、事件顺序、完成信号、异常事件/连接关闭、客户端取消或断开、超时；不得把流式结果错误拼接或重复发送 |
| D23-R03 | Memory | 会话/Conversation 标识关联、历史消息顺序、跨轮上下文传递、不同会话隔离、空历史、历史读取失败；若已有持久化能力，验证重启后恢复及存储行为 |
| D23-R04 | 结构化输出 | 合法输出映射、字段缺失/类型错误/非法枚举/格式错误、解析失败处理、业务 DTO 校验；无效模型输出不得直接进入业务流程 |
| D23-R05 | 关键问题修复 | 仅修复上述链路测试确认的正确性、兼容性、安全或稳定性问题；每项缺陷关联复现测试和修复证据 |

### 3.1 测试设计原则

- 先检查现有测试框架、命名、Mock 方式和测试数据，沿用项目既有约定。
- 测试至少覆盖正常、边界、失败和必要的并发/隔离路径；按功能裁剪并说明未覆盖场景。
- Mock 模型测试与真实模型集成测试分离。默认回归测试不得依赖真实 API Key、外网服务或产生真实模型费用。
- 对 SSE 使用可控的 Flux/模型替身，验证事件顺序、终止、异常和取消；需要真实 HTTP 层时增加对应集成测试。
- Memory 测试不得只验证方法被调用，必须验证消息是否按正确会话、正确顺序进入下一轮模型上下文；若存储层有持久化，增加存储读写和重启恢复验证。
- 结构化输出必须验证最终 DTO 内容和字段约束，不仅断言“没有抛异常”。
- 测试必须真实执行。不得以编译成功、静态阅读或新增测试代码代替测试通过。

### 3.2 关键设计边界

1. 不改变现有同步聊天接口的路径、HTTP 方法、请求/响应字段、状态码和业务语义；若发现现有契约本身有缺陷，先记录兼容性影响，再做最小修复。
2. SSE 与同步调用的异常、TraceId、脱敏记录、模型调用配置等公共能力优先复用；不得在两条链路复制两套互相漂移的业务逻辑。
3. Memory 必须明确会话标识来源、所有权校验、历史窗口/截断规则和消息写入时机。不得把不同用户或不同会话的消息混入同一上下文。
4. 结构化输出的模型结果属于不可信输入；完成解析后仍需执行应用层字段、枚举和业务规则校验。
5. 不为补齐测试而大规模重构，不删除或弱化已有断言，不屏蔽失败测试。
6. 如果发现问题超出 D23 范围，记录为新任务项，并顺手扩展为新功能。
