# 费曼口述：同步响应与 SSE（Server-Sent Events）的区别

说话人 1：费曼口述，同步响应与 SSE（Server-Sent Events，服务器发送事件）的区别，共五十六道关键问题，分七个阶段，由浅入深讲清 HTTP 通信机制、SSE 工作原理、Java 线程模型、Spring MVC 与 WebFlux、Spring AI 流式调用、前后端交互，以及企业级 AI 聊天系统的架构设计与故障排查。

说话人 1：本次以 JDK 21、Spring Boot 3.5.x、Spring AI 1.1.x 为主要工程背景。先明确一个核心认知：同步响应与流式响应描述的是数据如何返回，SSE 描述的是数据如何通过 HTTP 传输。Spring MVC、WebFlux 则涉及服务端如何处理请求和 I/O。它们不是同一个层面的概念。

## 第一阶段：基础概念与核心原理

说话人 1：问题一，什么是同步响应（Synchronous Response）？什么是流式响应（Streaming Response）？两者在数据返回方式上有什么区别？

说话人 1：答，同步响应最容易理解，就是客户端发送一个请求，服务端处理完成后，再把完整结果一次性返回给客户端。

说话人 1：比如，你调用一个普通的用户查询接口，服务端查询数据库、组装数据，最后返回完整的 JSON。客户端通常要等到整个响应体接收完成，才能拿到完整结果并使用。

说话人 1：流式响应就不一样了。服务端不需要等整个结果都生成完毕，而是可以在处理过程中不断把已经生成的数据片段发送给客户端，客户端收到一部分就可以处理一部分。

说话人 1：举个大模型聊天的例子。用户问：“解释一下 Java 线程池的工作原理。”同步响应需要等模型生成完整答案，才把全部内容返回；流式响应则可以先返回“Java 线程池”，接着返回“主要由核心线程数、最大线程数……”等后续片段。

说话人 1：所以，两者最核心的区别是：同步完整响应通常等全部结果完成再交付，流式响应则允许结果逐步交付。

说话人 1：不过，这里的同步主要描述接口和调用方的使用方式，不代表 HTTP 协议强制要求服务端线程必须一直阻塞。服务端也可以通过异步方式执行任务，最后仍然返回一个完整结果。

说话人 1：问题二，什么是 SSE（Server-Sent Events，服务器发送事件）？它解决了传统 HTTP 请求响应模式中的什么问题？

说话人 1：答，SSE 是一种基于 HTTP 的服务器向客户端持续发送事件的通信机制。

说话人 1：传统接口通常是客户端请求一次，服务器返回一次完整结果。如果服务端需要不断通知客户端新消息，早期比较常见的做法是客户端不断轮询服务器。

说话人 1：例如，客户端每隔一秒就问服务器一次：“有没有新的模型生成内容？”这种方式会产生大量重复请求，即使没有新数据也要不断访问服务端。

说话人 1：SSE 的思路是反过来的：客户端先建立一个 HTTP 请求，服务端保持响应连接，在有新数据时主动向客户端推送事件。

说话人 1：例如，大模型每生成一段内容，服务端就推送一个 SSE 事件，浏览器收到以后立即更新聊天界面。

说话人 1：这样就不需要客户端不断轮询，也不必等模型全部生成结束。

说话人 1：SSE 特别适合 AI 聊天、任务进度通知、实时日志和数据监控等服务器持续向客户端发送信息的场景。

说话人 1：问题三，同步响应、流式响应和 SSE 分别属于什么层次？为什么不能简单地将流式响应与 SSE 视为同一个概念？

说话人 1：答，这三个概念最重要的区别在于它们讨论的不是同一件事。

说话人 1：同步响应和流式响应，主要描述数据交付的方式。一个偏向完整结果返回，一个允许结果逐步返回。

说话人 1：SSE 则描述数据如何通过 HTTP 传输。它规定了事件流的媒体类型、数据格式和事件边界等内容。

说话人 1：举个例子，Spring AI 返回一个 `Flux<String>`，表示模型生成的内容可以逐步被消费。这属于流式数据处理。

说话人 1：但这个 `Flux<String>` 不一定已经发送给浏览器。它可以继续被业务代码处理，也可以转换成 SSE 事件，再通过 HTTP 发送给前端。

说话人 1：反过来，服务端也可以通过 SSE 推送任务进度、系统通知或者数据库查询结果，这些内容不一定来自大模型，也不一定需要 AI 流式生成。

说话人 1：所以一定要记住：Flux 是数据流，SSE 是 HTTP 事件传输格式，流式响应是数据逐步交付的方式。三者可以组合，但不能画等号。

说话人 1：问题四，传统 HTTP 请求响应模式是如何工作的？从客户端发送请求到服务器返回完整响应，经历哪些步骤？

说话人 1：答，一次典型的 HTTP 请求，大致经历以下过程。

说话人 1：第一步，客户端根据目标地址建立网络连接。如果使用 HTTPS，还需要完成 TLS 握手和相关安全协商。这里不一定每次请求都重新建立 TCP 连接，HTTP Keep-Alive 和连接池可以复用已有连接。

说话人 1：第二步，客户端发送 HTTP 请求，包括请求方法、URL、请求头和请求体。

说话人 1：第三步，服务器接收请求，根据路由规则找到对应的 Controller，再由业务服务执行业务逻辑。

说话人 1：例如，一个 AI 聊天接口可能需要校验用户身份、读取历史消息、组装 Prompt，再调用大模型。

说话人 1：第四步，服务器等待业务处理完成，生成响应状态码、响应头和响应体。

说话人 1：第五步，客户端接收响应，解析 JSON 或其他数据格式，完成本次请求。

说话人 1：传统 REST 接口通常按照这种方式工作，但要注意，HTTP 本身并没有规定响应体必须一次性生成完成。HTTP 同样支持分块传输和持续输出，SSE 就是建立在 HTTP 之上的一种事件流机制。

说话人 1：问题五，为什么同步响应通常需要等待服务端完成业务处理，才能获得完整结果？这对耗时较长的大模型调用有什么影响？

说话人 1：答，因为同步完整响应的交付目标就是把一个完整结果返回给调用方。

说话人 1：例如，模型生成一段 2000 字的回答，可能需要十几秒。客户端虽然已经把问题发给服务器，但如果接口采用完整响应方式，就通常要等模型全部生成完成，才能拿到最终内容。

说话人 1：这会带来两个问题。

说话人 1：第一，用户体验不好。用户可能长时间看不到任何生成内容，只知道请求还在等待。

说话人 1：第二，服务器的请求生命周期会比较长。如果底层调用采用阻塞方式，工作线程还可能一直等待模型返回，影响其他请求的处理能力。

说话人 1：但是要区分两个概念：客户端等待完整响应，不代表服务端一定使用阻塞线程。服务端可以使用异步任务处理，完成之后再返回完整结果。

说话人 1：所以，大模型场景下引入流式响应，首先改善的是内容交付体验；至于服务器资源是否得到优化，还要看后端具体使用什么 I/O 和线程模型。

说话人 1：问题六，SSE 如何利用 HTTP 长连接实现服务器向客户端持续推送数据？一次 SSE 连接经历哪些生命周期阶段？

说话人 1：答，SSE 的核心就是客户端先发起一个 HTTP 请求，服务端返回一个持续打开的 HTTP 响应，然后不断向响应体写入符合 SSE 格式的数据。

说话人 1：例如，浏览器通过 `EventSource` 连接 `/api/chat/events`，服务器返回 `Content-Type: text/event-stream`，表示后续响应内容按照 SSE 事件流格式解析。

说话人 1：连接建立后，服务器可以不断发送事件，例如：

```
data: Hello

data: World

event: complete
data: done
```

说话人 1：浏览器按照事件格式解析，每遇到事件结束标记，就触发对应的事件处理逻辑。

说话人 1：整个生命周期可以理解为：客户端建立连接、服务器确认并打开事件流、持续发送事件、客户端接收处理，最后由服务器完成、客户端主动关闭或者网络异常导致连接结束。

说话人 1：如果网络断开，浏览器原生 `EventSource` 通常会尝试自动重连。是否能够恢复此前的业务事件，则还需要服务端实现对应的事件 ID 和历史事件补发机制。

说话人 1：所以，SSE 不是把多个独立 HTTP 请求拼接起来，而是利用一个持续打开的 HTTP 响应，逐步发送多个事件。

说话人 1：参考资料：Using server-sent events | 使用服务器发送事件：[MDN 官方开发文档](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events?utm_source=chatgpt.com)

说话人 1：问题七，SSE 与 HTTP 普通响应有什么区别？SSE 是否需要建立独立于 HTTP 的通信协议？

说话人 1：答，SSE 不需要建立一套独立于 HTTP 的传输协议，它本身就是基于 HTTP 的事件流机制。

说话人 1：普通 HTTP 接口通常返回 `application/json`，响应体是一份完整 JSON；SSE 则使用 `text/event-stream`，响应体是一段持续输出的事件流。

说话人 1：两者都可以使用 HTTP 和 TCP 连接，也都可以运行在 HTTPS 之上。区别主要在于响应内容格式、事件边界和连接使用方式。

说话人 1：例如，普通接口可能返回：

```
{
  "message": "Hello World"
}
```

说话人 1：而 SSE 返回的是：

```
data: Hello

data: World
```

说话人 1：浏览器通过 `EventSource` 识别和解析这些事件，不需要我们自己设计一套 WebSocket 协议。

说话人 1：所以，SSE 是 HTTP 之上的应用层事件传输机制，不是 HTTP 的替代品，也不是一个独立的底层网络协议。

说话人 1：问题八，SSE 为什么是单向通信？客户端如何向服务器发送新的消息？

说话人 1：答，因为 SSE 的设计方向就是服务器向客户端推送事件。客户端建立连接以后，主要负责接收服务器持续返回的数据。

说话人 1：例如，AI 聊天时，用户发送问题是一个方向，模型生成回答并通过 SSE 返回是另一个方向。但这里不是在同一个 SSE 连接上实现双向通信。

说话人 1：实际项目通常会设计两个接口：一个 POST 接口接收用户问题，另一个 SSE 接口负责推送生成结果。也可以采用 POST 发起请求，然后让服务器在这个请求的响应体中返回 SSE 数据。

说话人 1：如果客户端需要持续向服务器发送实时消息，可以使用普通 HTTP 请求配合 SSE，或者直接采用 WebSocket。

说话人 1：所以，SSE 的单向限制不意味着整个业务只能单向交互，只是说单条 SSE 事件流的服务器推送方向是单向的。

说话人 1：问题九，SSE 与 WebSocket 有什么区别？它们在通信方向、协议复杂度、连接管理和适用场景方面分别有什么特点？

说话人 1：答，最核心的区别是通信方向和使用场景。

说话人 1：SSE 主要用于服务器向客户端持续推送数据，基于 HTTP，使用 `text/event-stream` 格式，浏览器原生提供 `EventSource`，支持自动重连，协议使用相对简单。

说话人 1：WebSocket 则支持客户端和服务器双向通信。建立连接时通常通过 HTTP 握手升级为 WebSocket 协议，之后双方都可以主动发送消息。

说话人 1：比如，AI 聊天如果只是用户通过 HTTP 提交问题，服务器持续返回模型生成内容，SSE 通常足够了。

说话人 1：但如果是多人在线协作、即时游戏、实时双向语音控制，或者客户端和服务器都需要高频主动推送数据，就更适合评估 WebSocket。

说话人 1：还有一个区别，SSE 原生提供事件类型和重连机制，而 WebSocket 的消息格式、心跳、重连和消息确认通常需要应用自己设计，或者借助 STOMP 等上层协议。

说话人 1：因此，并不是 WebSocket 一定比 SSE 高级。对于单向实时数据推送，SSE 往往更简单；对于真正双向、持续交互的通信，WebSocket 更合适。

## 第二阶段：同步响应与 SSE 的工作机制

说话人 1：问题十，同步响应从客户端发起请求到接收完整响应，客户端与服务端分别处于什么状态？

说话人 1：答，可以从客户端和服务端两边理解。

说话人 1：客户端发出请求以后，会等待服务端返回结果。在完整响应到达之前，调用方通常还不能拿到最终业务结果。

说话人 1：服务端接收到请求后，开始执行业务逻辑，例如查询数据库、调用大模型或者访问其他服务。业务没有完成之前，完整响应体通常还没有准备好。

说话人 1：如果服务端使用传统阻塞调用，处理请求的工作线程可能一直等待下游结果；如果使用异步执行，则可以释放原来的请求线程，等结果完成后再恢复响应处理。

说话人 1：所以，同步响应描述的是调用方如何获取完整结果，不应该直接等同于服务端一定使用一个线程从头阻塞到尾。

说话人 1：问题十一，SSE 如何将一个完整响应拆分成多个数据事件？客户端如何逐步接收和处理这些事件？

说话人 1：答，SSE 不是要求服务端先生成完整响应，再人为切成很多段，而是允许服务端在数据产生的过程中，按照 SSE 格式不断写入事件。

说话人 1：比如模型生成了第一段内容，服务端就发送一个 `data` 事件；模型生成第二段内容，再发送第二个事件。

说话人 1：浏览器收到以后，会根据 SSE 的格式解析事件，把对应的 `data` 交给前端监听函数，再更新聊天界面。

说话人 1：但需要注意，HTTP 网络传输过程中存在缓冲，TCP 数据包边界也不等于 SSE 事件边界。一个事件可能分成多个网络数据块到达，多个事件也可能一起到达。

说话人 1：因此，客户端不能简单地认为每收到一次网络数据就代表收到一个完整事件，而应该按照 SSE 的协议规则解析数据。

说话人 1：问题十二，SSE 的 `Content-Type: text/event-stream` 有什么作用？为什么服务器需要正确设置响应头？

说话人 1：答，`Content-Type` 用来告诉客户端，这次 HTTP 响应体采用什么媒体类型。

说话人 1：普通 JSON 接口通常使用 `application/json`，而 SSE 应该使用 `text/event-stream`。

说话人 1：浏览器的 `EventSource` 会根据这个媒体类型识别服务器返回的内容是否是符合 SSE 要求的事件流。

说话人 1：如果响应头错误，例如返回了 `application/json`，客户端就可能无法按照 SSE 预期处理响应，甚至直接判定连接失败。

说话人 1：实际项目一般还会配合适当的缓存控制，例如 `Cache-Control: no-cache`，并根据代理环境处理缓冲。

说话人 1：需要注意的是，HTTP/1.1 是否使用分块传输编码，应当由服务器和协议栈处理，不需要自己手动把 `Transfer-Encoding: chunked` 写进响应头。HTTP/2 也不使用 HTTP/1.1 的 chunked transfer encoding。

说话人 1：参考资料：Using server-sent events | 使用服务器发送事件：[MDN 官方开发文档](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events?utm_source=chatgpt.com)

说话人 1：问题十三，SSE 的 `data`、`event`、`id` 和 `retry` 字段分别有什么作用？它们如何影响客户端事件处理？

说话人 1：答，这四个字段是 SSE 中最常见的字段，各自负责不同的事情。

说话人 1：`data` 是事件的数据内容。比如模型生成的一个文本片段，可以放在 `data` 中发送给浏览器。

说话人 1：`event` 用来指定事件类型。默认事件类型是 `message`，如果服务端指定了 `event: token`，前端就可以使用 `addEventListener("token", callback)` 单独监听这个事件。

说话人 1：`id` 是事件标识。浏览器会记录最后处理的事件 ID，发生自动重连时，可以通过 `Last-Event-ID` 请求头把最后记录的 ID 发给服务器。

说话人 1：`retry` 用来指定浏览器断开连接以后等待多久再尝试重连，单位是毫秒，并且需要是有效的整数。

说话人 1：举个例子：

```
id: 101
event: token
data: Hello

id: 102
event: token
data: World

event: complete
data: done
```

说话人 1：这样前端就能区分文本片段和完成事件，也可以利用 ID 识别事件位置。

说话人 1：但要记住，`id` 只是让客户端具备记录事件位置的能力。服务器还必须保存或能够重新产生对应事件，才能真正实现断线恢复。

说话人 1：问题十四，SSE 消息为什么需要使用空行作为事件结束标志？如果消息格式不正确会出现什么问题？

说话人 1：答，因为 SSE 协议规定，一个完整事件由若干字段行组成，遇到空行才表示当前事件结束并触发事件分发。

说话人 1：例如：

```
data: 第一段内容

data: 第二段内容
```

说话人 1：第一条空行结束第一个事件，第二条空行结束第二个事件。

说话人 1：如果没有正确发送空行，浏览器可能一直认为当前事件还没有结束，数据无法及时分发给前端。

说话人 1：另外，如果错误地把多个事件直接拼在一起，或者没有按照 SSE 格式处理换行，也可能出现内容粘连、事件类型错误等问题。

说话人 1：这里还有一个细节：同一个事件可以包含多行 `data`，浏览器解析时会使用换行符将这些数据行连接起来，而不是把每一行都当成一个独立事件。

说话人 1：所以，开发 SSE 时，一定要正确处理事件边界，而不是只关注数据内容。

说话人 1：参考资料：HTML Living Standard — Server-sent events | HTML 现行标准——服务器发送事件：[WHATWG 官方标准](https://html.spec.whatwg.org/multipage/server-sent-events.html?utm_source=chatgpt.com)

说话人 1：问题十五，SSE 的 `EventSource` 是什么？浏览器如何建立连接、接收事件和处理连接错误？

说话人 1：答，`EventSource` 是浏览器提供的原生 JavaScript API，专门用来建立 SSE 连接。

说话人 1：使用起来很简单，创建一个 `EventSource` 对象，传入 SSE 接口地址，浏览器就会尝试建立连接。

说话人 1：连接成功后，可以通过 `onopen` 监听连接建立，通过 `onmessage` 接收默认消息，也可以使用 `addEventListener` 监听服务器指定的自定义事件。

说话人 1：发生连接错误时，可以通过 `onerror` 处理。如果是可以恢复的网络中断，浏览器一般会自动重连。

说话人 1：如果用户不再需要接收数据，可以主动调用 `close()` 关闭连接，避免继续占用网络和服务端资源。

说话人 1：另外，`EventSource` 还提供 `readyState`，可以观察连接处于连接中、已经打开还是已经关闭等状态。

说话人 1：前端常见代码可以这样写：

```
const source = new EventSource("/api/chat/events");

source.onopen = () => {
    console.log("SSE 连接成功");
};

source.onmessage = (event) => {
    console.log("收到数据：", event.data);
};

source.addEventListener("token", (event) => {
    console.log("模型输出：", event.data);
});

source.addEventListener("complete", () => {
    source.close();
});

source.onerror = (error) => {
    console.error("SSE 连接异常", error);
};
```

说话人 1：这里要注意，`onerror` 并不意味着浏览器一定已经永久断开。它可能正在尝试自动重连，因此不能一触发错误就把所有连接状态都当成彻底结束。

说话人 1：参考资料：EventSource: EventSource() constructor | EventSource 构造函数：[MDN 官方开发文档](https://developer.mozilla.org/en-US/docs/Web/API/EventSource/EventSource?utm_source=chatgpt.com)

说话人 1：问题十六，SSE 如何处理连接断开？浏览器自动重连的机制是什么？`Last-Event-ID` 有什么作用？

说话人 1：答，SSE 的一个实用优势就是浏览器原生支持自动重连。

说话人 1：例如，用户的网络突然断开，原来的 SSE 连接无法继续传输。只要连接并非被永久关闭，浏览器就可以等待一段时间，然后重新向服务器发起连接。

说话人 1：如果之前收到的事件包含 `id`，浏览器会记录最后的事件 ID。重新连接时，会通过 `Last-Event-ID` 请求头告诉服务器：“我最后收到的事件位置是这里。”

说话人 1：服务器拿到这个 ID 后，可以查询后面的事件并重新发送，从而恢复部分中断的数据。

说话人 1：但这有一个关键前提：服务器必须自己实现事件保存和重放。浏览器只负责记录和提交最后的事件 ID，不会替服务器保存业务事件。

说话人 1：比如，模型已经生成到第 50 个片段，客户端断开连接。即使浏览器重新连接并带上最后一个事件 ID，如果服务端没有保存之前的生成内容，也没有继续执行任务的机制，仍然无法真正恢复。

说话人 1：另外，浏览器可能重新接收到已经处理过的事件，所以还需要通过事件 ID、序列号和客户端去重机制处理重复数据。

说话人 1：参考资料：HTML Living Standard — The Last-Event-ID header | HTML 现行标准——Last-Event-ID 请求头：[WHATWG 官方标准](https://html.spec.whatwg.org/multipage/server-sent-events.html?utm_source=chatgpt.com#the-last-event-id-header)

说话人 1：问题十七，SSE 的心跳机制是什么？为什么需要定期发送心跳事件或注释？

说话人 1：答，心跳就是在一段时间没有业务数据时，服务端仍然定期发送一些轻量的数据，用来维持连接活跃。

说话人 1：比如，用户发起了一个耗时较长的 AI 请求，模型可能几秒甚至更久都没有返回内容。如果中间有 Nginx、API 网关或者负载均衡器，它们可能因为连接长时间没有数据而判断连接空闲，主动关闭连接。

说话人 1：所以，服务端可以定期发送 SSE 注释，例如：

```
: heartbeat
```

说话人 1：这一行以冒号开头，属于注释，浏览器不会把它作为普通业务消息分发，但能够让网络链路看到有数据经过。

说话人 1：也可以设计专门的业务心跳事件，但如果只是维持连接，通常使用注释就足够了。

说话人 1：心跳间隔应该根据网关、反向代理和服务器的空闲超时来确定，不能设置得太长，也没有必要频繁发送。

说话人 1：另外，心跳只能帮助维持连接，不能证明模型还在正常生成，更不能代替连接故障监控。

说话人 1：参考资料：Using server-sent events | 使用服务器发送事件：[MDN 官方开发文档](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events?utm_source=chatgpt.com)

说话人 1：问题十八，SSE 是否能够保证所有事件都被客户端成功接收？网络断开、重连和重复事件可能产生什么问题？

说话人 1：答，不能。SSE 本身不提供业务层面的端到端可靠交付保证。

说话人 1：例如，服务端发送了一条事件，但客户端可能恰好在接收过程中断网。服务器并不能仅凭自己成功写出了响应，就证明浏览器业务代码已经处理了这条事件。

说话人 1：网络重连时，如果服务器没有记录事件位置，可能出现部分事件丢失；如果服务器从上一个事件位置重新发送，又可能出现重复事件。

说话人 1：所以，对于普通的模型文本输出，可能只需要尽可能连续地推送即可；但如果是订单状态、支付通知或者工单创建结果，就不能只依赖 SSE 传输。

说话人 1：这类重要业务应该保存事件记录，使用唯一事件 ID 和序列号，必要时提供重放能力，并让客户端通过幂等方式处理重复事件。

说话人 1：记住，SSE 负责传输事件，不负责自动实现可靠业务消息队列，也不保证消息一定被消费一次且只消费一次。

## 第三阶段：性能、线程模型与响应式编程

说话人 1：问题十九，同步响应与 SSE 在客户端等待时间、首字节时间（TTFB）、首 Token 时间（TTFT）和整体响应时间方面有什么区别？

说话人 1：答，这几个指标要先区分清楚，否则很容易把 SSE 带来的体验提升误认为模型生成速度提升。

说话人 1：TTFB 是 Time To First Byte，首字节时间，表示从请求发出到客户端收到响应第一个字节所经历的时间。

说话人 1：TTFT 是 Time To First Token，首 Token 时间，在大模型场景中，通常表示从用户提交问题到客户端收到模型第一个有效输出片段的时间。

说话人 1：整体响应时间则是从请求发起到整个模型回答生成并交付完成所经历的时间。

说话人 1：同步响应如果需要等模型生成完整结果才返回，客户端通常要等到最后才能看到完整答案。此时，TTFB 也可能接近整体响应完成时间，但具体还取决于服务端是否提前发送响应头或其他数据。

说话人 1：SSE 则允许服务端更早地发送第一个事件，所以用户可以更早看到模型的第一个输出片段。之后每生成一部分内容，就可以继续推送。

说话人 1：但 SSE 不会自动缩短模型的实际生成时间。假设模型生成完整答案需要 10 秒，无论使用同步响应还是 SSE，模型仍然可能需要 10 秒才能生成全部内容。区别在于，SSE 不需要用户等这 10 秒全部结束才看到第一部分答案。

说话人 1：所以，评估 AI 流式体验时，应该分别观察 HTTP TTFB、模型 TTFT、首个有效内容显示时间和整体生成耗时，而不是只看一个响应时间指标。

说话人 1：问题二十，为什么 SSE 可以让用户更早看到模型生成的内容，但不一定能够缩短大模型生成全部内容的总时间？

说话人 1：答，因为 SSE 改变的是数据交付方式，不是大模型本身的推理速度。

说话人 1：例如，模型需要 8 秒钟生成完整答案。使用同步接口时，用户可能等到第 8 秒才能看到完整内容；使用 SSE 时，模型第 1 秒生成的内容就可以推送给前端，后续内容再陆续返回。

说话人 1：这样用户从第 1 秒就开始看到结果，但模型仍然可能在第 8 秒才真正生成完成。

说话人 1：如果想缩短整体生成时间，还需要从模型本身入手，例如选择更快的模型、减少输入 Token、优化 RAG 检索、减少不必要的工具调用，以及合理设置生成参数。

说话人 1：另外，还要优化首 Token 延迟。比如，RAG 检索耗时、记忆读取耗时和工具调用准备时间，都可能发生在模型正式输出之前。

说话人 1：所以，SSE 主要改善用户感知和内容交付体验，真正提高模型生成速度，还需要优化整个 AI 请求链路。

说话人 1：问题二十一，SSE 是否意味着服务端一定采用异步、非阻塞或响应式编程？为什么需要区分通信方式与服务端执行模型？

说话人 1：答，不意味着。SSE 只规定服务器如何通过 HTTP 向客户端发送事件，并没有规定服务端必须使用什么线程模型。

说话人 1：比如，一个 Spring MVC 接口使用 `SseEmitter` 推送数据，即使底层业务仍然通过阻塞方式调用大模型，也可以实现 SSE。

说话人 1：再比如，Spring WebFlux 可以返回 `Flux<ServerSentEvent<?>>`，利用响应式流逐步向客户端写入事件。

说话人 1：这两种方式都可以实现 SSE，但服务端的 I/O 和线程管理方式不一样。

说话人 1：所以，不能因为接口使用了 `text/event-stream`，就认为系统已经实现了非阻塞处理。还要检查 Controller、业务服务、模型客户端和存储操作是否存在阻塞调用。

说话人 1：这里要记住三个概念：SSE 负责通信格式，异步负责任务执行方式，非阻塞 I/O 负责 I/O 等待时的线程利用方式。

说话人 1：问题二十二，什么是阻塞式 I/O 和非阻塞式 I/O？它们分别如何影响 Java 服务端处理大量长连接的能力？

说话人 1：答，阻塞式 I/O 可以理解为线程发起一个 I/O 操作后，如果数据暂时还没有准备好，线程就需要等待。

说话人 1：例如，传统同步读取数据库或者调用阻塞式 HTTP 客户端时，执行线程可能一直等到结果返回才能继续执行。

说话人 1：非阻塞式 I/O 则不同。线程发起 I/O 操作后，不需要一直停在那里等待，而是可以继续处理其他任务，等数据准备好以后再通过事件机制继续处理。

说话人 1：这在大量长连接场景中尤其重要。假设有几千个客户端保持 SSE 连接，如果每一个连接都长期占用一个专门工作线程，线程资源和上下文切换成本可能很高。

说话人 1：而采用事件驱动的非阻塞模型，一个较少数量的事件循环线程就能够管理大量连接。但这不代表整个业务完全不需要线程，模型调用、数据库访问和其他阻塞操作仍然需要合理调度。

说话人 1：在 Java 中，Spring WebFlux 基于 Reactor 和非阻塞 I/O 提供响应式编程模型；Spring MVC 则基于 Servlet，并提供异步请求处理能力。

说话人 1：还需要注意，JDK 21 的虚拟线程可以降低大量阻塞式任务的线程开销，但它并不会自动把阻塞式 I/O 变成非阻塞式 I/O，也不意味着所有应用都必须迁移到 WebFlux。

说话人 1：问题二十三，Spring MVC 和 Spring WebFlux 在处理 SSE 时有什么区别？`SseEmitter` 与 `Flux` 分别承担什么职责？

说话人 1：答，这道题非常重要，因为它直接关系到我们在 Spring Boot 项目中应该如何选择技术栈。

说话人 1：Spring MVC 是基于 Servlet 的 Web 框架，处理 SSE 时可以使用 `SseEmitter`。它本质上是一个支持异步请求处理的响应发送器，业务代码可以在后续不断调用 `send()` 向客户端发送事件，全部结束以后调用 `complete()`。

说话人 1：例如，Controller 可以先返回一个 `SseEmitter`，然后在另一个执行线程中调用大模型，拿到模型输出片段以后，再通过 `emitter.send()` 发送给前端。

说话人 1：Spring WebFlux 则采用响应式编程模型，可以直接返回 `Flux<ServerSentEvent<String>>`，由响应式框架订阅并持续处理事件流。

说话人 1：两种方式的区别可以简单理解为：`SseEmitter` 是 Spring MVC 提供的 Servlet 异步事件发送工具；`Flux` 是 Reactor 提供的数据流抽象，可以承载多个异步产生的数据元素。

说话人 1：还有一个重要细节，Spring MVC 也支持返回 `Flux` 并将其适配为流式 HTTP 响应，但这不代表 MVC 就变成了 WebFlux。MVC 对响应的写入仍然可能使用阻塞线程执行，而 WebFlux 的设计目标是通过非阻塞 I/O 管理响应流。

说话人 1：所以，选型时不能只看 Controller 的返回类型，还要看应用整体采用的 Web 技术栈和下游调用方式。

说话人 1：参考资料：Asynchronous Requests | Spring MVC 异步请求：[Spring Framework 6.2 官方文档](https://docs.spring.io/spring-framework/reference/6.2/web/webmvc/mvc-ann-async.html?utm_source=chatgpt.com)

说话人 1：参考资料：Spring WebFlux | Spring WebFlux 响应式 Web 框架：[Spring Framework 6.2 官方文档](https://docs.spring.io/spring-framework/reference/6.2/web/webflux.html?utm_source=chatgpt.com)

说话人 1：问题二十四，为什么 SSE 连接数量增加后，需要关注线程资源、连接资源、内存占用和服务端吞吐量？

说话人 1：答，因为 SSE 是长连接，连接建立以后不会马上结束，而是可能持续几秒、几十秒，甚至更长时间。

说话人 1：每个连接都可能占用网络连接、文件描述符、服务端连接管理对象、缓冲区和一定的内存资源。

说话人 1：如果采用 Spring MVC，还要考虑执行模型、异步写入线程池和可能发生的阻塞写入；如果使用 WebFlux，则需要关注事件循环线程是否被阻塞，以及 Reactor 流程中是否存在无限制的数据堆积。

说话人 1：例如，1000 个用户同时发起 AI 流式请求，并不代表服务器只需要处理 1000 个 HTTP 连接就够了。每个请求背后还可能有一个模型供应商连接、历史记忆读取、RAG 查询和数据缓冲任务。

说话人 1：如果没有连接数限制、请求超时、并发限流和资源释放机制，服务器可能出现内存持续增长、连接耗尽或者模型供应商并发额度不足的问题。

说话人 1：所以，企业级 SSE 系统需要监控活跃连接数、平均连接时长、每连接内存、线程池队列、模型并发量和推送失败率，而不是只关注 HTTP QPS。

说话人 1：问题二十五，什么是背压（Backpressure）？当客户端消费速度低于服务端生产速度时，可能出现什么问题？

说话人 1：答，背压可以理解为下游消费方能够向上游表达自己的处理能力，避免上游产生数据的速度远远超过下游消费速度。

说话人 1：例如，大模型每秒生成 100 个数据片段，但客户端网络比较差，每秒只能接收和处理 20 个片段。如果服务端不断生产，数据就可能堆积在应用缓冲区、网络缓冲区或者代理缓冲区中。

说话人 1：堆积时间长了，就可能造成内存增长、推送延迟增加，严重时甚至导致服务资源耗尽。

说话人 1：在 Reactor 中，背压通过 Reactive Streams 的订阅和请求机制进行协调。下游可以按照自身能力请求数据，上游应该尊重这种需求。

说话人 1：但是要注意，原生浏览器 `EventSource` 并没有提供 Reactive Streams 那种 `request(n)` 接口，不能简单认为浏览器会直接向服务端反馈自己还想接收多少个事件。

说话人 1：因此，真实 SSE 系统还需要结合有限缓冲、消费速率控制、超时、丢弃策略或者主动断开慢连接等措施。

说话人 1：如果是模型文本输出，通常可以按照业务规则合并过小的数据片段，但不能随意丢弃有意义的文本内容。

说话人 1：问题二十六，当客户端主动关闭 SSE 连接时，服务端是否应该继续调用大模型？如何实现请求取消、资源释放和模型调用终止？

说话人 1：答，一般来说，如果用户已经明确停止生成，系统应该尽量取消后续模型调用，避免继续消耗 Token 和服务器资源。

说话人 1：但不能只关闭浏览器连接就认为模型一定停止了，因为 HTTP 连接关闭和模型供应商停止生成，是两个不同的动作。

说话人 1：如果使用 WebFlux，客户端断开后，响应式流通常会收到取消信号。应用可以利用 `doFinally` 或相关取消处理逻辑清理资源，并把取消继续传递到下游模型客户端。

说话人 1：如果使用 Spring MVC 的 `SseEmitter`，可以通过 `onCompletion()`、`onTimeout()` 和 `onError()` 等回调识别请求生命周期结束，然后取消对应的模型订阅或异步任务。

说话人 1：例如，Spring AI 的流式调用返回一个 `Flux<String>`，订阅以后得到一个 Disposable。用户停止生成时，可以通过取消订阅来通知上游停止继续发送数据。

说话人 1：不过，能否真正中止供应商侧的推理，还取决于具体模型客户端和 HTTP 请求是否支持取消传播。有些情况下只能停止本地消费，远端任务不一定立即停止。

说话人 1：因此，生产系统还应该保存请求 ID 和生成任务状态，明确区分正常完成、用户取消、超时和模型异常，并保证连接关闭后相关资源能够及时释放。

说话人 1：问题二十七，反向代理、Nginx、网关和负载均衡器可能如何影响 SSE？为什么缓冲、超时和连接空闲配置需要特别关注？

说话人 1：答，这是生产环境中 SSE 最容易出现问题的地方之一。

说话人 1：在本地直接调用接口时，模型内容可能能够逐字返回。但部署以后，如果请求经过 Nginx、API Gateway 或其他反向代理，代理可能先接收和缓存上游数据，再按自己的策略发送给客户端。

说话人 1：这样就会出现一种典型现象：后端日志显示模型每次生成一个 Token 都已经调用 `send()` 或写入响应，但前端直到模型全部生成完成后才一次性看到内容。

说话人 1：这时候就要重点检查代理缓冲。例如，Nginx 的 `proxy_buffering` 默认是开启的，可以针对 SSE 路径关闭：

```
location /api/chat/stream {
    proxy_pass http://chat-service;

    proxy_http_version 1.1;

    proxy_buffering off;

    proxy_read_timeout 3600s;
}
```

说话人 1：也可以由上游根据需要设置 `X-Accel-Buffering: no`，让 Nginx 不再缓冲该响应，前提是代理没有配置忽略这个响应头。

说话人 1：第二个问题是超时。模型生成时间可能比较长，如果网关的读取超时小于模型生成时间，连接就可能被提前关闭。

说话人 1：第三个问题是连接空闲。如果模型很长时间没有输出，而代理又有空闲连接超时，就需要通过心跳机制维持连接。

说话人 1：所以，SSE 上线前不仅要检查 Spring Boot Controller，还必须实际经过 Nginx 和网关测试。后端能推送，不代表整个网络链路都能实时推送。

说话人 1：参考资料：Module ngx_http_proxy_module | Nginx HTTP 代理模块：[Nginx 官方文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html?utm_source=chatgpt.com)

## 第四阶段：Spring AI 中的同步调用与流式调用

说话人 1：问题二十八，在 Spring AI 中，`ChatClient` 的 `call()` 和 `stream()` 分别代表什么调用模式？两者的返回类型和执行流程有什么区别？

说话人 1：答，这两个方法就是 Spring AI 提供的两种主要模型调用方式。

说话人 1：`call()` 对应非流式调用，适合一次性获取完整模型响应。调用之后，可以通过 `.content()` 得到最终的完整文本。

说话人 1：`stream()` 对应流式调用，适合逐步消费模型生成的内容，通常返回 Reactor 的 `Flux`，模型产生新的内容片段，就可以继续向下游发送。

说话人 1：例如，普通调用可以这样写：

```
String answer = chatClient.prompt()
        .user("解释一下 Java 线程池")
        .call()
        .content();
```

说话人 1：流式调用则是：

```
Flux<String> output = chatClient.prompt()
        .user("解释一下 Java 线程池")
        .stream()
        .content();
```

说话人 1：第一种得到完整字符串，第二种得到一条可以持续产生数据的响应式数据流。

说话人 1：但还有一个细节，`call()` 本身并不是一调用就完成整个模型请求。它先选择非流式调用模式，真正执行模型调用发生在后续调用 `.content()`、`.chatResponse()` 等取结果方法时。

说话人 1：参考资料：Chat Client API | 聊天客户端 API：[Spring AI 1.1 官方文档](https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html?utm_source=chatgpt.com)

说话人 1：问题二十九，`call().content()` 与 `stream().content()` 分别返回什么？为什么前者通常得到完整字符串，而后者能够逐步消费生成内容？

说话人 1：答，`call().content()` 返回的是一个完整的 `String`，而 `stream().content()` 返回的是 `Flux<String>`。

说话人 1：例如，模型最终生成“Spring Boot 是一个基于 Spring 的应用开发框架”。

说话人 1：调用 `call().content()`，业务代码拿到的就是这整句话。

说话人 1：调用 `stream().content()`，则可能先收到“Spring Boot 是一个”，再收到“基于 Spring 的”，最后收到“应用开发框架”。

说话人 1：这里一定要注意，`Flux<String>` 中的每个元素不一定严格对应模型的一个 Token。它可能是一个 Token、多个 Token，也可能是供应商协议中定义的一个文本片段。

说话人 1：所以，开发者应该把它理解成一系列逐步产生的文本片段，而不是假设每次 `onNext` 都只会返回一个字。

说话人 1：问题三十，Spring AI 中的 `Flux<String>` 是什么？它与普通的 `String` 在数据处理方式上有什么区别？

说话人 1：答，`String` 是一个已经存在的完整字符串，而 `Flux<String>` 是 Reactor 提供的响应式数据流，可以在未来不断产生多个字符串元素。

说话人 1：比如：

```
String result = "Hello World";
```

说话人 1：这里的结果已经完整存在，可以直接读取。

说话人 1：而：

```
Flux<String> result = Flux.just(
        "Hello",
        " ",
        "World"
);
```

说话人 1：这里表达的是一条包含多个数据元素的数据流。下游订阅以后，才能逐个接收这些元素。

说话人 1：这也是响应式编程中非常重要的一点：`Flux` 是 Publisher，通常具有惰性执行特征，只有发生订阅以后，数据流才真正开始执行。

说话人 1：因此，Spring AI 返回 `Flux<String>`，并不意味着模型内容已经全部生成完毕，也不意味着数据已经发送给浏览器。它只是给上游和下游提供了一种持续传递数据的方式。

说话人 1：如果业务代码使用 `collectList().block()`，把全部片段收集起来并阻塞等待完成，那么又会变回等待完整结果的处理方式。

说话人 1：问题三十一，Spring AI 的流式输出是否等同于 SSE？`Flux` 与 HTTP SSE 事件之间需要经过什么转换？

说话人 1：答，不等同于 SSE。

说话人 1：Spring AI 的 `Flux<String>` 解决的是模型内容如何持续传递给 Java 应用；SSE 解决的是这些内容如何按照 HTTP 事件格式发送给浏览器。

说话人 1：中间需要经过 Web 层的响应转换。

说话人 1：例如，Spring AI 返回一个 `Flux<String>`，Controller 可以使用 `map()` 把每个文本片段包装成 `ServerSentEvent<String>`，再返回给浏览器。

说话人 1：示意代码：

```
Flux<ServerSentEvent<String>> events =
        chatClient.prompt()
                .user("解释一下 SSE")
                .stream()
                .content()
                .map(text ->
                        ServerSentEvent.builder(text)
                                .event("token")
                                .build()
                );
```

说话人 1：这里的 `Flux` 仍然是数据流，而 `ServerSentEvent` 负责表达 SSE 事件中的数据和事件类型。

说话人 1：最终还需要 Controller 声明 `text/event-stream`，由 Spring Web 层按照 SSE 协议写出响应。

说话人 1：所以，完整链路是：大模型产生内容、Spring AI 转换为 Flux、Controller 包装事件、HTTP SSE 推送、浏览器解析并显示。

说话人 1：问题三十二，如果 Spring AI 返回 `Flux<String>`，如何通过 Spring Boot WebFlux 将其转换成 SSE 响应发送给前端？

说话人 1：答，如果采用 Spring WebFlux，直接在 Controller 中返回 `Flux<ServerSentEvent<String>>` 就可以了。

说话人 1：例如：

```
@RestController
@RequestMapping("/api/chat")
public class ChatController {

    private final ChatClient chatClient;

    public ChatController(ChatClient.Builder builder) {
        this.chatClient = builder.build();
    }

    @PostMapping(
        value = "/stream",
        produces = MediaType.TEXT_EVENT_STREAM_VALUE
    )
    public Flux<ServerSentEvent<String>> stream(
            @RequestBody ChatRequest request) {

        return chatClient.prompt()
                .user(request.message())
                .stream()
                .content()
                .map(text -> ServerSentEvent.builder(text)
                        .event("token")
                        .build());
    }
}
```

说话人 1：这里最重要的是三点。

说话人 1：第一，使用 Spring AI 的 `stream().content()` 获取模型片段。第二，通过 `map()` 把每个片段转换成 SSE 事件。第三，Controller 声明 `MediaType.TEXT_EVENT_STREAM_VALUE`，让 Spring WebFlux 按照 SSE 格式向客户端持续写出数据。

说话人 1：实际项目不能只发送 Token 事件，还应该设计开始、结束和错误事件。例如，模型开始生成时发送 `start`，每段内容发送 `token`，正常结束发送 `done`，遇到异常时发送 `error`。

说话人 1：另外，最好使用 `ServerSentEvent` 包装对象，而不是只返回裸字符串，因为后续可以增加事件 ID、业务类型和重连信息。

说话人 1：需要注意，这段代码展示的是 WebFlux Controller 层的基本实现。实际项目还需要处理用户身份、会话记忆、异常和取消信号。

说话人 1：参考资料：Return Values | WebFlux 控制器返回值处理：[Spring Framework 6.2 官方文档](https://docs.spring.io/spring-framework/reference/6.2/web/webflux/controller/ann-methods/return-types.html?utm_source=chatgpt.com)

说话人 1：问题三十三，如果使用 Spring MVC，如何利用 `SseEmitter` 实现大模型流式响应？它与 WebFlux 的 `Flux` 实现方式有什么区别？

说话人 1：答，Spring MVC 不需要因为要实现 SSE，就必须把整个项目改成 WebFlux。可以使用 `SseEmitter` 实现服务器持续推送事件。

说话人 1：例如，Controller 先创建一个 `SseEmitter` 并返回，然后让模型调用在后续执行。每当 Spring AI 的 `Flux<String>` 产生一个文本片段，就调用 `emitter.send()` 发送给前端。

说话人 1：示意代码可以这样理解：

```
@PostMapping(
    value = "/stream",
    produces = MediaType.TEXT_EVENT_STREAM_VALUE
)
public SseEmitter stream(@RequestBody ChatRequest request) {

    SseEmitter emitter = new SseEmitter(120_000L);

    Disposable subscription = chatClient.prompt()
            .user(request.message())
            .stream()
            .content()
            .subscribe(
                text -> {
                    try {
                        emitter.send(
                            SseEmitter.event()
                                .name("token")
                                .data(text)
                        );
                    } catch (IOException e) {
                        throw new UncheckedIOException(e);
                    }
                },
                emitter::completeWithError,
                emitter::complete
            );

    emitter.onCompletion(subscription::dispose);
    emitter.onTimeout(() -> subscription.dispose());

    return emitter;
}
```

说话人 1：这里主要展示两种组件的配合关系，完整生产实现还需要提前注册生命周期回调，妥善处理订阅建立与取消之间的竞态，并根据客户端断开、发送失败和超时情况统一释放资源。

说话人 1：`SseEmitter` 主要负责 Servlet 环境中的异步事件发送，`Flux` 主要负责上游模型数据流的生产和传递。

说话人 1：使用 MVC 时，Servlet 异步机制可以释放最初处理请求的容器线程，但响应写入仍然可能使用阻塞线程。使用 WebFlux 时，响应输出由响应式框架通过非阻塞 I/O 管理。

说话人 1：所以，两种方式都可以实现实时 SSE，但并发模型、资源管理和阻塞行为不同。

说话人 1：问题三十四，Spring AI 1.1.x 的流式调用需要哪些相关依赖与技术栈支持？为什么需要核实 Servlet 与 Reactive 技术栈的组合？

说话人 1：答，这个问题结合 Spring AI 1.1.x 非常重要，因为它的 ChatClient 并不是完全独立于 Servlet 和 Reactive 两种编程模型的。

说话人 1：在 Spring AI 1.1.8 官方文档中，有明确的实现说明：流式调用通过 Reactive 技术栈支持，命令式应用如果要使用流式调用，需要引入 Reactive 技术栈，例如 `spring-boot-starter-webflux`。

说话人 1：同时，非流式调用需要 Servlet 技术栈，响应式应用如果还要使用非流式调用，需要包含 Servlet 技术栈，例如 `spring-boot-starter-web`，并注意相关调用可能产生阻塞。

说话人 1：因此，如果我们开发一个以 Spring MVC 为主的 AI 项目，需要同步调用和流式调用同时存在，就可能需要同时引入两个 Starter：

```
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-webflux</artifactId>
</dependency>
```

说话人 1：这里有一个非常容易踩的坑：同时引入 `spring-boot-starter-web` 和 `spring-boot-starter-webflux`，Spring Boot 默认仍然会选择 Spring MVC，而不是自动切换到 WebFlux。

说话人 1：这是因为很多 MVC 项目引入 WebFlux，只是为了使用响应式 HTTP 客户端和 Reactor，而不是为了更换整个 Web 服务端。

说话人 1：所以，对当前 JDK 21、Spring Boot 3.5.x、Spring AI 1.1.x 的项目，我会优先考虑保留 Spring MVC 作为 Web 服务端，再根据 Spring AI 流式调用的要求引入 Reactive 依赖。

说话人 1：如果要改成真正的 WebFlux 服务端，则必须另外确认 Spring AI 非流式调用、Servlet 相关依赖及业务阻塞操作的兼容性，不能只修改一个启动配置就认为全部正常。

说话人 1：另外，Spring AI 1.1.x 的部分 Tool Calling 流程仍然采用命令式处理，可能产生阻塞，这一点也会影响完整响应式链路。

说话人 1：参考资料一：Chat Client API | 聊天客户端 API：[Spring AI 1.1.8 官方文档](https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html?utm_source=chatgpt.com)

说话人 1：参考资料二：Reactive Web Applications | Spring Boot 响应式 Web 应用：[Spring Boot 3.5 官方文档](https://docs.spring.io/spring-boot/3.5/reference/web/reactive.html?utm_source=chatgpt.com)

说话人 1：参考资料三：Spring AI Project | Spring AI 项目及版本兼容说明：[Spring AI 官方 GitHub 仓库](https://github.com/spring-projects/spring-ai?utm_source=chatgpt.com)

说话人 1：问题三十五，在 Spring AI 流式调用中，如何处理模型返回的多个响应片段、最终完成信号、异常信号和取消信号？

说话人 1：答，Spring AI 的流式响应本质上是一条 Reactor 数据流，所以我们需要理解它的几个生命周期信号。

说话人 1：第一，`onNext`，表示上游产生了一个新的数据元素。例如，模型生成了一段新的文本内容，下游就会收到一个 `String` 片段。

说话人 1：第二，`onComplete`，表示数据流正常结束。模型已经完成本次输出，业务可以发送结束事件、整理完整答案并保存最终记录。

说话人 1：第三，`onError`，表示数据流发生异常。例如，供应商接口超时、网络断开或者模型返回异常。

说话人 1：第四，`cancel`，表示下游主动取消订阅。例如，用户点击停止生成，或者浏览器关闭连接。

说话人 1：这四种情况需要分别处理，不能只写一个 `subscribe()` 就认为流式调用完成了。

说话人 1：尤其是取消信号，用户停止生成以后，系统应该尽量停止后续模型消费和不必要的资源占用。异常发生时，则要记录已生成的部分内容，并根据业务需要标记为失败或部分完成。

说话人 1：还要注意，如果需要最终模型元数据、完成原因或者供应商返回的其他信息，就不应该只使用 `Flux<String>`，可以考虑消费 `Flux<ChatResponse>`，因为它包含比纯文本更多的响应信息。

说话人 1：问题三十六，如果模型支持流式输出，但后端接口使用同步方式收集全部结果后再返回，为什么前端仍然无法实现实时打字效果？

说话人 1：答，因为中间的后端已经把流式输出重新变成了完整结果。

说话人 1：例如，模型底层确实使用了 `stream()`，但是业务代码这样写：

```
String result = chatClient.prompt()
        .user("介绍一下 Spring AI")
        .stream()
        .content()
        .collectList()
        .block()
        .stream()
        .collect(Collectors.joining());
```

说话人 1：这里发生了什么？模型原本可以逐步产生多个文本片段，但是代码使用 `collectList()` 把所有片段收集起来，再通过 `block()` 等待整个数据流结束，最后才拼成完整字符串。

说话人 1：如果 Controller 最后只返回这个 `String`，前端自然还是一次性拿到完整结果。

说话人 1：所以，要实现真正的端到端流式输出，不能只看大模型供应商是否支持 Stream，还要检查后端有没有在任何地方把数据流提前收集、阻塞或者缓冲起来。

说话人 1：问题三十七，如果后端使用 SSE，但底层模型调用实际上是同步阻塞的，这种组合可能产生什么性能问题？

说话人 1：答，首先要看同步调用发生在什么位置。

说话人 1：第一种情况，如果先调用 `chatClient.call().content()`，等模型生成完整答案以后，再把完整答案包装成一个 SSE 事件发送，那么虽然接口形式上是 SSE，实际并没有实现实时模型输出。

说话人 1：第二种情况，如果 Controller 已经创建了 SSE 连接，然后在一个工作线程中使用阻塞方式等待模型返回，再把结果分段写入 SSE，那么前端虽然可能看到分段内容，但执行线程仍然可能长期被占用。

说话人 1：例如，同时有 1000 个用户发起长时间的模型请求，如果每个请求都长期占用一个阻塞工作线程，就会对线程池造成很大压力。

说话人 1：即使使用 JDK 21 虚拟线程，也不代表可以无限制地创建模型请求。供应商并发额度、数据库连接、内存、网络连接和业务线程池仍然受到限制。

说话人 1：因此，SSE 和底层执行模型要分别设计。如果目标是大量并发流式请求，就应该尽可能让模型流式客户端、业务处理和 HTTP 响应形成合理的异步或响应式链路。

说话人 1：问题三十八，Spring AI 的流式响应如何与 Advisor、ChatMemory、RAG 和 Tool Calling 配合？哪些组件可能引入阻塞操作或影响首 Token 延迟？

说话人 1：答，这道题实际上是在考察整个 AI 请求链路，而不仅仅是 `stream()` 方法。

说话人 1：首先是 ChatMemory。系统在模型调用前可能需要读取历史消息，如果底层存储响应慢，就会延迟模型请求开始。

说话人 1：其次是 RAG。模型生成之前，可能要查询向量数据库、执行检索和组装文档上下文。如果检索过程很慢，TTFT 就会受到影响。

说话人 1：第三是 Advisor。Advisor 可以在模型调用前修改 Prompt、补充上下文，也可以处理模型响应。不同 Advisor 的实现方式不同，可能涉及阻塞操作、线程调度或额外模型调用。

说话人 1：Spring AI 1.1.8 的实现说明中提到，内置 Advisor 在普通调用时执行阻塞操作，在流式调用时使用非阻塞的流式处理方式，但具体调度器也需要根据 Advisor 实现进行配置。

说话人 1：第四是 Tool Calling。模型可能先决定调用某个工具，服务端执行数据库查询或者业务 API，然后再把工具结果交给模型继续生成答案。

说话人 1：这意味着用户可能已经建立 SSE 连接，但在工具执行完成之前还没有收到真正的文本内容。并且 Spring AI 1.1.x 的 Tool Calling 仍存在命令式处理和阻塞工作流，需要特别关注。

说话人 1：所以，排查首 Token 延迟不能只看模型本身。要拆成记忆读取、RAG 检索、Advisor 执行、模型请求建立、模型首 Token 生成和网络推送几个阶段分别统计耗时。

说话人 1：如果发现 RAG 查询占了 2 秒，就应该优化检索；如果工具调用耗时很长，就应该优化业务 API；如果模型本身 TTFT 很高，再考虑更换模型或调整模型参数。

说话人 1：参考资料：Chat Client API | 聊天客户端 API：[Spring AI 1.1.8 官方文档](https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html?utm_source=chatgpt.com)

## 第五阶段：前后端交互与工程实现

说话人 1：问题三十九，前端如何使用浏览器 `EventSource` 接收 SSE？如何监听 `message`、自定义事件、连接错误和连接关闭？

说话人 1：答，前端可以直接使用浏览器原生提供的 `EventSource`，不需要自己实现 HTTP 长连接。

说话人 1：首先创建连接：

```
const source = new EventSource("/api/chat/events");
```

说话人 1：连接建立后，可以通过 `onopen` 处理连接成功，通过 `onmessage` 接收默认消息，通过 `onerror` 处理连接错误。

说话人 1：如果服务器发送的是自定义事件，例如 `event: token`，就需要使用 `addEventListener` 进行监听：

```
source.addEventListener("token", event => {
    console.log(event.data);
});

source.addEventListener("complete", event => {
    console.log("生成完成", event.data);
    source.close();
});

source.addEventListener("error", event => {
    console.error("业务错误", event.data);
});
```

说话人 1：这里还有一个容易混淆的地方，浏览器原生的 `error` 事件和服务端自定义的 `event: error` 不是同一个概念。

说话人 1：前者代表 EventSource 连接层出现错误，后者可以代表业务层主动发送了一个错误事件。两者应该分别处理。

说话人 1：最后，当用户主动停止接收数据时，调用 `source.close()` 关闭连接。

说话人 1：参考资料：Using server-sent events | 使用服务器发送事件：[MDN 官方开发文档](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events?utm_source=chatgpt.com)

说话人 1：问题四十，为什么原生 `EventSource` 与普通 `fetch` 在请求方法、请求体和自定义请求头方面存在差异？聊天接口为什么有时选择 `fetch` 读取流，而不是直接使用 `EventSource`？

说话人 1：答，因为浏览器原生的 `EventSource` 是专门为 SSE 设计的 API，它的请求能力比较固定。

说话人 1：创建 `EventSource` 时，主要提供事件流 URL 和 `withCredentials` 配置。它不提供像普通 `fetch` 那样自由指定 HTTP 请求方法、JSON 请求体和任意自定义请求头的接口。

说话人 1：例如，AI 聊天请求通常需要同时提交用户问题、会话 ID 和请求 ID，而且可能需要在请求头中携带 JWT。

说话人 1：这种情况下，使用原生 `EventSource` 直接发起一个带 JSON 请求体的 POST 请求就不合适。

说话人 1：一种方式是使用 `fetch`：

```
const response = await fetch("/api/chat/stream", {
    method: "POST",
    headers: {
        "Content-Type": "application/json",
        "Authorization": `Bearer ${token}`
    },
    body: JSON.stringify({
        conversationId: "conversation-001",
        message: "解释一下 SSE"
    })
});
```

说话人 1：然后通过 `response.body` 获取 `ReadableStream`，使用 `getReader()` 逐步读取服务器返回的数据，再按照 SSE 格式解析事件。

说话人 1：这样做可以同时支持 POST、请求体和自定义请求头，但需要自己处理流式解码、事件分隔、异常和取消操作。

说话人 1：另一种方式是先通过 POST 创建一个生成任务，服务器返回 `taskId`，再使用 `EventSource` 连接对应任务的事件地址。

说话人 1：两种方案各有优势。原生 EventSource 自带 SSE 解析和重连机制，使用更简单；Fetch 灵活性更高，适合需要 POST 请求体和 JWT 请求头的 AI 聊天接口。

说话人 1：还有一点，不能为了让 EventSource 支持身份认证，就把长期有效的 JWT 直接放到 URL 查询参数中，因为 URL 可能进入访问日志、浏览器历史和其他记录系统。

说话人 1：参考资料：Using the Fetch API | 使用 Fetch API：[MDN 官方开发文档](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch?utm_source=chatgpt.com)

说话人 1：问题四十一，如果需要同时传递用户问题、会话 ID 和身份认证信息，应该如何设计前后端 SSE 接口？

说话人 1：答，我会先根据前端使用的是原生 EventSource 还是 Fetch，决定接口的交互方式。

说话人 1：如果使用 Fetch，可以直接设计一个 POST 接口：

```
POST /api/chat/stream
Authorization: Bearer <token>
Content-Type: application/json
```

说话人 1：请求体包含：

```
{
  "conversationId": "conversation-001",
  "requestId": "request-001",
  "message": "3号设备出现E102报警，应该怎么处理？"
}
```

说话人 1：服务器验证 JWT，校验会话归属和请求 ID，再调用 Spring AI。模型返回的文本片段通过同一个 POST 请求的 SSE 响应持续推送给前端。

说话人 1：如果采用原生 EventSource，可以拆成两个接口。第一个 POST 接口创建生成任务，返回 `generationId`；第二个 GET 接口通过这个 ID 建立 SSE 连接，持续接收生成事件。

说话人 1：例如：

```
POST /api/chat/generations
GET  /api/chat/generations/{generationId}/events
POST /api/chat/generations/{generationId}/cancel
```

说话人 1：这样，任务创建、事件订阅和取消操作各自独立，适合需要重连、断点恢复和任务状态查询的业务。

说话人 1：无论采用哪种方案，用户身份和会话权限都应该在服务端验证，不能因为客户端传入了某个会话 ID，就直接允许访问对应的历史记录。

说话人 1：问题四十二，如何设计 SSE 事件格式，使其能够区分模型内容片段、开始事件、结束事件、错误事件和业务状态事件？

说话人 1：答，不能把所有信息都当成普通文本发送，最好设计统一的事件协议。

说话人 1：例如，可以设计五种事件：

说话人 1：第一，`start`，表示模型生成任务已经开始；第二，`token`，表示本次产生了一个新的文本片段；第三，`status`，表示当前业务处理进度；第四，`error`，表示执行过程中发生异常；第五，`done`，表示本次生成正常结束。

说话人 1：对应的 SSE 数据可以这样组织：

```
id: 1
event: start
data: {"requestId":"request-001"}

id: 2
event: token
data: {"text":"Spring AI "}

id: 3
event: token
data: {"text":"支持流式调用"}

id: 4
event: done
data: {"finishReason":"stop"}
```

说话人 1：这样前端不需要猜测收到的数据是什么，可以根据事件类型执行不同的逻辑。

说话人 1：如果发生错误，则发送结构化错误信息，例如错误码、错误描述和请求 ID，而不是把 Java 异常堆栈直接暴露给浏览器。

说话人 1：另外，事件 ID 应该由服务端维护，保证同一次生成任务的事件可以按照明确的顺序识别和追踪。

说话人 1：问题四十三，模型生成过程中发生异常，服务器已经向客户端发送部分内容后，还能否正常返回 HTTP 错误状态码？应该如何设计流内错误协议？

说话人 1：答，通常不能再通过普通 HTTP 状态码改变已经提交的响应。

说话人 1：这是因为服务器一旦开始发送响应头和响应体，HTTP 响应就可能已经提交。此时，原来的 HTTP 200 或其他状态码已经发送给客户端，服务器不能再把它改成 HTTP 500。

说话人 1：例如，模型已经成功生成了前面三段内容，第四段突然发生网络超时。这时候客户端已经收到了部分答案，服务器不能再重新发送一个完整的 HTTP 500 响应覆盖之前的内容。

说话人 1：比较合理的设计是，在连接建立之前完成身份校验、请求参数校验和权限验证。此时如果参数错误，可以直接返回 HTTP 400；如果用户没有权限，可以返回 HTTP 403。

说话人 1：如果已经进入 SSE 推送阶段才发生错误，就应该发送一个 `error` 事件，然后结束事件流。

说话人 1：例如：

```
event: token
data: {"text":"当前设备的报警可能与"}

event: error
data: {"code":"MODEL_TIMEOUT","message":"模型服务暂时不可用"}
```

说话人 1：这样前端可以保留已经收到的部分内容，同时明确显示后续生成失败，而不是把这次请求误认为正常完成。

说话人 1：这里还有一个设计重点，`error` 和 `done` 应该有明确的终止语义。出现错误以后，不能再无条件发送一个表示正常成功的完成事件。

说话人 1：问题四十四，如何处理客户端刷新页面、主动停止生成、网络断开和重新连接等情况？是否需要请求 ID 和生成任务 ID？

说话人 1：答，这几种情况虽然表面上都是连接中断，但业务含义不一样，应该分别处理。

说话人 1：第一，用户刷新页面。如果系统只维护一个内存中的 SSE 连接，刷新以后原连接就会被关闭，需要重新建立连接。

说话人 1：第二，用户主动停止生成。这种情况应该发送明确的取消请求，告诉服务端停止当前生成任务，而不是只让浏览器关闭连接。

说话人 1：第三，网络突然断开。这种情况可能是意外中断，系统可以根据任务状态和事件记录决定是否允许恢复。

说话人 1：第四，重新连接。如果需要从上一次接收的位置继续，就必须保存事件记录，并利用事件 ID 或序列号确定从哪里补发。

说话人 1：因此，建议至少区分两个标识：`requestId` 用于识别本次用户请求，`generationId` 用于识别实际生成任务。每条 SSE 事件再通过 `eventId` 或序列号识别。

说话人 1：例如，用户发送一个问题后，服务器创建生成任务 G001。即使浏览器关闭，只要业务允许任务继续运行，用户再次打开页面也可以根据 G001 恢复事件订阅。

说话人 1：但这里需要明确业务策略：用户主动点击停止时，应当取消生成；网络意外断开时，则可以选择继续生成并允许重新订阅，也可以选择取消生成以节省成本。

说话人 1：不能把这两种情况简单处理成同一种断开事件。

说话人 1：问题四十五，多个用户同时发起流式请求时，如何保证不同用户、不同会话之间的事件不会串流？

说话人 1：答，关键是让每一次生成任务拥有独立的请求上下文和事件发布链路。

说话人 1：例如，用户 A 发起请求，生成任务 G001；用户 B 发起请求，生成任务 G002。两个任务必须分别绑定自己的用户 ID、会话 ID 和生成 ID。

说话人 1：如果后端使用 Reactor，每次请求都应该形成自己的独立响应式订阅，不能把所有用户的生成片段无条件写入同一个全局 `Flux` 或全局消息发送器。

说话人 1：如果使用 `SseEmitter`，也应该保证每个生成任务对应独立的 Emitter，并且在任务结束或连接断开后清理对应映射。

说话人 1：另外，用户身份校验必须发生在订阅之前。即使用户知道另一个任务的 generationId，也不能直接订阅其他用户的事件。

说话人 1：最后还要正确传播用户上下文。响应式线程可能发生切换，不能完全依赖 `ThreadLocal` 保存身份、租户等信息，需要结合 Reactor Context 或 Spring 提供的上下文传播机制。

说话人 1：这样才能避免事件串流、跨用户读取和上下文丢失。

说话人 1：问题四十六，SSE 如何与 Spring Security、JWT、网关鉴权和跨域配置配合？如何避免长连接中的身份验证与权限失效问题？

说话人 1：答，首先要解决连接建立时的身份认证。

说话人 1：如果使用 Fetch 发起 POST SSE 请求，可以像普通 HTTP 请求一样通过 `Authorization` 请求头携带 JWT，Spring Security 仍然可以在请求进入 Controller 之前完成认证和授权。

说话人 1：如果使用原生 EventSource，则需要考虑它不能自由添加 Authorization 请求头的问题。可以采用安全的 Cookie 认证，并在跨域场景下合理配置 `withCredentials`，或者采用前面说的 POST 创建任务、GET 订阅事件的方式。

说话人 1：跨域时，还要正确配置 CORS。特别是允许携带 Cookie 时，不能简单地使用任意来源 `*` 配合凭据模式。

说话人 1：其次，要注意长连接的身份生命周期。用户连接建立时通过了 JWT 校验，不代表连接持续几十分钟以后，用户的权限依然没有变化。

说话人 1：普通情况下，HTTP 认证主要发生在连接建立阶段。长连接持续期间，Token 过期、用户被禁用或会话权限被撤销，不会自动让服务器重新执行完整认证流程。

说话人 1：因此，对于敏感业务，可以在生成任务执行期间检查任务状态和授权状态，在必要时主动关闭连接、取消生成并释放资源。

说话人 1：网关层也要配置相应的连接超时、转发策略和身份信息传递，确保网关不会因为读取超时提前关闭 SSE。

说话人 1：核心原则就是：连接建立时完成认证，任务执行过程中保证授权边界持续有效，连接结束后释放资源。

## 第六阶段：可靠性、测试与故障诊断

说话人 1：问题四十七，如何通过单元测试、集成测试和浏览器实际验证，证明 SSE 能够逐步推送数据，而不是等待生成结束后一次性返回？

说话人 1：答，这个测试不能只验证接口最后有没有返回内容，而是要验证数据是否真的分批到达客户端。

说话人 1：第一，单元测试。可以通过 Reactor 的 `StepVerifier` 测试模型返回的 `Flux`，验证是否产生了多个数据片段，是否正常完成，以及出现异常时是否按照预期处理。

说话人 1：第二，接口集成测试。可以使用 `WebTestClient` 或适合当前 Web 技术栈的测试客户端，检查响应状态码、`Content-Type` 和事件内容。

说话人 1：但这里有一个细节：只验证最终响应体包含多段文本是不够的。因为即使服务端先把所有结果收集完，再一次性返回，测试也可能通过。

说话人 1：因此，应该使用带有时间间隔的测试数据，例如第一秒发送 A，第二秒发送 B，第三秒发送 C，检查客户端是否能够提前收到 A，而不是第三秒结束以后才收到 ABC。

说话人 1：第三，真实浏览器测试。打开浏览器开发者工具的 Network 面板，观察 SSE 请求是否持续保持 Pending 状态，以及 Response 是否随着模型生成逐步增加。

说话人 1：也可以使用：

```
curl -N http://localhost:8080/api/chat/stream
```

说话人 1：这里 `-N` 的作用是关闭 curl 自身的输出缓冲，方便观察服务器逐步返回的数据。

说话人 1：最后，还要经过真实 Nginx 和网关测试。因为本地测试通过，不代表上线后的代理没有重新缓冲数据。

说话人 1：所以，真正的验收标准应该包括：数据分批产生、客户端分批收到、连接生命周期正确，以及代理环境下仍然能够实时推送。

说话人 1：问题四十八，SSE 已经返回响应头，但前端始终收不到实时内容，你会从模型供应商、Spring AI、Controller、响应头、代理缓冲和前端消费几个环节如何排查？

说话人 1：答，我会沿着完整数据链路逐层排查，首先确认到底是哪一层没有及时输出。

说话人 1：第一步，检查模型供应商。确认当前调用是否真正启用了流式模式，供应商是否已经持续返回数据片段。

说话人 1：第二步，检查 Spring AI。确认代码使用的是 `.stream().content()`，而不是 `.call().content()`，并检查有没有使用 `collectList().block()` 之类的操作，把数据流重新聚合成完整结果。

说话人 1：第三步，检查 Controller。确认返回的是 `Flux`、`SseEmitter` 或其他真正支持流式发送的响应对象，而不是等待模型完成以后才返回一个完整字符串。

说话人 1：第四步，检查响应头。确认 `Content-Type` 是 `text/event-stream`，事件格式正确，并且没有错误的缓存配置。

说话人 1：第五步，检查 Nginx、网关和负载均衡器。尤其是 Nginx 的 `proxy_buffering` 是否开启，是否存在网关读取超时和响应缓冲。

说话人 1：第六步，检查前端消费逻辑。确认浏览器是否正确解析 SSE，或者 Fetch 是否正确读取 `ReadableStream`，有没有把所有数据收集完才更新 UI。

说话人 1：实际排查时，我会在模型返回、Flux 订阅、Controller 写出、网关转发和浏览器接收这几个位置分别记录时间戳。

说话人 1：例如，模型第 1 秒已经返回第一个片段，Controller 也在第 1 秒完成写出，但浏览器直到第 10 秒才收到内容，那么问题就很可能发生在代理缓冲或前端消费环节。

说话人 1：这种分层排查比直接修改 Controller 或不断调整 Prompt 更有效。

说话人 1：问题四十九，如果 SSE 连接运行一段时间后自动断开，你会检查哪些超时、心跳、网关和连接管理配置？

说话人 1：答，首先要区分是服务端主动结束、浏览器主动关闭，还是中间网络设备断开。

说话人 1：第一，检查 Spring MVC 的异步请求超时。如果使用 `SseEmitter`，需要关注它的超时配置，以及 `onTimeout()`、`onError()` 和 `onCompletion()` 回调是否正常执行。

说话人 1：第二，检查 Spring WebFlux 或底层 HTTP 服务器的连接管理配置，确认没有设置过短的请求处理或连接超时。

说话人 1：第三，检查 Nginx、网关和负载均衡器的读取超时。比如，Nginx 的 `proxy_read_timeout` 如果小于实际连接空闲时间，就可能主动断开连接。

说话人 1：第四，检查心跳机制。如果模型长时间没有生成内容，可以定期发送 SSE 注释，让链路中间的代理知道连接仍然有数据活动。

说话人 1：第五，检查应用本身的资源限制。例如，连接数量是否超过服务器能够承受的范围，线程池是否耗尽，或者模型请求是否一直占用资源。

说话人 1：我还会检查连接断开时，模型订阅有没有取消，相关任务和会话资源是否释放。

说话人 1：不能只想着把超时时间调大。真正的问题有时候是模型任务卡死、连接没有心跳，或者服务端资源没有得到释放。

说话人 1：问题五十，如果客户端收到重复事件、事件顺序错乱或部分内容丢失，应该如何设计事件 ID、序列号、重连恢复和幂等处理？

说话人 1：答，这类问题要从事件唯一性、事件顺序和断线恢复三个方面解决。

说话人 1：首先，每个生成任务应该有独立的 `generationId`，每条事件都应该有自己的唯一事件 ID 或递增序列号。

说话人 1：例如，一个生成任务 G001 产生了 100 条事件，可以依次使用 1 到 100 的序号。客户端收到事件以后，记录最后处理的位置。

说话人 1：如果网络断开，浏览器通过 `Last-Event-ID` 告诉服务器最后处理到哪里。服务器再根据这个位置，从事件记录中读取尚未补发的内容。

说话人 1：其次，前端需要进行幂等处理。如果收到序号小于或者等于已经处理的位置，就可以根据业务规则识别重复事件，避免重复显示文本或重复执行状态更新。

说话人 1：最后，如果事件已经生成但连接中断，服务器必须有地方恢复这些事件。可以通过数据库、Redis Stream 或其他事件记录机制保存必要的数据。

说话人 1：需要强调的是，SSE 的事件 ID 和自动重连本身并不提供完整的可靠消息能力。没有持久化、事件补发和去重机制，就不能保证断线以后不丢数据。

说话人 1：对于普通模型文本输出，允许部分内容在断线后重新生成，可能已经足够；对于支付、订单和设备控制等重要业务，就必须采用更严格的事件持久化与业务幂等设计。

## 第七阶段：架构选型与综合面试

说话人 1：问题五十一，哪些业务适合使用同步响应，哪些业务适合使用 SSE？如何根据响应时间、交互体验、并发量和业务复杂度进行选型？

说话人 1：答，我会先看业务是否需要在处理过程中不断向客户端提供结果。

说话人 1：如果是普通的数据查询、用户登录、配置更新和简单 CRUD，使用同步响应通常更合适。因为这些接口业务处理时间较短，返回一个完整 JSON 就足够了。

说话人 1：如果是大模型聊天、长时间报告生成、实时任务进度和持续日志推送，SSE 通常更有价值，因为用户希望在整个任务完成之前就看到处理结果。

说话人 1：另外，还要看通信方向。如果只是服务器向客户端持续发送数据，SSE 通常够用；如果双方都需要高频主动发送消息，就要评估 WebSocket。

说话人 1：并发量也很重要。短时间的普通请求和几分钟的 SSE 长连接，对服务器资源的占用模式完全不同。

说话人 1：所以，我会综合考虑业务耗时、用户体验、连接数量、服务端线程模型和基础设施成本，而不是只要涉及大模型就一律使用 SSE。

说话人 1：问题五十二，如果一个 AI 聊天系统既需要普通完整响应接口，又需要实时流式输出接口，如何设计两个接口并复用底层业务服务？

说话人 1：答，最简单的方式就是把业务逻辑和 HTTP 响应方式分开，两个 Controller 接口共用底层 AI 聊天服务。

说话人 1：例如，可以设计：

```
POST /api/chat/completions
POST /api/chat/stream
```

说话人 1：第一个接口调用同步服务，返回完整的聊天结果；第二个接口调用流式服务，通过 SSE 返回模型生成的多个片段。

说话人 1：底层可以抽取统一的业务能力，例如用户身份校验、会话读取、Prompt 构建、知识库检索和模型调用配置。

说话人 1：但要注意，不要为了所谓代码复用，把流式结果强行转成完整字符串，最后再通过 SSE 发送。那样就失去了流式接口的意义。

说话人 1：比较合理的分层是：应用服务负责业务规则和会话处理，模型调用层分别提供同步与流式调用能力，Web 层负责把完整结果转换成 JSON，或者把流式片段转换成 SSE 事件。

说话人 1：这样，同一个聊天业务可以支持两种交互方式，而不必维护两套完全不同的业务逻辑。

说话人 1：问题五十三，假设你正在使用 JDK 21、Spring Boot 3.5.x 和 Spring AI 1.1.x 开发 AI 聊天系统，如何设计同步接口与 SSE 流式接口？如何处理 MVC/WebFlux 技术组合、请求取消、异常处理和会话记忆？

说话人 1：答，如果是我来做，我会优先考虑保留 Spring MVC 作为现有项目的 Web 服务端，再结合 Spring AI 1.1.x 的 Reactive 流式能力实现 SSE。

说话人 1：这里先明确技术基线。JDK 21 可以运行 Spring Boot 3.5.x；Spring AI 1.1.x 对应 Spring Boot 3.5.x 技术线。

说话人 1：在这个组合中，首先引入普通 Web Starter，提供 MVC Controller 和 Servlet 技术栈；然后根据 Spring AI 流式调用要求引入 Reactive 相关依赖。

说话人 1：例如：

```
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
</dependency>

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-webflux</artifactId>
</dependency>
```

说话人 1：这里虽然同时引入了 Web 和 WebFlux，但 Spring Boot 默认仍然选择 Spring MVC 作为服务端 Web 框架。Reactive 相关依赖主要用于 Spring AI 的流式调用以及其他响应式客户端能力。

说话人 1：接下来设计两个接口。

说话人 1：第一个是同步聊天接口，接收用户问题、会话 ID 和请求 ID，完成权限校验、历史读取、Prompt 组装、模型调用和消息保存，最终返回完整 JSON。

说话人 1：第二个是流式聊天接口，接收同样的业务参数，但是底层使用 `ChatClient.stream().content()` 获取 `Flux<String>`，再转换成 SSE 事件。

说话人 1：例如，流式接口可以返回：

```
@PostMapping(
    value = "/stream",
    produces = MediaType.TEXT_EVENT_STREAM_VALUE
)
public Flux<ServerSentEvent<String>> stream(
        @RequestBody ChatRequest request) {

    return chatClient.prompt()
            .user(request.message())
            .stream()
            .content()
            .map(text ->
                    ServerSentEvent.builder(text)
                            .event("token")
                            .build()
            );
}
```

说话人 1：这段代码仅用于说明调用关系。真正的业务接口还需要在调用前校验用户、会话归属、请求幂等，并结合记忆 Advisor 和异常处理进行扩展。

说话人 1：这里还有一个关键技术区别。如果返回 `Flux`，Spring MVC 可以将其适配为流式 HTTP 响应，但响应写入仍然可能使用阻塞线程；如果希望整个服务端基于非阻塞 I/O 运行，就需要真正采用 WebFlux 的响应式服务器架构，而不是只在 Controller 中返回 Flux。

说话人 1：接下来是会话记忆。可以使用 Spring AI 的 `ChatMemory` 和 `MessageChatMemoryAdvisor` 管理短期上下文，每次调用都传入 `ChatMemory.CONVERSATION_ID`，确保历史属于正确会话。

说话人 1：如果用户主动停止生成，就需要通过取消订阅尽量终止后续模型请求；如果模型调用异常，就根据连接是否已经提交响应，决定返回 HTTP 错误还是发送 SSE 错误事件。

说话人 1：如果要求完整保存聊天记录，则应该在请求执行前后维护消息状态，不能仅依赖流式片段自动落库。

说话人 1：最后，我会对这套技术组合做一次实际验证：确认项目启动时采用的 WebApplicationType、依赖树、ChatClient 的同步和流式调用、真实模型供应商的增量响应，以及经过代理之后的 SSE 输出行为。

说话人 1：问题五十四，如果用户反馈同步接口体验很慢，但 SSE 接口已经能够逐字输出，如何进一步优化首 Token 延迟、整体生成时间和服务器资源使用？

说话人 1：答，我会把优化分成三个目标：首 Token 延迟、整体生成耗时和服务器资源利用率。

说话人 1：首先是首 Token 延迟。可以分析模型调用前的准备时间，包括用户认证、会话记忆读取、RAG 检索、Prompt 组装和网络连接建立。

说话人 1：如果 RAG 每次检索需要 2 秒，就应该优化向量查询、索引或检索策略。如果数据库读取历史过慢，就应该优化存储访问和查询。

说话人 1：其次是整体生成时间。需要考虑模型本身的生成速度、输出 Token 数、模型供应商延迟以及工具调用耗时。对于不必要的长 Prompt 和冗余上下文，可以进行裁剪。

说话人 1：第三是服务器资源。要观察活跃 SSE 连接、请求线程、异步任务、Reactor 调度器、内存缓冲和模型并发量。

说话人 1：如果当前采用 Spring MVC，还要检查异步请求线程池和响应写入线程池是否存在资源瓶颈。如果采用 WebFlux，则需要检查事件循环线程有没有执行阻塞操作。

说话人 1：最后，我会建立一组指标：接口 TTFB、模型 TTFT、完整生成时间、平均输出 Token 数、每秒输出 Token 数、活跃连接数和错误率。

说话人 1：先用数据找到最慢的环节，再进行针对性优化。不能因为 SSE 已经逐字输出，就认为系统性能已经没有问题。

说话人 1：问题五十五，如果业务要求模型生成完成后必须保存完整对话记录，但又希望前端实时接收内容，应该如何协调流式发送、消息持久化和异常恢复？

说话人 1：答，这个场景非常典型，核心就是把前端实时推送和后端完整消息持久化分开处理，但要让它们保持同一个请求状态。

说话人 1：首先，用户提交问题后，系统先完成认证和会话校验，然后保存用户消息，创建一条状态为 `PENDING` 的请求记录。

说话人 1：接着启动模型流式调用。每当 `Flux<String>` 返回一个新的文本片段，服务端就立即通过 SSE 推送给前端，同时在应用侧收集这些片段，形成完整的助手回答。

说话人 1：这里不建议每收到一个 Token 就立即写一次数据库，因为会造成大量细碎的数据库操作。可以先在内存或受控缓冲区中收集，必要时定期进行检查点保存。

说话人 1：模型正常结束后，系统将完整助手回答保存到数据库，再把请求状态更新为 `SUCCEEDED`。

说话人 1：如果模型执行失败，就应该保存已经产生的部分内容，记录失败原因，并将状态更新为 `FAILED` 或 `PARTIAL`。

说话人 1：如果用户主动停止生成，则应当记录取消状态，例如 `CANCELLED`，并根据业务规则决定是否保存已经生成的部分答案。

说话人 1：还有一个重要问题：如果模型已经生成完整回答，但是数据库写入失败，系统不能直接重新调用模型。应该根据原来的 `requestId` 执行持久化重试或补偿，避免生成重复回答。

说话人 1：如果业务要求即使应用进程突然崩溃，也能恢复已经产生的内容，那么还需要更可靠的任务记录或增量检查点机制，不能只把所有片段放在 JVM 内存中。

说话人 1：所以，我会把整个流程设计成：接收请求、保存用户消息、创建任务、流式推送、收集模型输出、持久化助手消息、更新请求状态。

说话人 1：这样既能让前端实时看到回答，又能保证后端拥有完整的聊天记录，并且发生异常时可以根据请求状态进行恢复。

说话人 1：问题五十六，请从 HTTP 通信机制、Java 线程模型、Spring MVC/WebFlux、Spring AI `call()` / `stream()`、前后端数据传输和生产环境部署几个层面，完整讲解同步响应与 SSE 的区别，并说明企业级 AI 聊天系统应该如何选型？

说话人 1：答，如果从整个系统的角度来看，我会把它分成六个层面。

说话人 1：第一，HTTP 通信层。传统完整响应通常返回完整 JSON；SSE 则使用 `text/event-stream`，通过一个持续打开的 HTTP 响应向客户端发送多个事件。

说话人 1：第二，数据交付方式。同步响应强调等待完整结果，流式响应允许客户端逐步接收数据。两者描述的是数据返回方式，不是底层线程模型。

说话人 1：第三，Java 服务端执行模型。Spring MVC 基于 Servlet，支持通过 `SseEmitter` 和响应式返回类型实现异步及流式响应；Spring WebFlux 则基于 Reactor，提供非阻塞 I/O 和背压支持。

说话人 1：第四，Spring AI 模型调用。`call().content()` 返回完整字符串，适合非流式调用；`stream().content()` 返回 `Flux<String>`，可以逐步消费模型生成的内容。需要注意，Spring AI 1.1.x 对 Servlet 和 Reactive 技术栈有明确的组合要求。

说话人 1：第五，前后端交互。前端可以使用 `EventSource` 监听事件，也可以使用 Fetch 读取 POST 请求返回的流。服务端需要设计事件类型、ID、完成和错误信号，并处理请求取消、连接恢复和多用户隔离。

说话人 1：第六，生产环境部署。需要检查 Nginx 和网关缓冲、连接超时、心跳、并发限制、资源释放、鉴权和日志监控，不能只保证本地 Controller 能运行。

说话人 1：如果是我负责企业 AI 聊天项目，我会保留普通同步接口，用于用户查询、简单问答以及需要一次性获得完整结果的业务；同时提供 SSE 流式接口，用于长时间模型生成和需要实时反馈的聊天场景。

说话人 1：在技术实现上，如果项目采用 JDK 21、Spring Boot 3.5.x 和 Spring AI 1.1.x，并且已有 Spring MVC 架构，我会优先考虑保留 MVC 服务端，引入必要的 Reactive 能力支持 Spring AI 流式调用，再根据并发量和业务复杂度决定使用 `Flux` 适配响应，还是使用 `SseEmitter`。

说话人 1：如果未来 SSE 连接规模非常大，且上下游都能够采用非阻塞技术栈，再进一步评估完整 WebFlux 架构。

说话人 1：最后，无论采用哪种方案，都不能忽略会话记忆、请求幂等、完整消息持久化、异常恢复和数据安全。

说话人 1：总结一下：同步响应解决完整结果交付，流式响应解决逐步交付，SSE 解决 HTTP 实时事件传输，MVC/WebFlux 决定服务端如何处理请求与 I/O，Spring AI 则负责模型的同步或流式调用。

说话人 1：真正的企业级 AI 聊天系统，不是简单地把 `.call()` 改成 `.stream()`，而是要让模型生成、后端传输、前端消费、消息持久化和异常恢复形成一条完整、可靠的链路。

## 本次主题总结：面试必须掌握的八个核心结论

说话人 1：第一，同步响应和流式响应的区别是数据交付方式。前者通常等待完整结果，后者允许逐步返回。

说话人 1：第二，SSE 是基于 HTTP 的服务器单向事件推送机制，使用 `text/event-stream`，不是独立于 HTTP 的通信协议。

说话人 1：第三，SSE 不等于异步，也不等于非阻塞。使用 `SseEmitter` 并不能让底层阻塞模型调用自动变成非阻塞。

说话人 1：第四，Spring MVC 使用 `SseEmitter` 或支持流式的响应式返回类型实现 SSE；Spring WebFlux 可以直接使用 `Flux<ServerSentEvent<?>>`。

说话人 1：第五，Spring AI 的 `call()` 对应完整结果调用，`stream()` 对应流式调用。`Flux<String>` 是模型数据流，不是 SSE 本身。

说话人 1：第六，Spring AI 1.1.x 对 Servlet 和 Reactive 技术栈有特定组合要求。Spring Boot 同时引入 MVC 和 WebFlux Starter 时，默认仍选择 MVC，需要实际检查应用启动类型。

说话人 1：第七，企业级 SSE 必须处理连接断开、请求取消、重复事件、异常通知、心跳、Nginx 缓冲、超时和多用户隔离。

说话人 1：第八，流式推送与完整消息持久化可以同时实现，但必须明确请求状态、消息保存时机和失败恢复策略。

说话人 1：如果面试官问我，同步响应与 SSE 最本质的区别是什么，我会这样回答：

说话人 1：同步响应通常是等服务端完成整个业务处理，再把完整结果返回给客户端；SSE 则是基于 HTTP 长连接，让服务器在业务执行过程中持续推送多个事件。

说话人 1：在大模型场景中，Spring AI 的 `stream()` 可以逐步产生模型内容，后端再将其转换为 SSE，前端就能够实时展示生成结果。

说话人 1：但是，SSE 只解决数据实时交付，不自动解决线程阻塞、模型生成速度、并发控制和消息持久化。真正上线时，还必须结合 Spring MVC 或 WebFlux 的执行模型、代理配置、请求取消和可靠性机制进行完整设计。

说话人 1：至此，《同步响应与 SSE 的区别》五十六道关键问题全部讲解完毕。
