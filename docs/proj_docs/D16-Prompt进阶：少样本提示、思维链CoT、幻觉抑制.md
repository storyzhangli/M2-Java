## 2. Prompt 进阶技术总览

基础 Prompt 解决“有没有指令”的问题，进阶技术解决“指令准不准、结果稳不稳、事实真不真”的问题。各类技术分层互补，没有单一方案可以覆盖所有场景。

### 2.1 核心技术对比

| 技术                          | 核心作用                 | 解决的核心问题                           | 实现成本       | 效果确定性               |
| ----------------------------- | ------------------------ | ---------------------------------------- | -------------- | ------------------------ |
| Zero-shot 零样本              | 直接下达指令             | 简单通用任务                             | 极低           | 低，波动大               |
| Few-shot 少样本               | 通过示例对齐规则         | 格式不统一、分类边界模糊、异常处理不一致 | 低             | 中等，依赖示例质量       |
| Chain-of-Thought (CoT) 思维链 | 引导输出中间推理步骤     | 多步推理任务跳步出错                     | 中高           | 中等，仍可能推理错误     |
| Self-Consistency 自一致性     | 多路径投票聚合结果       | 单条推理的偶然误差                       | 高（成倍增长） | 中高，仍存在系统性偏差   |
| Hallucination 幻觉            | 模型生成自信但错误的内容 | 内生风险，需抑制                         | -              | 无法根除，只能降低概率   |
| Grounding 基于证据生成        | 将回答锚定在给定资料上   | 无依据的事实编造                         | 中             | 中高，依赖资料质量       |
| RAG 检索增强生成              | 外部检索资料作为证据     | 模型知识不足、过时                       | 高             | 中高，依赖检索质量       |
| 结构化输出+程序校验           | 代码侧规则兜底           | 格式错误、业务逻辑违规                   | 低             | 极高，仅能校验格式与规则 |

### 2.2 技术协同逻辑

从指令对齐到最终兜底，形成分层防御体系：

1. **Few-shot**：对齐任务规则、输出格式、异常处理标准
2. **分步指令/CoT**：拆解复杂任务，设置检查点，减少跳步错误
3. **Grounding/RAG**：锚定事实依据，降低无依据编造
4. **结构化输出**：统一返回格式，便于程序处理
5. **程序化校验**：最终兜底，拦截格式与业务规则违规
6. **人工复核**：高风险场景的最终保障

## 3. Few-shot 原理、设计与实践

Few-shot Prompting（少样本提示）属于上下文学习（In-Context Learning）范畴，通过在 Prompt 中提供少量输入-输出示例，让模型在不修改权重的情况下对齐任务规则。

### 3.1 Zero-shot / One-shot / Few-shot 的区别

- **Zero-shot**：无示例，仅靠指令描述任务。适合简单、容错高、格式无严格要求的场景，成本最低，效果最不稳定。
- **One-shot**：提供 1 个完整示例。适合格式单一、规则简单的任务，效果优于零样本。
- **Few-shot**：提供多个覆盖不同场景的示例。适合分类边界模糊、有异常分支、格式复杂的任务，是工程中最常用的方案。

>
> 本质：示例不是让模型“学会新知识”，而是引导模型激活训练数据中对应的任务模式，在上下文内完成格式与规则的对齐。

### 3.2 Few-shot 与微调、预训练的区别

| 维度     | Few-shot           | 微调 Fine-tuning       | 预训练       |
| -------- | ------------------ | ---------------------- | ------------ |
| 生效范围 | 单次对话上下文     | 持久化修改模型权重     | 模型基础能力 |
| 数据量   | 几条到几十条       | 几百到几万条           | 万亿级 Token |
| 成本     | 仅 Token 消耗      | 训练算力成本高         | 极高         |
| 修改难度 | 随时修改 Prompt    | 需重新训练             | 几乎不可修改 |
| 适用场景 | 规则对齐、格式约束 | 领域深度适配、风格固化 | 基础能力建设 |

### 3.3 示例设计的关键要素

1. **代表性**：覆盖任务主流场景，避免极端特例主导规则
2. **多样性**：必须包含**正常样例、边界样例、异常/信息不足样例**三类
3. **标签准确性**：示例的输出必须 100% 正确，错误示例会直接污染输出结果
4. **顺序效应**：示例排列顺序会影响结果，通常正例在前、边界/异常例在后
5. **数量**：并非越多越好。通常 3~8 个高质量示例收益最高；过多示例会稀释核心指令、占用上下文、提升成本，且边际收益递减。

### 3.4 三类示例的设计目的

- **正例**：示范标准场景下的正确输出，明确核心规则与格式
- **边界例**：示范临界值、模糊场景的判定标准，划清分类边界
- **异常例**：示范信息不足、输入非法时的拒答/兜底规则，避免模型强行回答

### 3.5 常见失效场景

1. **示例冲突**：多个示例规则不一致，模型输出混乱
2. **错误示例**：示例本身标注错误，模型直接模仿错误结果
3. **示例混淆**：模型把示例中的业务数据当成当前输入的内容，张冠李戴
4. **上下文过载**：示例过多导致核心指令被稀释，或超出上下文窗口
5. **能力边界外**：任务本质是模型知识缺失，再多示例也无法弥补

### 3.6 工程最佳实践

- 用明确的标签（如 `<example>`、分隔线）划分**示例区**与**当前输入区**
- 示例中的业务数据使用占位符，避免真实数据造成混淆
- 示例结束后重申核心规则，强化指令权重
- 当问题本质是知识缺失、需要精确计算时，不要靠堆示例解决，应引入工具调用或程序逻辑

### 3.7 完整示例：工单分类场景

#### Zero-shot 版本（效果不稳定）

```
请对以下故障工单进行分类，可选分类：机械、电气、热控、软件、未知。
工单：设备运行20分钟后异常振动，面板提示温度偏高。
```

#### Few-shot 版本（含三类示例）

```
【任务】对设备故障工单进行分类，并提取事实、标注缺失信息。
【分类枚举】MECHANICAL机械 / ELECTRICAL电气 / THERMAL热控 / SOFTWARE软件 / UNKNOWN未知
【规则】信息不足以判断时必须返回UNKNOWN，不得强行分类。

--- 示例开始 ---
【示例1：正常输入】
输入：设备EQ-001，电机异响，转速下降，轴承温度85℃
输出：
分类：MECHANICAL
事实：["设备编号EQ-001", "电机异响", "转速下降", "轴承温度85℃"]
缺失信息：[]

【示例2：边界场景】
输入：设备EQ-002，温度报警，伴随接线处焦糊味
输出：
分类：ELECTRICAL
事实：["设备编号EQ-002", "温度报警", "接线处焦糊味"]
缺失信息：["实测温度值", "报警代码"]

【示例3：信息不足】
输入：设备EQ-003坏了，开不了机
输出：
分类：UNKNOWN
事实：["设备编号EQ-003", "无法开机"]
缺失信息：["故障现象细节", "报警代码", "供电状态"]
--- 示例结束 ---

【当前待处理工单】
{工单内容}
```

## 4. CoT、分步指令与适用边界

### 4.1 CoT 的定义与研究背景

Chain-of-Thought（思维链）指引导模型输出中间推理步骤，而非直接给出最终答案，以此提升复杂推理任务的准确率。该方法由 Google Brain 于 2022 年正式提出，在算术、常识、符号推理任务上效果显著。

>
> 引用：Chain-of-Thought Prompting Elicits Reasoning in Large Language Models | 思维链提示激发大语言模型的推理能力：[](https://arxiv.org/abs/2201.11903)[https://arxiv.org/abs/2201.11903](https://arxiv.org/abs/2201.11903)

### 4.2 Zero-shot CoT 与 Few-shot CoT

- **Zero-shot CoT**：仅追加一句引导语（如“请一步步思考并说明理由”），无需示例。成本低、通用，但效果不稳定。
- **Few-shot CoT**：在示例中同时给出推理过程和最终答案。效果更可控，适合特定领域的推理任务。

### 4.3 CoT 为什么能提升效果

1. 模型是逐 Token 生成的，复杂任务直接输出最终答案容易跳步出错；中间推理文本相当于为后续生成铺垫上下文
2. 将复杂任务拆解为多个简单子问题，每个子问题的生成准确率更高
3. 本质是引导模型激活训练数据中的推理模式，并非真的产生了“思考”

### 4.4 关键概念辨析

#### CoT vs 普通分步指令

- 普通分步指令：规定处理的流程顺序，是**流程约束**，不要求输出内部理由，工程可控性更强
- CoT：要求输出推理过程，是**思考过程显式化**，便于排查错误，但不可控因素更多
- 工程优先选择：能用普通分步指令解决的，不用 CoT；仅在复杂判断环节使用 CoT 辅助

#### CoT vs 程序化多阶段调用

- 程序化多阶段：每个步骤由代码控制，中间结果可校验、可中断、可替换工具，100% 可控
- CoT：所有步骤在模型内部完成，中间结果无法编程校验，错误会沿链路传播

#### CoT vs 工具辅助验证

- 工具辅助：计算、查询、逻辑判断交给确定性工具执行，结果 100% 准确
- CoT：模型“自行推导”，结果不可靠，仅适合初步分析

### 4.5 CoT 的局限性与风险

1. **Token 成本高**：推理过程占用大量 Token，输入输出成本成倍增加
2. **延迟高**：生成更多内容，响应时间显著变长
3. **错误传播**：中间某一步出错，后续所有推导都会基于错误前提
4. **合理化陷阱**：模型可能先得出结论，再反向编造看似合理的推理过程；推理不是答案的原因，而是答案的“辩护”
5. **过程≠真实计算**：展示的推理文本不等于模型内部真实的计算路径，只是生成的文本而已
6. **篇幅≠正确性**：推理越长、越详细，不代表答案越正确；冗长的推理可能只是在放大错误

### 4.6 适用与不适用场景

- ✅ 适合：多条件分类、故障初步排查、复杂逻辑拆解、方案思路梳理
- ❌ 不适合：精确数值计算、法定规则判定、数据查询、高风险结论输出——这些应交给程序或工具

### 4.7 Self-Consistency 自一致性

- **基本思路**：对同一个问题生成多条独立的推理路径与答案，通过投票聚合选择出现次数最多的结果，降低单路径的偶然误差
- **适用条件**：答案为离散分类、短文本、可聚合的场景；对准确率要求极高、可接受更高成本的场景
- **额外成本**：生成 N 个候选，Token 成本与延迟均为原来的 N 倍
- **局限性**：如果模型对该问题存在系统性偏差，多个候选可能犯同样的错误，“多数一致”仍然是错误答案

>
> 说明：对应 Google Research 参考页面解析异常，以上结论基于公开研究共识，原文链接供自行查阅：Self-Consistency Improves Chain of Thought Reasoning in Language Models | 自一致性提升语言模型的思维链推理能力：[](https://research.google/pubs/self-consistency-improves-chain-of-thought-reasoning-in-language-models/)[https://research.google/pubs/self-consistency-improves-chain-of-thought-reasoning-in-language-models/](https://research.google/pubs/self-consistency-improves-chain-of-thought-reasoning-in-language-models/)

### 4.8 工程实践原则

优先使用**可验证的分步流程**，关键节点设置检查点，最终输出做业务校验；不要把冗长的推理文本作为验收标准，只以最终结果的正确性和可验证性为准。

## 5. 幻觉类型、成因及分层抑制策略

### 5.1 幻觉的定义

幻觉（Confabulation，又称虚构）指生成式 AI 系统输出表述自信，但内容错误、无依据或与事实不符的现象。这是大模型基于统计概率生成文本的内生特性，并非模型“故意撒谎”。

>
> 引用：Artificial Intelligence Risk Management Framework: Generative Artificial Intelligence Profile | 人工智能风险管理框架：生成式人工智能概况：[](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)[https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)

>
> 核心认知：幻觉无法 100% 消除，只能通过分层策略降低发生概率和影响范围；任何声称“零幻觉”的方案都是不严谨的。

### 5.2 常见幻觉类型

1. **事实幻觉**：编造不存在的事件、规则、知识、人物
2. **引用幻觉**：编造不存在的论文、法规、URL、API 文档、官方说明
3. **数字与计算幻觉**：给出错误的数值、计算结果，且看起来非常精确
4. **代码/API 幻觉**：编造不存在的类、方法、参数、配置项，声称是官方 API
5. **上下文误读**：曲解输入内容，无中生有地解读出输入中没有的含义
6. **过度确定性**：对不确定的信息以 100% 肯定的语气输出，不标注不确定性

### 5.3 幻觉的主要成因

1. **输入缺失**：问题缺少必要信息，模型强行补全
2. **错误前提**：用户输入了错误假设，模型顺着错误前提继续生成
3. **知识限制**：训练数据中没有相关信息，或信息过时、错误
4. **上下文冲突**：上下文中存在矛盾信息，模型混淆处理
5. **错误检索**：RAG 场景下检索到错误、不相关、过时的资料
6. **错误推断**：基于正确前提做出错误的逻辑推导
7. **指令诱导**：Prompt 暗示了某种结论，模型顺着指令生成符合预期但不符合事实的内容

### 5.4 为什么“禁止幻觉”的指令无效

模型没有独立的“真假判断”机制，它始终选择概率最高的下一个 Token。“不要幻觉”的指令只能在一定程度上调整生成概率分布，无法从根本上改变生成机制；对于模型不知道的内容，它不会天然地“说不知道”。

### 5.5 幻觉抑制分层策略

#### 第一层：Prompt 层（第一道防线）

**解决问题**：从生成概率上降低无依据编造的比例
**常用手段**：

- 明确回答范围：限定只能使用给定资料，超出范围必须说明未知
- 强制分级输出：要求明确区分【明确事实】【合理推断】【无法确认】三个等级
- 拒答规则：信息不足时，直接列出缺失项，禁止强行回答
- 举证要求：关键结论必须标注依据来源，无依据不得下结论
- 明确禁令：禁止编造数据、引用、URL、API 名称
**剩余风险**：仅能降低概率，无法杜绝模型违反指令

#### 第二层：证据层（Grounding，第二道防线）

**解决问题**：将回答锚定在给定的可信资料上
**核心机制**：

- 建立“主张 → 对应证据原文 → 判断状态”的三元对应关系
- 证据分级：直接证据（原文明确陈述）、间接依据（原文可推导）、合理推断（基于常识）、无依据
**注意事项**：来源真实 ≠ 来源支持结论；必须核对证据与主张的对应关系，不能“有资料就认为结论正确”
**剩余风险**：资料本身可能错误；模型可能断章取义曲解资料

#### 第三层：检索与工具层（工程化证据）

**解决问题**：弥补模型知识不足，提供真实、实时的数据
**常用方案**：

- RAG：从外部向量库、数据库检索领域资料，作为 Grounding 的证据来源
- 工具调用：精确计算、数据查询、实时信息获取交给确定性工具（Java 代码、数据库、API）
  **选型边界**：
  - 精确计算、数据查询：用 Java 代码/数据库，不要让模型算
  - 实时业务数据：用 API/工具调用，不要靠模型记忆
  - 领域文档知识：用 RAG 检索，不要靠模型记忆
  **剩余风险**：检索不准、资料过时、工具返回错误数据

#### 第四层：输出与程序校验层（兜底防线）

**解决问题**：拦截格式错误、规则违规的输出
**常用手段**：

- 结构化输出：约定输出字段，每个事实带置信度、证据标识、状态字段
- 格式校验：Jackson 解析 JSON，校验字段存在性、类型、枚举值
- 业务规则校验：Java 代码校验数值范围、状态流转、逻辑一致性
- 引用校验：对输出的 URL、文档编号、API 名称做白名单校验
**核心认知**：JSON 合法 ≠ 内容正确；程序只能校验格式和规则，不能校验事实真伪；模型自我检查不能代替外部验证

#### 第五层：评估层（持续优化）

**解决问题**：持续监控幻觉率，闭环优化
**常用手段**：

- 建立基准测试集：覆盖常见、边界、易错问题
- 核心指标：事实准确率、证据支持率、无依据主张率、正确拒答率、幻觉率
- 人工抽检：高风险场景必须有人工复核
- Badcase 闭环：收集幻觉案例，优化 Prompt、补充证据、增加校验规则
**剩余风险**：只能覆盖已知场景，无法预见所有新型幻觉

## 6. 三种技术的组合应用

### 6.1 协同逻辑

| 技术          | 解决的问题                       | 在组合中的定位 |
| ------------- | -------------------------------- | -------------- |
| Few-shot      | 对齐任务规则、输出格式、异常处理 | 行为标准示范   |
| 分步指令/CoT  | 拆解复杂任务，减少跳步错误       | 处理流程约束   |
| 幻觉抑制规则  | 强制区分事实/推断/未知，禁止编造 | 事实边界约束   |
| Grounding/RAG | 提供真实可查的证据               | 事实依据来源   |
| 结构化输出    | 统一返回格式                     | 程序处理基础   |
| 程序化校验    | 拦截格式与逻辑违规               | 最终兜底       |

### 6.2 组合式 Prompt 标准结构

```
【System Message 固定部分】
1. 角色与职责范围
2. 核心工作规则（含幻觉抑制要求）
3. 输出结构与字段定义
4. 3~5 个覆盖多场景的 Few-shot 示例

【User Message 动态部分】
1. 当前待处理的输入数据
2. 本次临时补充的上下文/资料
3. 分步执行指令与检查点
```

>
> 关键原则：模型生成的推理文本是过程产物，不是证据；所有事实性结论必须有外部资料或工具结果支撑。

### 6.3 组合效果边界

- 组合使用可以显著提升输出的稳定性、格式合规率和事实准确率
- 依然无法 100% 避免幻觉，高风险场景必须人工复核
- 当错误根源是知识缺失时，优化 Prompt 的收益很低，必须补充外部证据或工具

## 7. Spring AI Java 示例

>
> 说明：以下代码基于 Spring AI 1.1.x API 编写，为示例实现，未在真实环境编译运行，仅供参考接口用法。

### 7.1 定义结构化返回实体（JDK 21 Record）

```
/**
 * 设备故障工单分析结果
 */
public record WorkOrderAnalysis(
    // 明确提取到的客观事实
    List<String> confirmedFacts,
    // 基于事实的合理推断
    List<String> reasonableInferences,
    // 缺失的关键信息
    List<String> missingInfo,
    // 故障分类
    FaultCategory faultCategory,
    // 置信度 0-1
    Double confidence,
    // 处理建议
    String suggestion
) {
    /**
     * 故障分类枚举
     */
    public enum FaultCategory {
        MECHANICAL, ELECTRICAL, THERMAL, SOFTWARE, UNKNOWN
    }
}
```

### 7.2 业务服务实现

```java
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.ai.chat.client.advisor.SimpleLoggerAdvisor;
import org.springframework.stereotype.Service;
import java.util.List;

@Service
public class FaultAnalysisService {

    private final ChatClient chatClient;

    /**
     * 注入自动配置的 ChatClient.Builder
     * 系统提示词（含规则 + Few-shot 示例）全局生效
     */
    public FaultAnalysisService(ChatClient.Builder chatClientBuilder) {
        this.chatClient = chatClientBuilder
                .defaultSystem(buildSystemPrompt())
                .defaultAdvisors(new SimpleLoggerAdvisor())
                .build();
    }

    /**
     * 构建系统提示词：规则 + 三类 Few-shot 示例
     */
    private String buildSystemPrompt() {
        return """
            【角色】制造业设备故障预处理工程师，严格基于给定信息判断，禁止臆造。
            
            【核心规则】
            1. 仅基于用户提供的故障描述分析，不得引入外部设备知识
            2. 严格区分：明确事实、合理推断、缺失信息三类
            3. 信息不足以分类时，faultCategory 必须为 UNKNOWN
            4. 所有推断必须标注依据，无依据内容不得输出
            
            【输出规范】
            严格按指定 JSON 结构输出，不得添加额外解释文字。
            
            【示例1：正常输入】
            输入：设备EQ-001，电机异响，转速下降，轴承温度85℃
            输出：
            {
              "confirmedFacts": ["设备编号EQ-001", "电机异响", "转速下降", "轴承温度85℃"],
              "reasonableInferences": ["大概率为轴承磨损导致的机械故障"],
              "missingInfo": [],
              "faultCategory": "MECHANICAL",
              "confidence": 0.85,
              "suggestion": "检查轴承磨损情况，更换润滑脂"
            }
            
            【示例2：信息不足】
            输入：设备EQ-002报警，无法启动
            输出：
            {
              "confirmedFacts": ["设备编号EQ-002", "设备报警", "无法启动"],
              "reasonableInferences": [],
              "missingInfo": ["报警代码", "报警时间", "供电状态"],
              "faultCategory": "UNKNOWN",
              "confidence": 0.2,
              "suggestion": "请补充报警代码与供电检查结果"
            }
            
            【示例3：用户臆测原因】
            输入：应该是主板坏了，设备EQ-003开机没反应，指示灯不亮
            输出：
            {
              "confirmedFacts": ["设备编号EQ-003", "开机无反应", "指示灯不亮"],
              "reasonableInferences": ["供电故障或主板故障均有可能，用户陈述的主板损坏未证实"],
              "missingInfo": ["供电电压检测结果", "主板指示灯状态"],
              "faultCategory": "UNKNOWN",
              "confidence": 0.3,
              "suggestion": "先检测输入电源是否正常，再排查主板"
            }
            """;
    }

    /**
     * 分析故障工单
     * @param faultDesc 故障描述文本
     * @return 结构化分析结果
     */
    public WorkOrderAnalysis analyze(String faultDesc) {
        // 调用 ChatClient，自动解析为 Java Record
        WorkOrderAnalysis result = chatClient.prompt()
                .user(faultDesc)
                .call()
                .entity(WorkOrderAnalysis.class);

        // 程序化兜底校验
        validateResult(result);

        return result;
    }

    /**
     * 业务规则校验：拦截不符合规则的输出
     */
    private void validateResult(WorkOrderAnalysis result) {
        // 1. 枚举非空校验
        if (result.faultCategory() == null) {
            throw new IllegalArgumentException("故障分类不能为空");
        }

        // 2. 置信度范围校验
        if (result.confidence() < 0 || result.confidence() > 1) {
            throw new IllegalArgumentException("置信度必须在 0-1 之间");
        }

        // 3. 业务规则：存在缺失信息时，置信度不得高于 0.5
        if (!result.missingInfo().isEmpty()
                && result.faultCategory() != WorkOrderAnalysis.FaultCategory.UNKNOWN
                && result.confidence() > 0.5) {
            throw new IllegalArgumentException("存在缺失信息时置信度过高，需人工复核");
        }

        // 4. 事实非空校验
        if (result.confirmedFacts() == null || result.confirmedFacts().isEmpty()) {
            throw new IllegalArgumentException("必须提取至少一条明确事实");
        }
    }
}
```

### 7.3 代码说明

1. **System Message** 存放固定规则与 Few-shot 示例，全局生效；动态输入通过 User Message 传入
2. `.entity()` 方法自动将模型输出解析为 Java Record，底层基于 `BeanOutputConverter`
3. `validateResult` 是程序化兜底，即使模型输出格式正确，也要经过业务规则校验
4. 生产环境可通过 `AdvisorParams.ENABLE_NATIVE_STRUCTURED_OUTPUT` 开启模型原生结构化输出，进一步提升格式准确率
5. API 参考：Chat Client API | Spring AI 聊天客户端 API：[](https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html)[https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html](https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html)

## 8. 制造业设备故障综合案例

### 8.1 案例背景

制造业设备故障工单自动预处理系统：从用户提交的故障描述中提取事实、标注缺失信息、完成初步分类，辅助工程师高效处理，**不替代专业诊断**。

### 8.2 输入示例

>
> 设备编号：EQ-1008。
> 故障描述：设备运行约 20 分钟后出现异常振动，随后控制面板提示温度偏高，但未提供温度实测值、报警代码或维修记录。

### 8.3 处理要求

1. 提取明确事实
2. 区分事实与推测
3. 标明缺失信息
4. 按枚举规则初步分类
5. 证据不足时返回未知
6. 结构化输出
7. 程序侧业务校验

### 8.4 预期输出示例

```
{
  "confirmedFacts": [
    "设备编号EQ-1008",
    "设备运行约20分钟后出现异常振动",
    "控制面板提示温度偏高"
  ],
  "reasonableInferences": [
    "振动与温度升高可能存在关联，需实测温度确认严重程度"
  ],
  "missingInfo": [
    "温度实测值",
    "报警代码",
    "设备维修记录",
    "振动幅度具体数值"
  ],
  "faultCategory": "UNKNOWN",
  "confidence": 0.35,
  "suggestion": "请补充温度实测值与报警代码，安排现场检查振动源"
}
```

### 8.5 三个 Few-shot 示例的设计目的

1. **正常输入示例**：示范完整信息下的标准分类流程，对齐输出格式
2. **信息不足示例**：示范缺失信息时的拒答规则，强制输出 UNKNOWN 与缺失清单
3. **用户臆测示例**：示范如何忽略用户未证实的主观判断，只基于客观描述分析

### 8.6 工程边界

本系统仅做预处理辅助，最终诊断必须由专业工程师确认；不得直接用于自动维修、自动停机等高风险操作。

## 10. 常见问题诊断

采用「现象 → 可能原因 → 核查证据 → 解决方向」结构：

1. **现象**：增加示例后，结果反而变差
   - 可能原因：示例规则冲突；示例顺序偏差；新增示例质量差；示例过多稀释核心指令
   - 核查证据：对比示例规则是否一致；调换示例顺序观察结果变化；检查示例标注准确性
   - 解决方向：删除冲突示例；统一输出标准；保留 3~5 个高质量示例；核心指令放首尾强化
2. **现象**：模型总是复制示例数据到当前结果中
   - 可能原因：示例与输入边界不清晰；示例使用了真实业务数据
   - 核查证据：检查是否有明确的示例区标记；示例数据是否为占位符
   - 解决方向：用标签/分隔线划分示例区与输入区；示例使用占位符；示例结束后重申“以上为示例，以下为当前输入”
3. **现象**：示例标签或规则互相矛盾
   - 可能原因：示例由多人编写，没有统一标注规范
   - 核查证据：逐条对比示例的输出规则，找出不一致条目
   - 解决方向：制定统一标注规范；按标准重写示例；删除矛盾示例
4. **现象**：CoT 输出很长、推理看似合理，但最终答案错误
   - 可能原因：中间某一步前提错误，后续全错；模型先定结论再反向编造推理；问题涉及模型没有的知识
   - 核查证据：逐行核对推理步骤的事实依据；对比外部真实数据
   - 解决方向：关键步骤增加证据校验；高风险结论引入工具验证；只看最终结论是否有实锤，不信推理过程
5. **现象**：模型生成了详细理由，却没有支持结论的证据
   - 可能原因：指令未强制举证；模型将推断当成事实
   - 核查证据：检查 Prompt 是否要求标注证据来源；是否区分事实与推断
   - 解决方向：强制要求“每个结论标注对应原文依据”；输出结构增加 evidence 字段；程序侧校验关键结论必须有对应证据
6. **现象**：资料明显缺失时，模型仍给出确定答案
   - 可能原因：无明确拒答规则；缺少信息不足的示例；模型倾向于“满足用户”而强行回答
   - 核查证据：检查是否有信息不足的处理规则；是否有对应 Few-shot 示例
   - 解决方向：明确写入“信息不足必须返回 UNKNOWN”；增加异常示例；程序侧校验：缺失信息超过阈值时强制置为未知
7. **现象**：模型虚构论文、引用、URL 或技术 API
   - 可能原因：无禁止编造引用的规则；内容超出模型知识范围
   - 核查证据：核对输出的 URL/API 是否真实存在
   - 解决方向：明确禁止编造引用；要求“无法确认直接说明未知”；程序侧增加白名单校验
8. **现象**：已检索到相关材料，回答仍不准确
   - 可能原因：材料本身错误/过时；模型断章取义；材料太多导致混淆
   - 核查证据：核对检索材料原文与回答是否一致；检查材料时效性
   - 解决方向：优化检索相关性；要求回答标注引用原文片段；限制材料数量避免过载；关键事实做原文匹配
9. **现象**：JSON 结构合法，业务内容却错误
   - 可能原因：结构化输出只能保证格式，不能保证内容正确
   - 核查证据：对比输入与输出的业务逻辑；核对事实依据
   - 解决方向：增加业务规则校验代码；关键字段做范围/枚举/逻辑校验；高风险字段引入人工复核
10. **现象**：增加示例、多次采样、多阶段调用后，成本上升但质量未改善
   - 可能原因：问题本质是模型知识不足/证据缺失，不是指令不清晰；已达到模型能力上限
   - 核查证据：判断错误类型是规则理解错误，还是事实知识缺失
   - 解决方向：停止堆 Prompt，转向补充外部证据/工具调用；评估模型是否满足任务要求，必要时升级模型

| Zero-shot | 基础指令           | 极低 | 低     | 简单通用问答         |

| CoT       | 推理增强           | 中高 | 中     | 复杂推理、初步排查   |
| Grounding | 事实锚定           | 中   | 中高   | 知识问答、资料总结   |
| RAG       | 外部知识补充       | 高   | 中高   | 领域知识库问答       |
| 程序校验  | 格式与规则兜底     | 低   | 极高   | 所有结构化输出场景   |
| 工具调用  | 确定性执行         | 中   | 极高   | 精确计算、数据获取   |
