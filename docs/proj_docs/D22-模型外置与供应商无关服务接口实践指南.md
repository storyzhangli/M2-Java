# D22 模型外置与供应商无关服务接口实践指南

> 适用模块：D22（`com.zl.d22`），Spring Boot 3.5.16 + Spring AI 1.1.8 + JDK 21
> 文档定位：技术说明与操作实践指南（双交付物之二）
> 视角：以"12 年 Java 架构 + 6 年 AI 工程落地"的经验，讲清**是什么、为什么、怎么落地、如何扩展、怎么避坑**

---

## 1. 核心概念：什么是"供应商无关"

### 1.1 定义

**供应商无关（Vendor-agnostic / Provider-agnostic）** 指：业务编排逻辑只依赖框架的**可移植抽象**
（Spring AI 的 `ChatModel`、`ChatOptions`、`Message`、`Usage` 等），而不直接依赖某一家模型供应商的
**专有类型**（如 `DeepSeekChatOptions`、`DeepSeekAssistantMessage`、`DeepSeekApi`）。

需要区分两个层次：

| 层次 | 是否允许 | 例子 |
| --- | --- | --- |
| 类型耦合（编译期 import 专有类） | 业务层禁止，仅适配层允许 | `import DeepSeekChatOptions` |
| 数据耦合（运行时字符串标签） | 允许 | 观测字段 `provider="deepseek"` |

关键认知：**配置里出现供应商名字（如默认 URL、观测标签）不等于类型耦合**。
真正要消除的是"换供应商必须改业务代码、改方法签名"的编译期依赖。

### 1.2 采用的架构模式：端口与适配器（Hexagonal / Ports & Adapters）

- **端口（Port）**：应用定义的中立接口，表达"我需要什么能力"。
- **适配器（Adapter）**：针对具体供应商的实现，把专有 SDK 翻译成端口契约。
- **依赖方向**：业务 → 端口 ← 适配器。专有类型只存在于适配器一侧，依赖箭头永远指向中立抽象。

D22 用包结构物理表达这一模式：

```text
adapter
├─ ChatModelPort        （端口：中立）
├─ NativeUsageReader    （端口 SPI：中立）
├─ NativeUsage          （中立数据载体）
└─ deepseek             （适配器：DeepSeek 专有实现）
```

## 2. 为什么这样设计：三个必须解决的底层问题

### 2.1 问题一：专有 Options/消息类型泄漏

**现象**：旧 `DeepSeekAiChatService` 的方法直接返回 `DeepSeekChatOptions`，
并 `instanceof DeepSeekAssistantMessage` 取推理内容。

**根因**：框架为每家供应商提供了专有 Options 子类与专有消息子类，
业务代码若直接使用它们，就与该供应商的 SDK 焊死。

**解法**：用 `ChatModelPort` 把这两个动作收口，业务层只看到可移植的 `ChatOptions`/`AssistantMessage`：

```java
public interface ChatModelPort {
    ChatOptions requestOptions(String model);
    String reasoningContent(AssistantMessage message);
}
```

### 2.2 问题二：可移植 Usage 的"null 被强制成 0"陷阱

这是 Spring AI 抽象层的一个真实坑，必须理解：

- `DefaultUsage` 会把 `null` 字段强制成 `0`；
- 默认 `getTotalTokens()` 会把 `null` 的 prompt/completion 当 `0` 相加。

后果：**无法区分"供应商没返回该字段"和"供应商真实返回了 0"**，观测数据失真。

而 DeepSeek 原生 `DeepSeekApi.Usage` 是一个保留 `null` 的 record，能真实判空。

**解法**：定义 `NativeUsageReader` SPI，让供应商在适配边界内读取自己的原生 record：

```java
public interface NativeUsageReader {
    boolean supports(Usage usage);
    NativeUsage read(Usage usage);
}
```

`DeepSeekNativeUsageReader` 实现：

```java
@Override
public boolean supports(Usage usage) {
    return usage != null && usage.getNativeUsage() instanceof DeepSeekApi.Usage;
}

@Override
public NativeUsage read(Usage usage) {
    DeepSeekApi.Usage nativeUsage = (DeepSeekApi.Usage) usage.getNativeUsage();
    return new NativeUsage(nativeUsage.promptTokens(),
            nativeUsage.completionTokens(), nativeUsage.totalTokens());
}
```

### 2.3 问题三：两套配置并存

**现象**：Spring AI 自动配置读 `spring.ai.deepseek.*`，而应用想用自己的 `app.ai.*`。

**解法**：启动类排除自动配置 + 适配层手动构造，保证**只有一个配置源**。

```java
@SpringBootApplication(exclude = DeepSeekChatAutoConfiguration.class)
```

## 3. 落地原理：手动装配 ChatModel 的完整链路

### 3.1 装配链路图

```mermaid
graph TD
    Props ["AiProperties app.ai"] --> ApiBuilder ["DeepSeekApi builder"]
    RestBuilder ["RestClient Builder 含超时"] --> ApiBuilder
    WebBuilder ["WebClient Builder 含超时"] --> ApiBuilder
    ApiBuilder --> Api ["DeepSeekApi 实例"]
    Props --> OptBuilder ["DeepSeekChatOptions builder model temperature"]
    OptBuilder --> DefaultOpt ["defaultOptions"]
    NoRetry ["RetryTemplate maxAttempts 1"] --> ModelBuilder ["DeepSeekChatModel builder"]
    Api --> ModelBuilder
    DefaultOpt --> ModelBuilder
    ObsRegistry ["ObservationRegistry"] --> ModelBuilder
    ModelBuilder --> ChatModelBean ["ChatModel Bean 可移植类型"]
```

### 3.2 关键代码与设计意图

```java
@Bean
public ChatModel chatModel(AiProperties aiProperties,
                           RestClient.Builder restClientBuilder,
                           WebClient.Builder webClientBuilder,
                           ObservationRegistry observationRegistry) {

    DeepSeekApi deepSeekApi = DeepSeekApi.builder()
            .baseUrl(aiProperties.getBaseUrl())
            .apiKey(aiProperties.getApiKey())
            .restClientBuilder(restClientBuilder)
            .webClientBuilder(webClientBuilder)
            .build();

    DeepSeekChatOptions defaultOptions = DeepSeekChatOptions.builder()
            .model(aiProperties.getModel())
            .temperature(BASELINE_TEMPERATURE)   // 0.7 保留基线
            .build();

    RetryTemplate noRetry = RetryTemplate.builder().maxAttempts(1).build();

    return DeepSeekChatModel.builder()
            .deepSeekApi(deepSeekApi)
            .defaultOptions(defaultOptions)
            .retryTemplate(noRetry)
            .observationRegistry(observationRegistry)
            .build();
}
```

设计意图逐条说明：

1. **返回类型声明为 `ChatModel` 而非 `DeepSeekChatModel`**：即使运行时是 DeepSeek 实现，
   注入方也只依赖可移植抽象，这是"面向接口"的具体落地。
2. **复用容器的 Builder**：`ModelClientConfiguration` 已把 JDK HttpClient 的连接/读取超时
   注入到 `RestClient.Builder/WebClient.Builder`，手动构造时直接注入即可复用，不重复造超时。
3. **`maxAttempts(1)` 关闭内置重试**：Spring AI 自带重试与应用层 `resilience` 会叠加，
   必须关掉前者，让重试只有一个责任层。
4. **`@ConditionalOnProperty` 条件装配**：仅 `app.ai.mode=deepseek` 时创建，
   Mock 模式不创建任何 `ChatModel`，避免无意义的 HTTP 客户端 Bean。

### 3.3 字节码签名核验方法（重要工程习惯）

对版本敏感的 API 调用，不要凭记忆或网络博客，应直接核验本地字节码：

```powershell
# PowerShell 中内部类名用单引号防止 $ 被展开
& "D:\SoftwareInstall\JDK\JDK21\bin\javap.exe" -p `
  -cp "<target\classes 或依赖 jar>" 'org.springframework.ai.deepseek.DeepSeekChatOptions$Builder'
```

D22 已通过 `javap` 核验的关键事实：

- `DeepSeekChatOptions.Builder` 有 `model(String)`、`temperature(Double)`、`build()`；
- `DeepSeekApi.Builder` 有 `baseUrl`、`apiKey(String)`、`restClientBuilder`、`webClientBuilder`；
- `DeepSeekChatModel.Builder` 有 `deepSeekApi/defaultOptions/retryTemplate/observationRegistry/build`；
- `DeepSeekApi.Usage` 是 record，构造参数顺序为 `(completion, prompt, total)`，accessor 为 `promptTokens()/completionTokens()/totalTokens()`。

## 4. 边界守卫：把架构约定变成可回归测试

### 4.1 为什么需要机器校验

"供应商类型不许出现在适配层之外"如果只靠 Code Review，会随时间腐化。
D22 用 `VendorBoundaryTest` 直接扫描 class 常量池，把约定固化为测试。

### 4.2 原理：class 文件常量池解析

class 文件头部结构：

```text
magic(4) + minor_version(2) + major_version(2) + constant_pool_count(2) + 常量池条目...
```

常量池条目按 tag 区分长度，其中 `CONSTANT_Utf8(tag=1)` 承载类名/字符串。
测试遍历所有 Utf8 条目，检查是否以 `org/springframework/ai/deepseek` 开头：

```java
if (referencesVendor(classFile) && !relative.startsWith("com/zl/d22/adapter/deepseek/")) {
    violations.add(relative);
}
assertThat(violations).isEmpty();
```

### 4.3 实践中的一个真实 Bug（值得复盘）

首次实现时，解析器在 `magic` + `minor_version` 后**漏读了 `major_version`（2 字节）**，
直接把 major version（值 65）误读成常量池数量，导致后续全部错位、读到 `tag=0`。

修复：在 minor 与读 count 之间补 `skip(2)`。

复盘要点：**手写二进制解析必须严格按规范逐字段对齐，任何一个字段漏读都会让后续全部错位；
出现 `tag=0` 这类非法值，首先怀疑读取位置已偏移，而不是文件损坏。**

### 4.4 为什么不会误报

- Javadoc 注释不进入字节码，仅文案含 deepseek 的类不会被标记；
- 普通字符串（如 `"deepseek"` 标签）不是类路径前缀 `org/springframework/ai/deepseek`，不匹配；
- 只有真正 `import` 并在常量池留下类引用才会触发。

## 5. 操作实践（How-to）

### 5.1 Mock 模式启动（默认，无需 Key）

```powershell
# 直接以默认 mock 启动
java -jar D22_EMN_URLs_Keys_schemas-1.0-SNAPSHOT.jar
# 或显式指定
$env:AI_MODE="mock"
java -jar D22_EMN_URLs_Keys_schemas-1.0-SNAPSHOT.jar
```

### 5.2 真实模式启动（必须注入 Key）

```powershell
$env:AI_MODE="deepseek"
$env:AI_API_KEY="sk-你的真实密钥"
$env:AI_MODEL="deepseek-flash"
$env:AI_BASE_URL="https://api.deepseek.com"
java -jar D22_EMN_URLs_Keys_schemas-1.0-SNAPSHOT.jar
```

### 5.3 调用接口

- 同步：`POST http://localhost:8080/api/v1/ai/chat`，body `{"message":"你好"}`
- 流式：`POST http://localhost:8080/api/v1/ai/chat/stream`，同 body，返回 `text/event-stream`
- 健康：`GET http://localhost:8080/api/v1/ai/health`

### 5.4 运行测试

```powershell
& "D:\SoftwareInstall\Apache\Maven\apache-maven-3.9.16\bin\mvn.cmd" test
# 结果：Tests run: 83, Failures: 0, Errors: 0
```

### 5.5 扩展第二家供应商（未来操作清单）

当前保持克制、不预先平台化。真正需要时按以下步骤，**不改业务层**：

1. 在 `adapter` 下新建子包，如 `adapter/openaicompat/`；
2. 实现 `ChatModelPort`（专有 Options/消息）、`NativeUsageReader`（专有 usage）；
3. 新增一个 `@Configuration`，`@ConditionalOnProperty` 匹配新 mode，手动构造 `ChatModel`；
4. 在 `AiConstants` 与 `AiConfigurationValidator` 增加新 mode 的合法值与校验；
5. 复用 `VendorBoundaryTest` 思路，把新供应商包名加入扫描前缀白名单。

## 6. 竖屏层级树（能力视角）

```text
供应商无关能力分层
├─ 配置层 app.ai（唯一配置源）
│  ├─ mode/model/base-url/api-key → AI_* 环境变量
│  └─ AiConfigurationValidator → 启动快速失败
├─ 端口层 adapter（中立）
│  ├─ ChatModelPort → 选项构造 + 推理读取
│  ├─ NativeUsageReader SPI → 原生用量
│  └─ NativeUsage → 可空字段载体
├─ 适配器层 adapter/deepseek（专有边界）
│  ├─ DeepSeekChatAdapter
│  ├─ DeepSeekNativeUsageReader
│  └─ DeepSeekChatModelConfiguration → 手动 ChatModel
├─ 业务层 service（只依赖可移植抽象）
│  ├─ RemoteAiChatService
│  └─ MockAiChatService
├─ 观测层 observability（去供应商化）
│  ├─ TokenUsageSnapshot（reader 版）
│  ├─ ModelCallRecorder / ModelCallObservation
└─ 治理层 resilience（超时/重试单一责任层）
```

## 7. 常见问题与避坑（Pitfalls）

| 问题 | 正确做法 | 错误做法 |
| --- | --- | --- |
| 配置源 | 只用 `app.ai.*`，排除自动配置 | 同时保留 `spring.ai` 与 `app.ai` 两套 |
| 重试 | 关闭内置重试，`resilience` 单层治理 | 两处都开重试导致放大叠加 |
| Token 判空 | 走原生 reader 保留 null | 信任 `DefaultUsage` 把缺失当 0 |
| 密钥管理 | 环境变量注入，错误不回显 | 硬编码或在日志打印 Key |
| 类型依赖 | 业务层只 import 可移植抽象 | 业务层直接 `import DeepSeek*` |
| 二进制解析 | 严格按字段顺序，先怀疑偏移 | 把 `tag=0` 归因于文件损坏 |
| 验证诚实 | 无 Key 标注"未验证" | 虚构联网成功结果 |

## 8. 记忆简语（Mnemonics）

- **一句话定义**：`供应商无关 = 业务只认可移植抽象，专有类型关进适配器。`
- **端口适配器口诀**：`端口中立定契约，适配器里做翻译，依赖箭头指抽象，换家不碰业务层。`
- **Usage 口诀**：`原生 record 真判空，SPI 读取在边界，null 是缺失零是零。`
- **配置口诀**：`一个命名空间 app.ai，一套环境变量 AI_*，一个责任层管重试。`
- **守卫口诀**：`常量池扫描做哨兵，越界引用不放行，注释字符串不扰民。`
