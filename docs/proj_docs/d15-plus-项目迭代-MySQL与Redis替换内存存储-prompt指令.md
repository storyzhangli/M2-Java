## 2. 本次功能目标

将原来基于 **classpath 种子 JSON + `ConcurrentHashMap` 内存仓库** 的运行时数据存储方案，改造为基于 MySQL 和 Redis 的可靠存储方案。当前项目包含 Prompt 模板管理与客服、编程两个角色的对话功能，因此先查明哪些数据由内存仓库存储，再分别设计持久化与缓存职责。

核心原则：

- **MySQL 优先作为需要长期保存、可查询、可更新的数据的持久化主存储。** 如果扫描结果证明本次数据属于 Prompt 模板管理，应优先保证模板创建、查询、更新、启停、版本或更新时间等行为持久化。
- **Redis 按实际需求用于缓存或短期高频状态。** 不得仅因已添加 Redis 依赖，就将其当成 MySQL 的无条件替代品或唯一长期数据源。若项目现状要求 Redis 承担特定持久化职责，必须说明数据类型、持久化配置、丢失风险、恢复方案与一致性设计，并用证据验证。
- classpath JSON 可以保留为初始种子数据或开发初始化资源，但不得继续作为每次运行的权威数据源，也不得在每次启动时无条件覆盖数据库中的新增、编辑、禁用或删除数据。
- `ConcurrentHashMap` 可以用于确有必要的进程内临时缓存，但不得继续承担需要重启后保留或多实例共享的权威存储职责。
- 必须尽量沿用 D15 现有架构、命名、接口和代码风格，以增量改造为主，不做无关重构。

## 4. 第二阶段：设计存储职责与数据迁移

### 4.1 数据职责划分

扫描后建立数据清单，逐类说明：数据用途、是否必须持久化、读写频率、是否适合缓存、数据丢失影响、选定的存储方式。

至少评估：

- Prompt 模板定义及模板内容。
- 模板唯一标识、场景、角色、启用状态和版本/更新时间等元数据（以真实领域模型为准）。
- 客服与编程角色的模板引用关系。
- 如项目确实将会话或临时执行状态存于旧内存仓库，也要独立分析其生命周期，不能因本次范围而未经设计地混用数据模型。

不得凭空新增不需要的业务字段或功能。若模板管理属于实际内存数据主体，优先建议 **MySQL 持久化、Redis 缓存（在有实际收益时）** 的职责组合；如性能和复杂度评估表明暂时不需要 Redis 缓存，应说明理由，而不是机械地为所有读写加缓存。

### 4.2 MySQL 设计要求

根据实际数据模型设计表结构，并在设计中说明：

- 主键与业务唯一键。
- 必需字段、字段长度、非空约束、默认值。
- 创建时间、更新时间及必要的启用状态。
- 对高频查询实际有帮助的索引。
- 重复模板标识、并发更新与数据一致性如何处理。
- 删除策略（物理删除、逻辑删除或禁用），按现有业务需求选取。
- SQL 初始化/迁移脚本的执行方式与重复执行风险。
- 连接凭据从环境变量或项目既有安全配置注入，不将生产凭据写进源码。

遵循项目已有的数据访问技术。如果项目使用 MyBatis-Plus，就优先沿用其实体、Mapper、Service 和分页规范；不要为了本任务将整个项目迁移到另一套持久化技术。

### 4.3 种子 JSON 迁移策略

必须确定现有种子 JSON 的实际格式及字段映射，并选择可重复验证的初始化策略。要求：

- 将种子 JSON 作为初始数据来源，而不是运行期间的权威存储。
- 设计显式初始化或版本化迁移机制；若自动初始化，必须确保可安全重复执行。
- 不得在每次启动时无条件用种子数据覆盖数据库内已有修改。
- 通过稳定的业务唯一键处理重复导入；明确相同键但内容不同的处理策略。
- 对导入数量、跳过数量、失败记录和原因形成可追踪日志。
- 导入失败时不得静默吞掉异常，也不得让系统误报初始化成功。
- 说明历史数据如何校验、回滚或恢复；如果当前没有生产数据，仍须提供清晰的开发环境初始化方式。

不得直接删除原 JSON 文件；在确认初始化方式和迁移完成前保留它作为可审查、可恢复的资源。

### 4.4 Redis 设计要求

首先确认 Redis 的实际用途，再决定是否实现缓存。若作为 MySQL 缓存，必须明确：

- 缓存的数据对象与 Redis Key 规范。
- Key 是否需要环境、应用和业务域前缀。
- TTL 与失效策略。
- 读路径：缓存命中、未命中回源、数据库失败时的处理。
- 写路径：先写数据库还是先写缓存，以及更新/删除时如何失效缓存。
- 并发更新、缓存击穿/穿透/雪崩是否属于当前规模下的实际风险。
- 序列化方式、兼容性与反序列化异常处理。
- Redis 不可用时的行为：对允许降级的读操作回源 MySQL；对必须持久化的写操作不能假装写入成功。
- 缓存内容不得成为绕过权限校验的数据来源。

若当前场景不需要复杂缓存机制，不要无意义地引入分布式锁、复杂双删或过度设计。所有策略需与实际并发、部署方式和一致性要求匹配。
