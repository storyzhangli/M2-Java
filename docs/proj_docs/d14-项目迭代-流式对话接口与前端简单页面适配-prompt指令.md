## 4. 阶段 B：接口与流式协议设计

### 4.1 流式接口

结合实际项目技术栈和现有 API 风格决定端点、HTTP Method、请求 DTO、响应协议和返回类型。不得在未检查现有接口的情况下强制采用固定路径。设计中必须明确：

- 用户输入字段及必要校验。
- 会话标识（如项目已有会话机制则复用），以及新会话与续聊的区别。
- 成功数据事件、完成事件、错误事件的协议。
- 流开始、内容增量、正常结束、异常结束和客户端中断的处理。
- HTTP 状态码、`Content-Type: text/event-stream`、字符编码、缓存策略及必要响应头。
- 请求与日志是否需要关联已有 `requestId` / `traceId`。
- 超时、取消、限流和资源清理策略。

事件协议要稳定且易于前端解析。推荐在核实项目约定后采用明确的事件类型，例如 `message` / `delta`、`complete`、`error`，并使用一致的数据结构；不要让前端只能通过猜测字符串内容来判断事件状态。确保换行和特殊字符能被安全编码，不得手工拼接出格式不合法的 SSE 帧。

### 4.2 EventSource 与 Fetch 的选择

根据实际请求方式、鉴权方式和前端模板判断客户端实现：

- 浏览器原生 `EventSource` 通常适合 GET 请求，不能像 `fetch` 一样自由设置请求体和任意请求头。
- 如果聊天请求需要 POST JSON、请求体较大或必须携带自定义 Authorization Header，应评估使用 `fetch` 读取 `ReadableStream` 并解析 SSE 帧的方式。
- 如果使用 `EventSource`，应说明如何传递会话参数、如何处理断线重连、以及凭据/CORS 的影响。

不能只因为接口名叫 SSE 就默认前端必须使用 `EventSource`；选择必须与真实 API 契约一致，并在文档中说明理由。

### 4.3 Spring AI 流式调用

使用项目当前 Spring AI 版本已支持的流式调用 API。确认现有调用入口、返回类型和异常语义，重点核查：

- 模型流式调用是否真正启用。
- 如何把每个增量转换成客户端可识别的 SSE 事件。
- 正常完成如何发送结束事件。
- 异常发生在流开始前或开始后时如何处理。
- 客户端取消/断开后如何停止不必要的消费并释放资源。
- 不得将每个流式数据块假定为一个 Token、单词或完整句子。
- 流式返回不等于更快完成全部生成；应正确区分首段响应和完整结束。

如当前 MVC / WebFlux 技术栈对具体流式实现有约束，按实际依赖与官方文档选择兼容方案；不允许为图方便而引入大范围依赖变更。

## 5. 阶段 C：前端现成模板适配

优先改造仓库内已有模板，保持其布局、依赖、风格与目录规范。最小可用页面应包含：

1. 用户输入区域和发送操作。
2. 对话消息展示区域，区分用户消息与模型回答。
3. 模型输出的逐步追加展示，而不是等待全部完成才显示。
4. 请求期间的加载状态，并合理避免重复提交。
5. 完成、网络错误、服务端错误和中断状态的可见反馈。
6. 必要的清空/新会话操作（遵循项目现有会话设计）。
7. 基本输入校验、空输入保护、滚动展示和可用性处理。

前端处理要求：

- 按后端实际 SSE 事件协议解析，不要依赖硬编码的随机字符串格式。
- 将用户输入、模型增量、完成事件与错误事件分开处理。
- 处理响应体为空、非预期事件、连接中断和重复提交。
- 避免将模型返回内容直接作为不可信 HTML 注入 DOM；默认按纯文本安全渲染。
- 如果项目采用 Markdown 渲染，必须核实既有渲染库及其安全配置，防止 XSS。
- 不引入新的大体量 UI 框架，除非现有工程确有必要且经过说明。
- 不重建整套页面、不破坏现有模板结构，不擅自替换原有构建工具。

如果扫描后找不到可复用的模板，先记录证据，并采用项目现有技术栈下最小的 HTML/CSS/JavaScript 页面作为备选；不得未经说明创建新的独立前端工程。

## 6. 阶段 D：异常、安全与质量要求

至少检查并处理：

- 输入为空、过长或不符合请求 DTO 约束。
- 模型服务认证失败、限流、超时或返回异常。
- SSE 事件格式错误或客户端无法解析。
- 流开始前发生异常与流开始后发生异常。
- 客户端关闭页面、断网或取消请求。
- 重复提交与同一会话连续请求。
- 跨域、鉴权和必要请求头。
- 前端不可信内容的安全渲染。
- API Key 等机密不得写入源码、页面或日志。
- 对输出和日志设定合理上限，避免把整段超长对话无条件写入日志。

禁止为了让 SSE“看起来能用”而吞掉异常、把失败伪装成正常完成，或在完成事件之后继续输出内容。对已经开始发送响应头后的异常，应遵循 SSE 协议设计发送错误事件或关闭流，并在服务端记录可诊断的错误。
