## 一、任务目标

生成一份面向 Java 后端开发者的 Spring AI 工程实践知识笔记，帮助学习者理解并正确处理模型/API 调用中的：

1. 鉴权错误；
2. 限流与并发限制；
3. 网络连接错误；
4. 各类超时；
5. 服务端错误；
6. 重试、退避、限流配合及明确不应重试的场景。

核心目标不是罗列 HTTP 状态码，而是能够根据**错误原因、请求是否已被服务端处理、操作是否可安全重复、剩余时间预算**，设计有边界、可观测、不会放大故障的恢复策略。

## 二、学习基线与资料核验

- 默认基线：JDK 21、Spring Boot 3.5.16、Spring AI 1.1.8、Maven 3.9.16；示例以 Java 为主。
- 必须先核对目标版本的 `pom.xml`、Spring AI BOM、模型 Starter 和实际 HTTP 客户端依赖，再决定 API、配置项、异常类及默认值。
- 官方文档版本不一致时，以项目实际依赖版本对应的官方文档/API 为准；明确标注版本差异，不得把 Spring AI 1.0、1.1、2.x 或 SNAPSHOT 配置混用。
- 不得凭记忆编造配置项、默认重试次数、超时默认值、异常类型或 DeepSeek 错误码。无法确认的内容应标注“待核验”。
- 重点核验 Spring AI 模型调用重试配置、`TransientAiException`、`NonTransientAiException`、底层 HTTP 客户端超时与异常映射，以及流式调用是否适用相同重试策略。

## 三、必须覆盖的核心知识

### 1. 错误分类与定位层次

先建立从应用到远端模型服务的调用链：业务代码 → Spring AI `ChatClient` / `ChatModel` → Spring AI 模型实现 → HTTP 客户端 → DNS/TCP/TLS/网络 → 远端 API 网关与模型服务。

解释各层错误如何产生、可能映射成什么异常，以及为什么不能只根据异常类名或 HTTP 状态码做粗略判断。区分：

- HTTP 响应错误：收到明确状态码和响应体；
- 传输层错误：未能建立连接、连接中断或响应读取失败；
- 超时：连接、读取、请求总时限或连接池等待超限；
- 应用层错误：参数、业务状态、余额、权限、模型能力或响应格式问题。

### 2. 鉴权与请求参数错误

必须讲清：

- 401 与 403 的典型区别：身份凭证无效/缺失与已认证但无权限；具体语义仍以服务商文档为准；
- API Key 错误、缺失、撤销、权限不足、环境变量未注入等常见原因；
- 400、422 等请求格式或参数错误；
- 402 等账户余额/计费状态错误（以实际服务商错误码为准）；
- 为什么凭证、权限、请求参数或账户状态未修正前，重复请求通常不会成功；
- 错误响应可以记录状态码、服务商错误码、请求关联 ID 等必要诊断信息，但不能记录凭证或敏感请求内容。

### 3. 限流、并发与 429

必须讲清：

- QPS / RPM、并发数、账户级限额、模型级限额和配额不是同一个概念；
- 限流与服务端过载的区别；
- 429 的典型原因、读取并尊重 `Retry-After`（若服务端提供）、客户端令牌桶/漏桶/并发闸门等限流策略；
- 多实例应用如何避免每个实例各自限流却导致账户总量超限；
- 指数退避、随机抖动（jitter）、最大等待时间及重试预算；
- 不能通过立即、高频重试解决 429，否则会形成重试风暴。

### 4. 网络错误

至少解释并比较：

- DNS 解析失败；
- TCP 连接拒绝或无法建立；
- TLS 握手/证书错误；
- 连接重置、连接提前关闭；
- 连接池获取连接失败；
- 请求发送后连接中断、响应读取中断。

重点说明：请求尚未发送、请求已发送但响应未收到，是两种不同状态。后者可能存在“服务端已经处理，但客户端不知道结果”的不确定性；重试前必须考虑操作幂等性及重复计费/重复副作用风险。

### 5. 超时分类

至少区分：

- DNS 解析超时（若客户端栈可单独配置/观测）；
- 连接超时（connect timeout）；
- TLS 握手超时（若客户端支持独立配置）；
- 连接池获取超时（connection-request / pool-acquire timeout）；
- 响应/读取超时（response/read timeout）；
- 单次请求总时限与上游业务整体 deadline；
- 流式请求的首包等待、空闲读取或整体生命周期限制（按客户端能力和场景核验）。

说明不同超时代表什么、在哪一层配置、超时后请求是否可能仍在远端执行。禁止把所有超时统一称为“连接超时”。

### 6. 服务端错误

解释 500、502、503、504 等常见状态码的典型含义与边界：

- 500：服务端内部处理失败；
- 502：网关从上游获得无效响应或上游连接异常；
- 503：服务暂不可用、过载或维护；
- 504：网关等待上游响应超时。

状态码含义以实际服务商文档和响应为准。讲清暂时性故障与永久性配置/业务错误的区别，以及有限重试、退避、熔断和快速失败的适用关系。

### 7. 重试、退避与不重试决策

必须提供一张“错误类型—典型表现—是否重试—前置条件—等待策略—最终处理”的决策表，至少涵盖：

- 401/403：修正凭证或权限前不重试；
- 400/422：修正请求前不重试；
- 402：处理余额/账户状态前不重试；
- 429：受控重试，优先尊重 `Retry-After`，并结合限流与抖动；
- DNS/TCP 临时故障：根据根因、请求发送阶段与剩余预算决定；
- TLS 证书/信任配置错误：修复配置前不盲目重试；
- 连接中断/读取超时：结果可能未知，先分析幂等性；
- 500/502/503/504：可有限重试，但必须有最大次数、总时限和退避；
- 用户主动取消、业务校验失败、模型输出无法满足业务约束：一般不应把它们当作网络瞬时错误反复重试；
- 流式响应已经向客户端输出部分内容后发生错误：解释为什么通常不能简单从头重放并拼接，需设计明确的流中断协议或由调用方重新发起。

讲解固定间隔、指数退避、指数退避 + full jitter 的差异。给出公式或伪代码，并解释初始间隔、倍率、最大间隔、最大尝试次数、总 deadline、随机抖动的作用。说明“最大尝试次数”是否包含首次调用，必须按所用库的定义核验。

### 8. 幂等性、重试风暴与多层重试

必须覆盖：

- 幂等操作与非幂等操作；
- 请求发送后结果未知的风险；
- 幂等键的作用和适用边界（不能假设所有模型 API 都支持）；
- Spring AI 内置重试、HTTP 客户端重试、Resilience4j 重试及业务层重试叠加可能造成的请求倍增；
- 只选择清晰的重试责任层，避免多层无协调重试；
- 最大尝试次数、总超时预算、并发限制、熔断和快速失败；
- 退避期间线程阻塞与响应式非阻塞等待的区别（只讲与本主题相关内容，不扩展为完整响应式教程）。

### 9. Spring AI 落地

以实际版本为准，介绍：

- `ChatClient` / `ChatModel` 调用链中重试所在的位置；
- Spring AI 模型实现提供的重试属性、异常分类及适用范围；
- 底层 HTTP 客户端连接/读取超时与 Spring AI 重试配置之间的关系；
- `TransientAiException` 与 `NonTransientAiException` 的语义和实际使用方式（仅在目标版本确实存在时示例）；
- 如使用 Resilience4j，解释 Retry 配置中的最大尝试、等待间隔、异常白名单/黑名单和退避函数；
- 同步调用与流式调用的重试差异，禁止未经验证宣称流式场景自动适用普通重试规则；
- 如何统一映射成业务可识别的错误类型，同时保留原始 cause 与必要诊断字段。

避免堆砌多个容错组件。示例只选一条推荐主线，其他方案简要对比即可。

## 四、必须完成的最小实践

采用**模拟故障优先**，不要求真实模型 API 调用。使用 Java 单元测试或可运行的小型 Spring Boot 示例模拟以下结果：

1. 401/403：不重试，直接失败并给出可操作错误；
2. 400/422：不重试；
3. 429：有限重试，验证退避/等待策略；
4. 503 或 5xx：达到成功条件前有限重试，超过次数后失败；
5. 连接异常或超时：验证重试策略和最终异常映射；
6. 不可重试业务异常：确认不会被重试；
7. 达到最大次数：确认总调用次数与最终异常正确；
8. 请求取消或流式已输出部分内容：说明并测试所选策略（若本练习涉及流式接口）。

测试必须验证“调用次数、等待策略/退避计算、错误分类、最终结果”，不能只断言没有抛异常。优先使用 Mock、Stub、MockWebServer/WireMock 或项目已有测试设施；只有确有必要才引入新依赖。

## 六、学习验收标准

知识笔记必须使学习者能够独立回答并实践：

1. 为什么 401、429、503 不能采用相同重试策略？
2. 为什么连接超时、读取超时与总 deadline 必须区分？
3. 请求已发送但响应未收到时，为什么不能确认服务端没有处理？
4. 指数退避为什么还需要 jitter 和最大等待时间？
5. 为什么多层重试会放大请求数量？
6. 哪些错误必须先修复根因而不能重试？
7. Spring AI 重试配置与底层 HTTP 超时如何配合？
8. 流式响应部分输出后为什么不能简单从头自动重试？
9. 如何用 Mock 测试证明重试次数、退避和不重试策略正确？

验收必须包含可执行测试及其实际结果；不得伪造“测试通过”或编造执行证据。若 AI 未实际运行代码，必须标明“示例代码，未执行验证”。
