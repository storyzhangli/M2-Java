7. 记录初始 Git 状态，保护用户已有未提交改动。

### 4.2 必须核实的 Spring AI 1.1.8 行为

依据 Spring AI **1.1** 版本文档和实际解析的 1.1.8 依赖，核实并记录：

- `ChatClient` 同步链：`prompt() -> call() -> content()`；
- `ChatClient` 流式链：`prompt() -> stream() -> content()`，以及是否需要 `chatResponse()` 获取元数据；
- `stream()` 返回的 Reactor `Flux` 类型与订阅/执行时机；
- 流式调用支持的响应类型和异常传播行为；
- Spring AI 1.1.8 对 imperative / reactive 两种调用模式的官方实施说明；
- 当前模型 Provider（沿用项目已有配置）是否支持流式响应，是否需要额外参数或不同 API 配置；
- 当前模型调用、Advisor、上下文/历史服务是否存在阻塞步骤，以及它们对流式输出的影响。

不得用 Spring AI 2.x 文档或不匹配版本的示例代替 1.1.8 结论。遇到文档与实际依赖行为不一致时，记录最小复现和实际结果。

### 4.3 MVC / WebFlux 方案决策

以当前项目真实 POM 和应用类型作判断，不先入为主：

- 若现有应用是 Spring MVC/Servlet，同步接口已稳定，优先评估保留 MVC，并按 Spring AI 1.1.8 的要求补充 Reactive 运行依赖，使模型层可使用流式能力；
- 若同时存在 `spring-boot-starter-web` 与 `spring-boot-starter-webflux`，核实 Spring Boot 3.5.16 的自动配置结果。双依赖通常仍选择 MVC，而不是自动切换到 WebFlux；必须用启动日志、条件评估或运行时应用类型证据确认；
- Spring MVC 可适配 `Flux` 等响应式返回值；使用流式媒体类型时可将多值流转换为异步响应写出。但 Servlet 响应写出仍有阻塞部分，不能把它描述为端到端完全非阻塞；
- 只有当现有系统已是 WebFlux，或有清晰业务/运行理由时，才考虑完整 Reactive Stack。若建议迁移，必须分析同步接口兼容、过滤器、安全、事务、阻塞 DAO、部署服务器和测试影响，不得顺手迁移。

最终输出一张决策表：当前 Web 依赖、实际应用类型、Spring AI 流式要求、推荐组合、备选方案、兼容风险、验证证据。明确说明为何选择该组合。

## 5. 阶段二：流式接口设计

先沿用原同步接口的业务输入、会话标识、提示词组装、权限及历史上下文逻辑。新增流式入口，不复制一套业务逻辑。

### 5.1 接口契约

- 新增独立的流式聊天接口；具体 URL 和 HTTP 方法根据现有接口命名规范设计，并在实施前列明。
- 原同步接口的 URL、HTTP 方法、请求/响应 DTO、成功响应结构和既有错误行为保持不变。
- 请求参数优先复用现有 DTO；若流式场景确需差异字段，说明必要性并确保旧客户端不受影响。
- 明确媒体类型（通常为 `text/event-stream`）、字符编码、事件格式、结束事件和错误事件语义。
- 明确流式响应是纯文本片段，还是包含 `event` / `id` / `data` 的结构化 SSE。不得让前端无法区分普通内容、结束和失败。
- 不把 API Key、内部异常堆栈或敏感会话内容放入事件和日志。

### 5.2 共享业务逻辑

设计一条可复用的请求准备链，覆盖参数校验、身份/会话权限、上下文读取、Prompt 构造和模型选项；同步与流式分支仅在模型调用和响应适配处区分。

- 同步分支继续使用现有同步调用方式，不因新增流式 API 改变行为。
- 流式分支使用 Spring AI 1.1.8 支持的 `ChatClient.stream()` / `Flux` 路径。
- 不在 Reactor 流中调用 `block()`、`collectList()` 等把流重新聚合为同步响应的操作；除非某个明确的既有边界必须阻塞，并且设计说明原因、线程影响及替代方案。
- 不通过脱离请求生命周期的 `subscribe()` 启动后台调用；让响应式流由 Web 层订阅和管理。
- 不把流式响应伪装成逐字输出；按模型实际产出的 chunk 发送，并承认 chunk 不等于单个字符或 token。

### 5.3 生命周期和失败行为

设计并验证：

- 正常首块、连续数据块、正常结束；
- 模型异常、鉴权失败、超时、限流和上游断流；
- 客户端主动断开时取消上游订阅并释放资源；
- 无数据/慢响应情况下的超时策略；
- 代理或服务器缓冲导致的伪流式问题；
- 异步请求的 TraceId、用户身份和 MDC / Reactor Context 传播；
- 若沿用 历史记录，用户消息和最终助手消息的记录时点；中途失败或取消时如何标记，不得把半截回答标成完整成功消息；
- 流式端点的并发与资源上限。仅实现满足当前场景所需的机制，不添加无依据的复杂框架。

如使用 SSE 心跳、事件 ID、断线重连或 Last-Event-ID，必须由实际客户端需求决定，不得扩大为本次默认必做项。

### 5.4 原接口兼容清单

逐项列出并验证：路径、方法、参数、响应 DTO、状态码、错误结构、鉴权、会话上下文、同步等待行为、前端调用方式。没有经过用户批准，不得改变原接口契约。
