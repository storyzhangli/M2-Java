# 你的 90 天 Java → Java AI 工程师训练计划

这套计划专门针对你的情况设计：4 年 Java 开发经验、2.5 年职业空窗期、能写代码，但自律性不足、技术表达不足。

你的任务不是从零学习编程，而是重新建立三种能力：

- 工程能力： 恢复 Java 后端开发能力，能够独立实现、测试、排错和部署。
- AI 应用能力： 按照 Spring AI → RAG → Tool Calling → MCP → Agent Workflow → 生产级工程化的顺序，构建真正可用的 AI 应用。
- 求职与表达能力： 能够解释原理、阐明设计取舍、展示代码证据、回答面试官的连续追问。

本计划共 90 天，每天安排 9 小时训练时间，总计 810 小时的计划投入。考虑到持续 90 天的强度较高，9 小时是每日安排的训练时段，包含复盘、求职、表达练习和休息间隔，不要求连续进行 9 小时高强度编码。

## 一、90 天的路线与验收成果

第 1–14 天：Java 工程恢复

恢复 Java 核心、并发、JVM、Spring Boot、SQL、测试与部署基础。

成果：基础测评报告、后端服务、错题库、简历初稿。

第 15–28 天：Spring AI

模型调用、Prompt、结构化输出、流式响应、记忆、异常处理。

成果：独立开发一个 Java AI 问答服务。

第 29–44 天：RAG

文档解析、切分、Embedding、向量检索、引用、评估。

成果：企业技术文档知识库问答系统。

第 45–53 天：Tool Calling

工具定义、参数校验、实际执行、失败处理和权限控制。

成果：AI 能查询工单、检索资料、创建待审批工单。

第 54–62 天：MCP

MCP Server、Client、工具发现、协议通信和访问控制。

成果：可让 AI 应用通过 MCP 使用 Java 业务工具。

第 63–73 天：Agent Workflow

路由、状态、工作流、重试、人工审批、可恢复执行。

成果：企业研发助手工作流，而不是只有聊天功能的 Demo。

第 74–86 天：生产级工程化

测试、权限、安全、日志、追踪、评估、成本、性能和部署。

成果：一个能够重复运行、验证和演示的完整项目。

第 87–90 天：最终验收与求职冲刺

项目答辩、模拟面试、简历优化、求职数据复盘。

成果：可展示的作品集、面试讲解稿、下一阶段行动计划。

关键原则： Java 求职从第 1 天开始，不等待 90 天学习结束。AI 是升级方向，不是让你再经历一段没有收入的长期准备期。

技术主线使用 Spring AI。它提供统一的模型 API、ChatClient、向量存储、Tool Calling 和 MCP 等能力；工具调用时由应用程序执行实际操作，而不是把业务系统权限直接交给模型。

[Spring AI API 官网](https://docs.spring.io/spring-ai/reference/api/)

[Tool Calling 官网](https://docs.spring.io/spring-ai/reference/api/tools.html)

# 二、每日 9 小时的固定执行制度

你的自律问题不能靠“每天努力一点”解决，需要把学习变成一个有时间、有交付物、有验收的流程。

## 每日时间表

### 09:00–09:30

闭卷回忆和计划

回答昨天的 3 个问题，查看昨日未完成任务，确定今日最重要的交付物。

### 09:30–11:30

技术学习与源码阅读

学习一个明确主题，查阅官方文档，理解一个关键实现流程。

### 11:45–13:15

独立编码

关掉教程，自己实现功能；遇到问题先定位，再请 AI 给提示。

### 14:15–16:15

主项目开发

将上午知识用于主项目，完成一个可以运行、测试或演示的增量。

### 16:30–17:30

技术表达训练

不看稿讲原理、画架构图、回答 AI 面试官追问；录音或文字复盘。

### 18:30–19:30

求职行动

投递匹配岗位、优化简历、准备面试或根据真实反馈补弱。

### 19:30–20:30

测试、日报和明日准备

运行测试、提交 Git 代码、填写学习记录，确定明日第一项任务。

每天安排的训练时段共 9 小时；餐饮和较长休息不计入其中。建议每 50–60 分钟短休息几分钟，避免持续长时间盯屏幕。每第 7 天仍保留 9 小时计划，但以测评、复盘、修复和整理为主，不再堆积大量新知识。

## 每天必须留下的五类证据

| 证据     | 合格标准                               |
| -------- | -------------------------------------- |
| 技术笔记 | 能用自己的话解释，不是复制文档         |
| 独立代码 | 有实际代码改动，不只有 AI 生成的内容   |
| 测试记录 | 有测试结果、失败用例或明确的未解决问题 |
| 技术表达 | 至少一次不看稿的讲解或口头问答         |
| 求职记录 | 有真实投递、面试准备或招聘反馈记录     |

项目代码统一保存在 Git 仓库中；重要结论放在 `docs/` 目录。AI 可以帮助检查这些证据，但不能凭对话内容假装知道你实际执行了什么。

## 主项目：一个项目逐步升级，不做十个半成品

项目名称：`engineering-assistant`

你将它从普通 Java 后端应用逐步升级为 AI 研发助手。

第 1 版：工单管理后端

用户、工单、状态流转、数据库、权限

第 2 版：Spring AI 问答服务

Prompt、结构化输出、流式回答、日志

第 3 版：企业知识库 RAG

文档入库、检索、引用来源、质量评估

第 4 版：Tool Calling + MCP

查询工单、检索文档、受控业务工具

第 5 版：Agent Workflow

意图识别、路由、执行状态、人工审核

第 6 版：生产级交付

安全、测试、可观测性、成本控制、部署

每天围绕这个项目增加一个功能或解决一个问题。你不需要独立训练模型，也不需要先学完全部机器学习课程。

## 阶段 C：第 29–44 天，RAG 实战

RAG（Retrieval-Augmented Generation，检索增强生成）包含文档导入、切分、检索和生成等环节。Spring AI 提供模块化 RAG 组件，可组合检索器、上下文增强和生成流程；你必须理解每一环节，而不是只调用一个封装好的 Advisor。

[Retrieval Augmented Generation | 检索增强生成 官方文档](https://docs.spring.io/spring-ai/reference/api/retrieval-augmented-generation.html)





| 天数   | 核心学习与实践任务                                           | 当天必须提交的成果                                           |
| ------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| Day 29 | 学习 RAG 的完整数据流：导入、解析、切分、向量化、检索、生成。设计知识库模块边界。 | RAG 架构图、主要 API 清单、数据模型初稿。能用 3 分钟解释 RAG 为什么不同于直接向模型提问。 |
| Day 30 | 学习文档解析和清洗。处理文本、Markdown 等基础格式，再扩展到 PDF。 | 完成文档解析服务，保留文件 ID、标题、页码或段落来源。        |
| Day 31 | 学习文本切分、重叠窗口、语义边界、元数据。                   | 对同一批文档实现两种切分方式；记录 chunk 数量、长度和切分缺陷。 |
| Day 32 | 学习 Token、Embedding（文本向量化）、向量维度和相似度。      | 将固定文档转换为向量；记录向量模型及其维度，不把不同模型的向量混用。 |

| Day 38 | 研究来源引用、页码和文档 ID 的保留方式。                     | 每条回答展示来源及相关片段；校验引用不能只是编造的链接或页码。 |
| Day 39 | 测试切分粒度、Top-K 和相似度阈值对检索的影响。               | 做一张对照表，记录至少 3 组参数组合的结果与缺点。            |
| Day 40 | 学习元数据过滤、用户权限和文档更新。                         | 增加用户或部门权限过滤；验证无权用户无法检索受限文档。       |

| Day 42 | 研究重排（Reranking）和检索后处理。                          | 在小样本上比较重排前后结果；保留实验记录，说明是否值得继续使用。 |
| Day 43 | 完成 RAG 端到端集成：导入、检索、回答、引用、权限。          | 通过固定问题集的自动化测试；生成第一版 RAG 质量报告。        |
| Day 44 | RAG 综合答辩和代码重构。随机抽取问题，现场追踪检索证据。     | 输出架构图、失败案例、评估数据与修复清单；独立讲解一次完整问答过程。 |

### RAG 阶段的硬性验收

你的系统至少应该支持：

- 上传文档、解析、切分、向量化与检索。
- 回答展示真实来源，而非只有一段生成文本。
- 无相关证据时，系统能够拒答或明确说明不知道。
- 用户和文档权限能够隔离。
- 有一组固定评估问题，可重复运行比较效果。

### Tool Calling 的安全底线

- 模型的参数必须经过应用端校验，不能直接拼接 SQL 或执行任意命令。
- 只读工具优先；写工具需要适当的业务授权与审批。
- 工具超时或失败时，不能凭模型生成的回答假装操作已成功。
- 记录真实工具调用结果，让使用者能够确认查询和写操作是否完成。

你的优势在这里会开始显现：你不是只会提示词的 AI 使用者，而是能够将大模型与企业 Java 业务服务集成的工程师。

### 为什么先做 Workflow，再做更自主的 Agent？

第 73 天验收： 你能回答“为什么这里使用模型决策，而那里必须使用确定性的代码？”并能展示实际执行记录，而不是只展示对话截图。

# 五、技术表达训练：每天 1 小时，按固定模板练

你提到技术表达不足，这需要单独训练。技术表达不等于背出概念，而是把思考过程组织成对方听得懂、能够验证的解释。

每天 16:30–17:30 按下列方式执行：

- 前 10 分钟：不看资料，写下主题的关键点。
- 接下来 15 分钟：用 3–5 分钟口头讲解，录音或转成文字。
- 接下来 20 分钟：让 AI 充当面试官，连续追问至少 3 轮。
- 最后 15 分钟：改写答案，再讲一遍，记录改进点。

## 固定技术表达模板

遇到技术问题，按这个顺序回答：

1. 结论： 先直接回答问题。
2. 原理： 解释它为什么这样工作。
3. 实现： 说明在代码或系统中如何使用。
4. 取舍： 说明为什么选择当前方案，而不是另一方案。
5. 异常与边界： 说明有哪些失败场景。
6. 验证证据： 说明如何用代码、测试或数据证明结论。

例如，面试官问：“为什么知识库用了 RAG？”

你的回答应包括它解决了什么实际问题、文档如何进入向量库、检索结果如何成为上下文、什么时候会检索失败、如何评估准确性，以及权限如何隔离，而不是只说“因为 RAG 可以减少幻觉”。

| ----------- | ------------------------------------ | ----------------------------- |
| 第 1–14 天  | 能用自己的话解释 Java 核心知识       | 每天至少回答 3 个不看稿的问题 |

不要追求口音、措辞或术语听起来“高级”。你需要的是：说得清楚、说得有依据、能够经得起追问。

# 六、AI 外部监督系统：让计划每天都能执行

## 每天的调整规则

80–100

低于 65

单日分数只是反馈信号。不能因为所有代码测试通过，就忽略技术表达完全说不清；也不能因为当日没有面试，就把所有求职相关工作判定为失败。AI 监督应根据当天实际约定的任务与证据评分。

## 每周闭卷测试

每 7 天做一次 60–90 分钟测验，包含概念、编码、调试与口头讲解。第 14、28、44、53、62、73、86、90 天设置阶段验收，不通过时优先补齐关键能力，而不是机械追赶进度。

你有 2.5 年空窗期，所以求职必须与学习并行。每天固定的 18:30–19:30 求职时段，按照以下阶段执行。

## 空窗期怎么表达？

不要编造经历，也不必在开场时做长篇解释。可以按事实简洁说明：

> 我之前有一段职业间隔。目前已经重新投入到 Java 工程能力恢复和 AI 应用开发实践中，近期主要在构建基于 Spring AI 的知识库问答与工具调用系统。我希望通过当前的代码、测试和项目演示，展示自己的实际能力。

这段话只适合在符合你真实情况时使用。面试时应以具体代码、测试和项目证据支撑；如果被问及空窗期的具体原因，如实回答即可。

# 九、如果某一天自律失败，如何防止计划崩盘？

不要求你 90 天每天都保持相同状态。真正的外部监督体系必须有失败恢复机制。

## 90 分钟最低执行方案

当你因疲惫、拖延或其他事情无法完成正常训练时，执行以下任务：

| 时间    | 最低任务                       |
| ------- | ------------------------------ |
| 20 分钟 | 闭卷回忆一个技术主题           |
| 40 分钟 | 独立写一个小功能或修复一项缺陷 |
| 20 分钟 | 运行测试并记录结果             |
| 10 分钟 | 提交日报，写好明日第一任务     |

最低方案不是替代 9 小时计划，而是防止一次失控发展成连续数天停摆。

还要设定三条纪律：

1. 不因某一天没完成而把全部计划推倒重来。
2. 不通过延长到深夜来补偿白天的拖延，优先恢复正常作息。
3. 如果连续两天低于执行门槛，先把后续任务缩小，不再添加新技术、买新课程或换新框架。

对你而言，稳定完成一个中等规模项目，比每天把学习时长做得很漂亮但没有代码交付更重要。
