# Spring AI M2 知识笔记：多模型适配——切换不同厂商模型与统一封装

版本基线：JDK 21 · Spring Boot 3.5.16 · Spring AI 1.1.8 · Maven 3.9.16

## 1. 学习目标与核心结论

本主题要解决的问题是：当应用同时需要 DeepSeek、OpenAI、Anthropic 等不同厂商的模型时，如何在不让业务代码依赖具体厂商 SDK 的前提下，实现模型切换、统一调用和能力差异管理？

完成本章后，应具备以下能力：

1. 区分模型厂商、模型 ID、API 协议、Endpoint 和 Spring AI 适配器。
2. 理解 `ChatModel`、`StreamingChatModel`、`ChatClient` 和 `ChatOptions` 的职责。
3. 掌握同一厂商切换模型、不同厂商切换、多模型共存和运行时路由。
4. 能够设计适度的统一模型调用接口。
5. 理解通用 API 不代表厂商能力完全一致。
6. 能通过 Mock 测试验证模型选择、能力检查和异常处理。

## 2. 多模型适配的基本概念

### 2.1 必须区分的五个概念

| 概念              | 含义                                   | 示例                                        |
| ----------------- | -------------------------------------- | ------------------------------------------- |
| Provider          | 模型服务提供商                         | DeepSeek、OpenAI、Anthropic                 |
| Model ID          | 厂商提供的具体模型标识                 | `deepseek-chat`、`deepseek-reasoner`        |
| API Protocol      | 应用与服务之间的接口协议               | OpenAI Chat Completions、Anthropic Messages |
| Endpoint          | 实际请求地址                           | `https://api.deepseek.com`                  |
| Spring AI Adapter | 将厂商 API 映射到 Spring AI 抽象的实现 | `DeepSeekChatModel`、`OpenAiChatModel`      |

这五者之间的关系：

```
业务任务
   |
   v
Spring AI ChatModel 抽象
   |
   +--------------------------+
   |                          |
   v                          v
DeepSeekChatModel        AnthropicChatModel
   |                          |
   v                          v
DeepSeek API              Anthropic API
   |                          |
   v                          v
deepseek-chat             claude 模型
```

模型 ID 不是 Provider，Endpoint 也不是模型 ID。

例如，使用同一个 DeepSeek Endpoint，可以指定不同的模型 ID；而同一个 OpenAI-compatible API 协议，也可以连接不同的服务商。

### 2.2 四种不同的多模型场景

| 场景                          | 示例                           | 需要解决的问题           |
| ----------------------------- | ------------------------------ | ------------------------ |
| 同一厂商切换模型              | DeepSeek Chat 切换 Reasoner    | 模型参数和能力变化       |
| 不同厂商切换                  | DeepSeek 切换 Anthropic        | 不同适配器与配置         |
| 多模型同时存在                | 一个应用同时使用两个 ChatModel | Bean 注册和选择          |
| OpenAI-compatible 多 Endpoint | DeepSeek、其他兼容服务         | Base URL、密钥及协议差异 |

### 2.3 为什么需要多模型适配？

企业应用可能存在多种需求：

- 简单文本任务优先选择低成本模型。
- 复杂分析任务选择推理能力更强的模型。
- 某个模型无法使用时，选择满足业务要求的备用模型。
- 不同业务场景使用专门模型。
- 对比不同模型的响应质量和成本。

但是，备用模型不能随意切换。新模型必须满足当前任务所要求的最低能力，例如结构化输出、工具调用或流式响应。

### 2.4 OpenAI-compatible 不等于完全兼容

OpenAI-compatible 通常表示某些 API 接口和请求格式兼容，不代表：

- 请求参数完全一致。
- 所有模型能力一致。
- Tool Calling 的调用过程完全一致。
- JSON Schema 支持完全一致。
- 流式事件完全一致。
- 错误码和限流策略完全一致。
- 模型行为和生成质量一致。

DeepSeek 官方说明其 API 支持 OpenAI / Anthropic 兼容格式，但仍需遵循各自的模型参数和 API 文档。

## 3. Spring AI 抽象层与调用链

### 3.1 核心 API 职责

| API                  | 职责                   | 主要使用场景                       |
| -------------------- | ---------------------- | ---------------------------------- |
| `ChatModel`          | 同步聊天模型抽象       | 普通请求与响应                     |
| `StreamingChatModel` | 流式聊天模型抽象       | Flux 响应                          |
| `ChatClient`         | 面向应用的流畅调用 API | 业务服务调用模型                   |
| `ChatClient.Builder` | 构建 ChatClient        | 配置默认系统消息、Advisor 等       |
| `Prompt`             | 封装消息和模型选项     | 构建模型请求                       |
| `Message`            | 表示对话消息           | System、User、Assistant 等         |
| `ChatOptions`        | 通用模型参数抽象       | 温度、Token 上限等                 |
| `ChatResponse`       | 模型统一响应结构       | 获取结果及响应元数据               |
| `Generation`         | 单个生成结果           | 获取 AssistantMessage 和结果元数据 |

Spring AI 1.1.8 的 `ChatModel` 定义了：

```
public interface ChatModel
        extends Model<Prompt, ChatResponse>, StreamingChatModel {

    @Override
    ChatResponse call(Prompt prompt);
}
```

`StreamingChatModel` 的流式调用返回：

```
Flux<ChatResponse> stream(Prompt prompt);
```

其中：

- `ChatModel` 处理同步模型调用。
- `StreamingChatModel` 处理响应式流。
- `ChatClient` 封装更方便的 Prompt 构建和调用过程。

### 3.2 ChatClient 与 ChatModel 的关系

推荐理解：

```
业务 Service
     |
     v
 ChatClient
     |
     v
    Prompt
     |
     v
  ChatModel
     |
     v
 Provider Adapter
     |
     v
 模型服务 API
```

业务层主要使用：

```
String content = chatClient.prompt()
        .user("解释 Spring AI 的作用")
        .call()
        .content();
```

如果希望获得完整响应信息，可以使用：

```
ChatResponse response = chatClient.prompt()
        .user("解释 Spring AI 的作用")
        .call()
        .chatResponse();
```

需要注意：

- `ChatClient` 是统一调用入口，不会自动连接所有厂商。
- 每个 `ChatClient` 都需要对应实际的 `ChatModel`。
- 模型适配器负责将统一请求映射成供应商的请求，并将响应转换为 Spring AI 的结构。

### 3.3 Prompt、Message 与 ChatOptions

`Prompt` 用于封装一组 `Message` 和可选的模型参数。

`Message` 代表对话中的消息及其角色，例如：

- `SystemMessage`
- `UserMessage`
- `AssistantMessage`

`ChatOptions` 提供一组可移植的通用参数，例如：

- `model`
- `temperature`
- `maxTokens`
- `topP`
- `topK`
- `frequencyPenalty`
- `presencePenalty`
- `stopSequences`

厂商还可以提供自己的专属 Options。

例如：

```
OpenAiChatOptions
DeepSeekChatOptions
```

它们继承或实现通用选项契约，并提供对应供应商的扩展能力。

关键边界：通用接口只统一了可表达的抽象，不保证每个模型都支持每个参数，也不保证相同参数在不同供应商上具有完全相同的语义。

Spring AI 的运行时参数还需要注意覆盖规则：直接使用 `ChatModel.call(Prompt)` 时，Prompt 中的选项可以整体覆盖模型启动时的选项；使用 `ChatClient` 时，流畅 API 提供按请求调整选项的方式。

### 3.4 ChatResponse 与 Generation

`ChatResponse` 保存模型返回的一个或多个生成结果，以及响应级元数据。

```
ChatResponse
  |
  +-- getResults()
  |     |
  |     +-- Generation
  |     +-- Generation
  |
  +-- getMetadata()
        |
        +-- model
        +-- id
        +-- usage
        +-- rateLimit
```

`Generation` 包含：

- `AssistantMessage`
- `ChatGenerationMetadata`

其中 `ChatGenerationMetadata` 可以提供 `finishReason`。

`ChatResponseMetadata` 可以提供：

- 响应 ID。
- 实际使用的模型。
- Token 用量。
- 限流相关元数据。

因此统一响应 DTO 不应只保留一段字符串，否则可能丢失计量和诊断信息。

## 4. 不同厂商接入与切换模式

### 4.1 模式一：同一厂商切换模型 ID

这是最简单的模型切换方式。

以 DeepSeek 为例，Spring AI 1.1.8 原生适配器提供 `DeepSeekChatOptions`，可以在模型调用时指定模型 ID。

```
DeepSeekChatOptions options = DeepSeekChatOptions.builder()
        .model("deepseek-chat")
        .temperature(0.7)
        .build();

Prompt prompt = new Prompt(
        "请解释 Java 的线程池",
        options
);

ChatResponse response = deepSeekChatModel.call(prompt);
```

切换到另一个模型时，更换对应模型 ID，并根据模型的实际能力调整参数。

注意：模型 ID 是否仍然可用，需要结合执行时 DeepSeek 的官方模型列表核验。Spring AI 适配器支持传递模型参数，并不代表厂商一定提供该模型。

[image](https://www.google.com/s2/favicons?domain=https://docs.spring.io\&sz=32)

Home+1

适用场景： 同一供应商提供多个模型，而应用只需要根据任务选择模型。

### 4.2 模式二：Spring Profile 或配置切换 Provider

如果每个部署环境只使用一个主要模型，可以采用 Profile 和外部配置管理。

示意：

```
application.yml
application-deepseek.yml
application-openai.yml
application-anthropic.yml
```

DeepSeek 配置示例（Spring AI 1.1.8）：

```
spring:
  ai:
    deepseek:
      api-key: ${DEEPSEEK_API_KEY}
      chat:
        options:
          model: deepseek-chat
```

OpenAI 配置示例：

```
spring:
  ai:
    openai:
      api-key: ${OPENAI_API_KEY}
      chat:
        options:
          model: ${OPENAI_MODEL}
```

Anthropic 配置示例：

```
spring:
  ai:
    anthropic:
      api-key: ${ANTHROPIC_API_KEY}
      chat:
        options:
          model: ${ANTHROPIC_MODEL}
```

这些配置示例应结合各自的 Spring AI 1.1.8 属性文档检查实际绑定结果。

切换 Profile 的目的，是让一个部署环境选择一个主模型，并不意味着所有供应商自动配置会同时生效。

重要版本边界： Spring AI 1.1.8 不同 Provider 文档中的自动配置启用属性存在差异。DeepSeek 1.1 文档列出 `spring.ai.deepseek.chat.enabled`，而 OpenAI、Anthropic 文档列出了顶层 `spring.ai.model.chat` 选择属性。不要将一个 Provider 的自动配置开关直接套用到另一个 Provider。应结合对应版本的配置元数据和自动配置条件核实。

### 4.3 模式三：多个 ChatModel 同时存在

适合：

- 应用需要同时调用 DeepSeek 与 Anthropic。
- 同时保留两个不同供应商的模型。
- 需要按照不同业务任务选择模型。

Spring AI 1.1.8 的 ChatClient 文档明确说明，多模型场景需要关闭默认 `ChatClient.Builder` 自动配置：

```
spring:
  ai:
    chat:
      client:
        enabled: false
```

然后根据具体 `ChatModel` 创建各自的 `ChatClient`，并通过 `@Qualifier` 精确注入。

示意：

```
@Configuration
public class MultiModelClientConfig {

    @Bean
    ChatClient deepSeekChatClient(
            DeepSeekChatModel deepSeekChatModel) {

        return ChatClient.create(deepSeekChatModel);
    }

    @Bean
    ChatClient anthropicChatClient(
            AnthropicChatModel anthropicChatModel) {

        return ChatClient.create(anthropicChatModel);
    }
}
```

业务服务：

```
@Service
public class MultiModelService {

    private final ChatClient deepSeekClient;
    private final ChatClient anthropicClient;

    public MultiModelService(
            @Qualifier("deepSeekChatClient")
            ChatClient deepSeekClient,

            @Qualifier("anthropicChatClient")
            ChatClient anthropicClient) {

        this.deepSeekClient = deepSeekClient;
        this.anthropicClient = anthropicClient;
    }

    public String askDeepSeek(String prompt) {
        return deepSeekClient.prompt()
                .user(prompt)
                .call()
                .content();
    }

    public String askAnthropic(String prompt) {
        return anthropicClient.prompt()
                .user(prompt)
                .call()
                .content();
    }
}
```

注意：

1. 以上展示的是多个模型 Bean 与 ChatClient 的组装方式。
2. 两个 `ChatModel` 必须分别真实注册到 Spring 容器，不能因为添加两个 Starter 就认为两个模型一定都已创建成功。
3. 不同 Provider 的自动配置条件和凭证要求需要单独处理。
4. 如果某个模型是手动构造的，应根据其官方 Builder 或 API 创建方式注册 Bean。
5. 不要将 `@Primary` 当成运行时路由方案。它只帮助 Spring 解决某些按类型注入的优先选择问题。
6. 所有同类型 Bean 都应使用明确的 `@Qualifier`，避免注入歧义。

以上多模型配置方式对应 Spring AI 1.1.8 官方 ChatClient 文档。

### 4.4 模式四：OpenAI-compatible 多 Endpoint

Spring AI 1.1.8 的 `OpenAiApi` 与 `OpenAiChatModel` 提供 `mutate()` 方法，可以基于现有配置创建不同的模型实例。

典型场景：

```
OpenAiChatModel
      |
      +-- OpenAI Endpoint
      |
      +-- DeepSeek Endpoint
      |
      +-- 其他兼容 Endpoint
```

Spring AI 官方提供了使用 `mutate()` 为不同 OpenAI-compatible 服务构建模型的示例。

但你的 M2 项目优先使用 DeepSeek 原生适配器：

- 原生 DeepSeek Starter：直接使用 DeepSeek 的模型参数和配置。
- OpenAI-compatible 适配方式：复用 OpenAI API 适配器，适合已经使用统一 OpenAI API 协议的场景。

两种方案不是必须同时采用。除非需要验证兼容性或已有统一 OpenAI 接口架构，否则不必为了同一个 DeepSeek 接口同时维护两套适配。

### 4.5 四种模式的选择

| 需求                            | 推荐方案                                      |
| ------------------------------- | --------------------------------------------- |
| 同厂商更换模型                  | Runtime Options 修改模型 ID                   |
| 不同环境使用不同厂商            | Profile + 外部配置                            |
| 一个应用同时使用不同厂商        | 多个 ChatModel + ChatClient + `@Qualifier`    |
| 多个 OpenAI-compatible Endpoint | `OpenAiApi` / `OpenAiChatModel` 的 `mutate()` |
| 按业务任务动态选择              | Model Router / Registry                       |

## 5. 统一封装架构

### 5.1 是否一定需要自定义 ModelGateway？

不一定。

只有一个模型、一个供应商、调用逻辑简单时，直接注入 `ChatClient` 就足够。

例如：

```
@Service
public class ChatService {

    private final ChatClient chatClient;

    public ChatService(ChatClient.Builder builder) {
        this.chatClient = builder.build();
    }

    public String chat(String prompt) {
        return chatClient.prompt()
                .user(prompt)
                .call()
                .content();
    }
}
```

当以下需求逐渐出现时，再引入统一门面：

- 多厂商同时接入。
- 模型需要按任务切换。
- 需要模型能力检查。
- 需要统一响应结构。
- 需要统一错误分类。
- 需要限制业务层直接使用 Provider 专属 API。

### 5.2 推荐的分层

~~~mermaid
flowchart TD
    A[Controller / Business Service]
    B[ModelGateway 统一调用门面]
    C[Model Router]
    D[Model Registry]
    E[DeepSeek Adapter]
    F[OpenAI Adapter]
    G[Anthropic Adapter]
    H[DeepSeek API]
    I[OpenAI API]
    J[Anthropic API]

    A --> B
    B --> C
    C --> D
    C --> E
    C --> F
    C --> G
    E --> H
    F --> I
    G --> J
~~~



### 5.3 每层职责

| 层次             | 职责                          | 不应承担的责任                   |
| ---------------- | ----------------------------- | -------------------------------- |
| 业务层           | 描述业务任务                  | 不直接处理供应商专属参数         |
| ModelGateway     | 统一调用入口                  | 不承载大量供应商判断逻辑         |
| Model Router     | 根据模型 ID 或任务选择模型    | 不任意相信外部输入的模型名称     |
| Model Registry   | 登记模型及其能力              | 不宣称能力信息自动等于运行时实测 |
| Provider Adapter | 调用对应 ChatModel            | 不决定整个业务流程               |
| 配置层           | 管理 Endpoint、模型 ID 和参数 | 不保存明文真实 API Key           |

### 5.4 统一请求 DTO

建议至少包含：

| 字段                   | 含义                       |
| ---------------------- | -------------------------- |
| `modelId`              | 应用内部允许使用的模型标识 |
| `taskType`             | 业务任务类型               |
| `prompt`               | 用户或业务生成的输入       |
| `requiredCapabilities` | 本次任务需要的能力         |
| `options`              | 经过校验的通用模型参数     |

不要将底层供应商 SDK 的所有参数全部暴露给业务层。

### 5.5 统一响应 DTO

建议保留：

| 字段               | 含义                    |
| ------------------ | ----------------------- |
| `provider`         | 实际服务商              |
| `requestedModelId` | 请求选择的模型          |
| `actualModelId`    | 实际响应中报告的模型    |
| `content`          | 模型文本结果            |
| `promptTokens`     | 输入 Token 数，可能为空 |
| `completionTokens` | 输出 Token 数，可能为空 |
| `finishReason`     | 结束原因，可能为空      |
| `metadata`         | 经筛选的响应元数据      |
| `latencyMs`        | 应用测量的调用时长      |

用量和结束原因可能缺失。禁止用模拟数字填充真实响应字段。

## 6. 模型能力差异与兼容性矩阵

### 6.1 必须区分三个能力层次

1. Spring AI 框架层： 提供什么接口和抽象。
2. Provider Adapter 层： 当前适配器实现了什么能力。
3. 供应商及具体模型层： 当前模型 ID、账号及 API 版本是否真正支持该功能。

例如：

Spring AI 存在 `StreamingChatModel`，并不意味着每一个模型都支持流式输出。

Spring AI 存在通用 `ChatOptions`，并不意味着每个供应商都能处理全部参数。

### 6.2 能力核验表

下表依据 Spring AI 1.1.8 官方 Chat Model 文档及各 Provider 接入文档整理。表中“需验证”不是“不支持”，而是不能仅凭通用接口断言供应商和具体模型一定支持。

| 能力          | 框架层                   | DeepSeek 1.1.8 适配层  | OpenAI / Anthropic 适配层          | 最终核验要求       |
| ------------- | ------------------------ | ---------------------- | ---------------------------------- | ------------------ |
| 同步文本调用  | `ChatModel`              | 支持                   | 支持                               | 核对模型及 API     |
| 流式调用      | `StreamingChatModel`     | 支持                   | 支持                               | 核对具体模型       |
| Tool Calling  | 提供通用工具调用机制     | 有对应 Tool 配置       | 有对应适配                         | 核对供应商 API     |
| 结构化输出    | 提供转换与调用抽象       | 可用性依赖模型及接口   | 依赖原生 JSON 能力或转换方式       | 验证真实输出       |
| JSON Schema   | 存在结构化输出相关机制   | 需按模型/API 验证      | 需按模型/API 验证                  | 检查 Schema 能力   |
| 图片输入      | Message/Media 抽象       | 1.1.8 能力表按文本列示 | OpenAI、Anthropic 文档列出图像能力 | 核对模型版本       |
| PDF 输入      | 需要适配器与模型支持     | 未在本主题验证         | Anthropic 比较表列有 PDF           | 单独核验输入格式   |
| 通用参数      | `ChatOptions`            | 部分支持               | 部分支持                           | 核对参数映射       |
| 厂商专属参数  | 允许扩展                 | `DeepSeekChatOptions`  | 各自 Options                       | 不应暴露为统一字段 |
| Token Usage   | `ChatResponseMetadata`   | 依响应而定             | 依响应而定                         | 检查实际响应元数据 |
| Finish Reason | `ChatGenerationMetadata` | 依响应而定             | 依响应而定                         | 检查实际响应元数据 |

Spring AI 1.1.8 的比较文档列出了各适配器的多模态、工具、流式和 JSON 等能力概览；该表是适配能力的导航，不应替代对 конкрет具体模型和供应商 API 的验证。

### 6.3 为什么不能把所有参数都统一？

例如：

```
ChatOptions
```

提供了可移植参数，但某个供应商可能支持：

- `seed`
- `logitBias`
- 特殊推理模式
- 专用 JSON 格式
- 特殊工具选择参数

这些不一定存在于另一个供应商的 API 中。

因此建议：

- 通用参数：放在统一请求 DTO。
- 特殊参数：由适配器的扩展选项管理。
- 不支持的特殊参数：明确拒绝或忽略，必须有明确策略。
- 不允许静默地将不支持的参数伪装成已经生效。

### 7.8 定义统一调用门面

`ModelInvocationException.java`

```
public class ModelInvocationException extends RuntimeException {

    public ModelInvocationException(String message, Throwable cause) {
        super(message, cause);
    }
}
```

`ModelGateway.java`

```
@Service
public class ModelGateway {

    private final Map<String, ModelProviderAdapter> adapters;

    public ModelGateway(List<ModelProviderAdapter> adapterList) {

        this.adapters = adapterList.stream()
                .collect(Collectors.toUnmodifiableMap(
                        ModelProviderAdapter::modelId,
                        Function.identity()
                ));
    }

    public ModelResponse generate(ModelRequest request) {

        ModelProviderAdapter adapter = adapters.get(request.modelId());

        if (adapter == null) {
            throw new IllegalArgumentException(
                    "不允许使用的模型：" + request.modelId()
            );
        }

        Set<ModelCapability> missing = EnumSet.noneOf(
                ModelCapability.class
        );

        missing.addAll(request.requiredCapabilities());
        missing.removeAll(adapter.capabilities());

        if (!missing.isEmpty()) {
            throw new UnsupportedOperationException(
                    "模型不支持所需能力：" + missing
            );
        }

        try {
            return adapter.generate(request);
        } catch (RuntimeException ex) {
            throw new ModelInvocationException(
                    "模型调用失败：" + adapter.modelId(),
                    ex
            );
        }
    }
}
```

这个示例完成了三个核心工作：

1. 通过 `modelId` 选择 Adapter。
2. 执行模型能力检查。
3. 将具体 Adapter 的运行异常统一映射到应用层异常。

生产环境还需要增加模型白名单配置、任务类型路由、权限验证和明确的模型错误分类。不能让外部调用者通过任意提交 Endpoint 或 API Key 控制底层模型服务。

### 8.1 DeepSeek Adapter 示例

```
@Component
public class DeepSeekSpringAiAdapter {
```

- `ChatClient` 提供统一的流畅调用 API。

### 8.2 保存有用的响应元数据

```
ChatResponse response = chatClient.prompt()

        .call()

```

## 9. 模型路由、备用模型与风险

### 9.1 四种路由策略

| 路由方式           | 示例                                    | 主要依据       |
| ------------------ | --------------------------------------- | -------------- |
| 按配置固定模型     | 当前环境使用 DeepSeek                   | 部署配置       |
| 按业务任务         | 简单问答使用 Fast，复杂分析使用 Quality | 任务类型       |
| 按模型能力         | 结构化输出任务选择支持对应能力的模型    | 能力注册表     |
| 按成本、质量或延迟 | 从满足最低要求的模型中选择              | 评估数据和策略 |

### 9.2 推荐的路由原则

不要让 Controller 和各个业务 Service 到处编写：

```
if (provider.equals("deepseek")) {
    // ...
} else if (provider.equals("openai")) {
    // ...
}
```

应由统一路由层管理。

同时应遵守：

1. 使用内部模型别名，例如 `fast-chat`、`quality-chat`。
2. 真实 Provider、Endpoint 和凭证由服务端配置。
3. 外部调用方不能任意指定模型 Endpoint 或供应商 API Key。
4. 模型选择必须受到白名单控制。
5. 不满足能力要求的模型不能被选中。
6. 切换模型需要重新检查参数、响应结构和业务正确性。

### 9.3 备用模型不能只按可用性选择

例如：

```
主要模型：支持结构化输出
备用模型：只保证普通文本生成
```

如果业务要求模型必须返回可以解析的结构化对象，那么即使备用模型正常可用，也不应盲目切换。

需要先确认备用模型满足：

- 输入协议要求。
- 输出格式要求。
- 工具调用要求（如果有）。
- 流式要求（如果有）。
- 业务结果质量要求。

模型切换可能改变输出格式、Token 用量、响应延迟和内容质量，因此需要契约测试及模型评估数据。

本章只定义路由与能力边界，不展开完整重试、熔断和降级实现。

## 10. 常见误区与排查

| 常见误区                                  | 正确理解                                              |
| ----------------------------------------- | ----------------------------------------------------- |
| `ChatClient` 可以自动连接任意厂商         | 它依赖具体 `ChatModel`                                |
| 所有模型都支持相同参数                    | 通用参数和厂商专属参数需要区分                        |
| 添加多个 Starter 就一定能同时使用多个模型 | 还必须处理自动配置、Bean 创建和注入选择               |
| `@Primary` 就能实现模型路由               | 它解决默认注入优先级，不是动态路由                    |
| OpenAI-compatible 就是完全兼容            | 只代表特定接口协议或部分能力兼容                      |
| 切换模型只需要改 Model ID                 | 还要验证模型能力、参数及响应格式                      |
| 模型返回字符串就是完整结果                | `ChatResponse` 可能还有 Usage、Finish Reason 等元数据 |
| 通用接口可以自动发现所有模型能力          | 能力注册与验证需要应用自己管理                        |
| 有备用模型就能无条件故障切换              | 备用模型必须满足当前任务的最低能力                    |
| Mock 能调用成功就代表供应商 API 可用      | Mock 只证明应用层路由和封装符合设计                   |

### 10.1 常见问题排查

问题一：注入 ChatModel 时出现 Bean 歧义。

检查：

- 当前有多少个 `ChatModel` Bean。
- 是否使用 `@Qualifier`。
- 是否存在自动配置的默认 `ChatClient.Builder`。
- 是否需要关闭 `spring.ai.chat.client.enabled`。
- 手动创建的 `ChatModel` 是否已经正确注册。

问题二：添加多个 Starter 后应用不能启动。

不要直接假设是 API Key 错误。依次检查：

1. Starter 是否与 Spring AI BOM 版本一致。
2. 自动配置的条件属性。
3. 当前有哪些模型 Bean。
4. 是否重复创建了同名 Bean。
5. 是否存在必须提供的模型连接配置。
6. `ConditionEvaluationReport` 和启动异常。

问题三：切换模型后参数报错。

重点检查：

- 是否误把一个 Provider 的 Options 用于另一个 Provider。
- 是否传递了不被目标模型支持的参数。
- 模型 ID 是否正确。
- 目标供应商是否支持该参数。
- 该参数是否需要特殊 API 版本或 Endpoint。

问题四：备用模型返回结果与主要模型不一致。

检查：

- 两个模型是否都满足任务最低能力。
- 是否使用相同输出格式要求。
- 是否需要重新校验结构化输出。
- 是否存在模型专属参数差异。
- 是否有对应的模型评估和回归测试。

## 11. 核心知识自测

问题 1：ChatModel 和 ChatClient 有什么区别？

答：ChatModel 是模型调用抽象，负责与具体模型适配器交互；ChatClient 是面向应用层的流畅调用 API，帮助构造 Prompt 并调用底层模型。

问题 2：Spring AI 的统一抽象为什么不能保证所有模型能力一致？

答：统一抽象解决的是调用方式和通用数据结构，不同厂商的 API、模型能力、参数含义和服务端限制仍然存在差异。

问题 3：同一个 DeepSeek Provider 如何切换模型？

答：在同一个 DeepSeek 适配器下，使用与 Spring AI 1.1.8 匹配的 `DeepSeekChatOptions` 设置目标 Model ID。

问题 4：一个应用需要同时使用 DeepSeek 和 Anthropic，应如何设计？

答：分别提供对应 `ChatModel`，根据 Spring AI 1.1.8 的多模型配置要求创建不同的 `ChatClient`，并使用 `@Qualifier` 明确注入。

问题 5：为什么要增加 ModelGateway？

答：当应用需要多供应商、模型选择、能力检查和统一结果处理时，使用统一门面可以减少业务层对供应商实现的直接依赖。

问题 6：模型能力应该如何管理？

答：建立应用自己的能力登记表，记录框架抽象支持、适配器支持及具体模型经过验证的能力，不能仅凭模型名称推断。

问题 7：为什么不应该让 Controller 任意传入 Base URL？

答：这会让外部输入影响服务端模型连接目标，产生越权访问、密钥滥用和 SSRF 等风险。Endpoint 和凭证应由服务端配置。

问题 8：响应 DTO 为什么不能只包含 content？

答：因为还可能需要记录实际模型、Provider、调用 ID、Token 用量、结束原因等信息，支持成本统计和问题诊断。

问题 9：使用 OpenAI-compatible Endpoint 有什么风险？

答：目标服务可能只兼容部分请求格式，某些参数、工具调用、结构化输出和流式协议仍然存在差异。

问题 10：什么情况下值得引入模型路由？

答：当多个任务存在明显不同的模型能力、成本或延迟要求，并且已有可验证的模型能力登记及选型规则时，才值得增加动态路由。

- 能准确解释 Provider、Model ID、Endpoint、API Protocol 和 Adapter。
- 能解释 ChatModel 与 ChatClient 的职责。
- 能说明 Prompt、Message、ChatOptions 和 ChatResponse 的关系。
- 能通过 Runtime Options 切换同一 Provider 的模型。
- 能通过 Profile 管理不同运行环境的模型配置。
- 理解 Spring AI 1.1.8 多模型 Bean 配置及注入边界。
- 能说明 DeepSeek 原生 Starter 与 OpenAI-compatible 接入的区别。
- 能设计 Provider Adapter、ModelGateway 和 Model Registry。
- 能保留响应元数据及 Token Usage，不伪造用量。
- 能管理模型能力差异并拒绝不满足任务要求的模型。
- 能完成两个 Mock Provider 的模型切换及测试。
- 能说明模型路由和备用模型选择的风险。

本章最终能力标准： 能够从单模型调用出发，独立设计一个使用 Spring AI 统一抽象、支持多模型适配和运行时选择的 Java 应用，并清楚解释统一接口与供应商专属能力之间的边界。
