## 四、必须覆盖的七个知识部分

### 1. Spring AI 自动配置

必须讲清：
- Starter、底层模块依赖、Spring AI BOM 的职责与关系；依赖传递和版本对齐。
- Spring Boot AutoConfiguration 的加载机制、自动配置导入元数据、条件装配与 Bean 创建流程。
- `@ConditionalOnClass`、`@ConditionalOnMissingBean`、`@ConditionalOnProperty` 等常见条件的作用；仅在项目或对应版本实际使用时展开具体配置类。
- Model Starter 如何创建厂商 ChatModel、配置属性如何绑定、自动配置如何创建 `ChatClient.Builder`。
- 用户自定义 Bean、`@Primary`、`@Qualifier`、自动配置回退/覆盖、排除自动配置的适用场景。
- 如何诊断 Bean 缺失、Bean 冲突、条件不匹配、配置未生效：依赖树、启动日志、条件评估报告和测试上下文。

### 2. ChatClient 与 ChatModel

必须讲清：
- `ChatModel` 是模型调用抽象；`ChatClient` 是面向应用的 Fluent API 门面。各自职责、适用层次及不能混为一谈的地方。
- `ChatClient.Builder`、`ChatClient`、`Prompt`、`ChatResponse`、`Generation`、`AssistantMessage` 等关键对象关系；只列出目标版本确实存在的 API。
- 一次调用链路：业务入口 → ChatClient 构建请求 → Advisor 链（若有）→ ChatModel → 厂商客户端/HTTP → ChatResponse → 内容或实体转换 → 业务响应。
- `call()` 与 `stream()` 的区别、终端操作触发执行的时机、`content()` / `chatResponse()` / `entity()` 等返回方式及适用边界。
- 多模型、多 ChatClient 的 Bean 组织、默认 Builder 自动配置与自定义 Builder 的冲突处理。
- 对照项目真实调用代码画出时序图或流程图，指出每层职责和异常传播位置。

### 3. Prompt 与消息构建

必须讲清：
- `Prompt`、`Message`、System / User / Assistant / Tool 消息角色与完整请求结构。
- `PromptTemplate`、`TemplateRenderer`、变量占位符、运行时变量注入、模板渲染时机；说明默认模板语法与 JSON 花括号等特殊字符冲突的处理方法。
- `ChatOptions` 通用选项与厂商专属 Options 的关系；模型名、temperature、max tokens 等选项的适用性和厂商差异。
- 默认选项、模板参数、请求级选项的覆盖规则；不得凭经验猜测优先级，必须按 1.1.x API 和项目代码验证。
- Prompt 模板集中管理、版本与场景隔离的工程实践；避免在业务方法中散落硬编码 Prompt。
- 提示词注入风险、用户输入与系统指令边界、变量白名单及敏感数据最小化。

### 4. 对话记忆与历史管理

必须讲清：
- LLM 请求的无状态特征；多轮对话为何需要由应用重新提供上下文。
- `ChatMemory`、`ChatMemoryRepository`、`MessageWindowChatMemory` 的职责关系；短期记忆、长期记忆和完整聊天历史的边界。
- `MessageChatMemoryAdvisor` 等 Advisor 如何读取历史、构造 Prompt、保存消息；Advisor 执行顺序和参数传递。
- `ChatMemory.CONVERSATION_ID` 的使用要求；会话 ID 的生成、用户隔离、越权访问防护和生命周期。
- 消息窗口按消息数管理不等于 Token 上下文窗口；窗口淘汰、SystemMessage 保留、工具调用消息及上下文预算问题应按 1.1.x 实际实现说明。
- 内存存储与 JDBC/Redis 等持久化实现的选择；区分记忆窗口与完整会话历史/审计记录，不重复建设存储能力。
- 结合项目说明实际采用的 Repository、Advisor、会话存储与数据隔离方案；未采用的实现仅做简要选型说明。

### 5. 结构化输出

必须讲清：
- 普通文本、JSON、JSON Schema、Provider 原生结构化输出之间的区别及保证边界。
- `StructuredOutputConverter`、`BeanOutputConverter`、`MapOutputConverter`、`ListOutputConverter` 等 API 的实际用途；仅介绍 1.1.x 存在且适用的类。
- `ChatClient.entity()`、`responseEntity()` 与低层 Converter 的转换链路；Record / POJO、嵌套对象、集合、枚举、空值和泛型映射。
- JSON 语法解析、Schema 校验、Jackson 反序列化、Bean Validation、业务语义校验是不同层次，不能相互替代。
- 模型输出不可靠：字段缺失/多余、类型错误、枚举越界、格式包裹文本、截断和拒绝响应的处理。
- 有限自修正/重试的触发条件、次数、成本和失败收口；不得无限重试。
- 结构化候选结果必须经过业务校验和授权后才能触发写库、工单或其他副作用；模型输出不能直接成为可信业务事实。

### 6. SSE 流式响应

必须讲清：
- Spring AI `stream()` 与 Reactor `Flux` 的关系；响应数据如何从模型流转换为应用层事件。
- SSE 协议的 `Content-Type: text/event-stream`、`data`、`event`、`id`、`retry`、空行分隔、UTF-8、心跳和重连机制。
- 区分模型流分片、HTTP 网络分片、SSE 事件和模型 Token；它们不保证一一对应。
- Spring WebFlux `Flux<ServerSentEvent<?>>` 与 Spring MVC `SseEmitter` 的差别、线程/请求生命周期和选型边界；不得把 `SseEmitter` 说成 Spring AI 的返回类型。
- 建立连接、首包、持续推送、正常完成、服务端异常、超时、取消和客户端断开的完整生命周期。
- 背压、缓冲、慢客户端、取消传播、资源释放、连接超时/读取超时及代理层缓冲问题。
- 事件协议设计：开始、内容增量、完成、业务错误等事件；错误发生后如何结束流，如何避免既发送部分内容又伪装为完整成功。
- 对照项目现有 SSE Controller / Service / 前端消费实现，解释真实事件格式、错误处理和断连清理。

### 7. 失败策略与可靠性

必须讲清：
- 鉴权失败、权限/参数错误、限流、网络错误、连接/读取超时、服务端 5xx、模型拒绝、结构化解析失败、客户端取消等错误分类。
- 哪些错误可重试、哪些不应重试；最大尝试次数、指数退避、随机抖动、`Retry-After`、总 Deadline 和重试预算。
- Spring AI `spring.ai.retry.*` 属性在实际 1.1.x Provider Starter 中的支持范围、准确属性名和默认值；不得把模型调用重试误认为底层 HTTP 连接/读取超时配置。
- HTTP 客户端超时、Spring AI Retry、Resilience4j Retry / RateLimiter / CircuitBreaker / Bulkhead / TimeLimiter 的职责边界；避免多层重试叠加放大请求。
- 降级策略：受控提示、缓存/只读备用能力、人工处理或明确失败；不得将错误结果伪装成模型成功回答。
- 幂等与副作用：Tool Calling、工单创建等操作的重复提交风险；部分 SSE 内容发出后不能简单从头重试并重复输出。
- 统一异常映射、失败状态收口、日志与指标关联、用户可理解错误信息。
