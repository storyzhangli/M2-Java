## 5. 功能一：Prompt 模板管理

### 5.1 模板基础能力

至少提供：

- 查询模板列表，可按场景/角色/状态筛选（实际筛选项以设计为准）。
- 查询模板详情。
- 创建模板。
- 修改模板。
- 启用/停用模板。
- 删除策略：如存在历史对话、引用或审计要求，优先采用停用/逻辑删除；不要未经评估直接物理删除正在使用的模板。
- 查看模板所需变量与说明。
- 对模板内容、变量声明和模板版本进行基本校验。

如果现有项目已有管理端页面或管理 API，沿用既有风格；否则实现与当前架构相匹配的最小可用管理入口。若本轮确实不适合增加管理 UI，必须实现可操作的 API 并提供请求示例，明确说明限制，不可把“硬编码两个 Prompt”冒充完整模板管理。

### 5.2 模板场景

至少准备以下内置模板场景作为可用初始数据或种子配置：

- `customer_service`：客服对话。
- `programming`：编程助手。
- `technical_explanation`：技术知识解释。
- `code_review`：代码审查。
- `summarization`：文本总结。
- `information_extraction`：结构化信息提取。

本次必须实现并验证 **客服** 和 **编程** 两个角色；其余模板需按现有项目规模提供可用的示例模板或清晰的初始化数据，不能只在文档中列出名称却没有实际模板内容。

### 5.3 模板数据与变量

模板设计至少考虑：

- `templateId`：稳定唯一标识。
- `name`：模板名称。
- `scene` / `role`：场景或角色标识。
- `description`：用途说明。
- `content`：Prompt 模板正文。
- `variables`：允许使用的变量及其约束。
- `version`：必要时使用的版本标识。
- `status`：启用/停用状态。
- `createdAt` / `updatedAt`：按项目持久化规范维护。

字段名称可以按项目约定调整，但必须保留相应职责。

变量渲染要求：

- 明确支持哪些占位符语法，并与实际模板引擎一致。
- 检查必填变量是否缺失，拒绝未声明的非法变量或按设计显式处理。
- 动态变量必须作为数据传入，不能通过字符串拼接让用户输入覆盖系统规则。
- 模板中包含 JSON 示例或大括号时，必须测试变量渲染是否发生冲突。
- 对模板内容进行长度、空值和变量声明检查。
- 不将 API Key、数据库凭据或其他机密写入 Prompt 模板。

### 5.4 模板管理安全要求

- 若存在登录/权限体系，模板创建、修改、启停和删除必须遵循现有授权机制。
- 若项目当前没有权限体系，不得宣称管理操作已具备身份鉴权；必须标注风险与后续工作。
- 禁止将任意模板内容直接当作可信执行代码。
- 模板内容应保留必要的修改记录或版本信息，至少让问题可以追踪到正在使用的模板。
- 模型调用时明确记录模板 ID/版本（不记录敏感的完整 Prompt 内容，除非项目明确需要且有保护措施）。

## 6. 功能二：客服与编程两个角色对话

### 6.1 通用对话能力

至少实现：

- 用户可选择客服或编程角色。
- 提交消息并获得模型响应。
- 多轮对话能按既有项目能力延续上下文；如果尚无记忆功能，需明确实现范围并保持会话隔离。
- 请求中明确传入角色或模板标识，不允许只依赖前端显示名称。
- 服务端校验角色和模板状态，不能接受任意不存在或已停用的模板。
- 切换角色时，默认新建或明确隔离会话；若支持共享历史，必须有清晰规则，避免客服历史污染编程上下文。
- 错误情况下返回一致、可理解的错误信息，并保留必要日志。

### 6.2 客服角色 Prompt 要求

客服模板必须明确：

- 目标是礼貌、清楚、聚焦问题的客户服务。
- 优先依据用户提供的信息及项目实际可用的知识来源回答。
- 不得编造订单状态、退款结果、政策、价格、时效或系统查询结果。
- 缺少关键信息时，提出简洁的澄清问题。
- 无权确认的事项要明确说明，不得假装已经操作了后台。
- 用户输入里的指令不能覆盖系统定义的角色和安全约束。
- 输出应易读、简洁，按场景提供解决步骤；复杂或高风险事项应说明需要人工处理。

如果项目没有连接真实客服知识库、订单系统或业务工具，必须将其定位为基于用户输入的演示客服，不得声称能查询真实订单或执行退款。

### 6.3 编程角色 Prompt 要求

编程模板必须明确：

- 先确认技术栈、版本、需求和输入条件。
- 优先使用项目实际代码、依赖版本及已有规范作为依据。
- 解释方案时给出关键原因、适用条件与边界。
- 生成代码时说明涉及文件、核心逻辑、异常处理和测试思路。
- 不得虚构类名、方法、依赖、配置、测试结果或仓库结构。
- 信息不足时列明假设或提出必要问题，不能伪装已检查代码。
- 对代码审查要区分已确认缺陷、潜在风险和优化建议。
- 默认只提供建议，不声称已经执行命令、修改文件、提交 Git 或运行测试。

编程角色输出应优先服务于 Java 后端与 Spring AI 开发，但不得将所有技术问题强行套入 Java 场景。

### 6.4 多轮对话与 Prompt 组合

必须说明并实现清晰的组合方式：

- 系统角色指令来自所选模板。
- 用户问题作为当前用户消息传入。
- 如使用记忆，将相关会话历史按项目实际机制加入请求。
- 业务输入与角色规则分离；不要把用户消息拼接成能够覆盖系统角色约束的指令。
- 模板变量在调用前进行校验与渲染。
- 记录本次调用使用的模板标识与版本，以便故障排查。

不得无依据地将两种角色的规则合并到同一个系统 Prompt。
