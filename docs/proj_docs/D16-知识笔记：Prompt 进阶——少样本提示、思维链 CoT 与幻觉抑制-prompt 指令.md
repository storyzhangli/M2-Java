### 4. 幻觉及其产生原因

必须解释：

- 幻觉的定义，以及为什么流畅、完整、自信的表达不代表事实真实。
- 事实幻觉、引用幻觉、数字与计算错误、代码/API 幻觉、上下文误读和过度确定性。
- 输入缺失、错误前提、模型知识限制、上下文冲突、错误检索及错误推断等风险来源。
- 为什么幻觉并不等于模型“故意撒谎”。
- 为什么仅通过一句“禁止产生幻觉”无法保证回答正确。

使用适当的例子说明不同幻觉的表现、影响及诊断方法。

### 5. 幻觉抑制的分层策略

必须按以下层次讲解，明确每层解决的问题和剩余风险。

**Prompt 层：**

- 明确回答范围与可信信息来源。
- 要求区分已知事实、推断和未知。
- 资料不足时允许回答无法确认或请求补充信息。
- 禁止虚构数据、引用、URL、API 和未经证实的结论。
- 对关键结论要求给出可核查的依据。

**证据层：**

- 解释 Grounding 的基本机制。
- 建立“主张—证据—判断状态”的对应关系。
- 区分直接证据、间接依据、合理推断和无依据陈述。
- 说明为什么来源真实不代表来源支持对应结论。

**检索与工具层：**

- 简述 RAG 提供外部证据的机制。
- 分析检索遗漏、不相关材料、过时资料和错误引用的风险。
- 说明哪些任务适合交给数据库、HTTP API、Java 计算或其他外部工具。
- 不要求实现完整 RAG，只需建立与当前主题相关的原理认知。

**输出与程序校验层：**

- 通过结构化输出规范事实、推断、未知状态及必要字段。
- 使用 Java 代码校验字段、枚举、数值和业务规则。
- 说明 JSON 合法不代表事实正确。
- 说明模型自我检查不能代替外部证据或程序验证。

**评估层：**

- 通过固定测试集、引用检查、结果抽检和错误分类持续监控质量。
- 说明人工复核在高风险业务中的作用。

必须明确：幻觉抑制只能降低风险，不能保证彻底消除幻觉。

### 6. 三种技术的组合应用

必须解释 Few-shot、CoT/分步指令和幻觉抑制如何协同：

- Few-shot：示范任务规则、分类方式和未知状态处理。
- 分步指令：规定任务处理顺序和检查条件。
- Grounding：提供真实可查的证据。
- 结构化输出：组织结果。
- 程序校验：检查确定性约束。
- 外部检索或工具：提供必要的实时数据或真实业务结果。

提供一个完整组合案例，明确每个组件解决的问题，不能将模型生成的推理文字本身当作证据。

## 七、常见问题诊断

采用“现象—可能原因—核查证据—解决方向”的结构，至少覆盖：

- 增加示例后结果反而变差。
- 模型复制示例数据。
- 示例标签或规则互相矛盾。
- CoT 输出很长但答案错误。
- 模型生成了详细理由，却没有支持结论的证据。
- 资料缺失时依旧给出确定答案。
- 虚构论文、引用、URL 或技术 API。
- 检索到了相关材料，但回答仍不准确。
- JSON 结构合法，业务内容却错误。
- 增加示例、多次采样或多阶段调用后，成本上升但质量未改善。

不能把“继续增加 Prompt 长度”“强制模型多想几步”作为不经分析的通用方案。
