## 2. 技术基线与设计原则

默认基线：JDK 21、Spring Boot 3.5.16、Spring AI 1.1.8、Maven 3.9.16；实际依赖以 POM 为准。不得擅自升级、降级或引入第二套 AI 框架。

**必须先核实 Spring AI 1.1.8 的实际 API、Starter 自动配置及配置属性。** 当前 DeepSeek 专用 Starter 的配置前缀属于供应商配置，不等同于项目自己的通用配置。若新增 `app.ai.*` 配置，必须设计清楚它如何映射到实际 `ChatModel`/`ChatClient` Bean；不能只在 YAML 中定义属性，却未真正接入模型构造或自动配置。

设计约束：
1. 配置至少覆盖 `mode`、`model`、`base-url`、`api-key`；如项目确有供应商切换需求，可增加 `provider`，但不得无需求扩展成复杂多供应商平台。
2. 建议使用项目自己的配置命名空间（如 `app.ai.*`）承载应用级配置；是否保留 Spring AI `spring.ai.deepseek.*` 原生属性，由现有自动配置方式决定。禁止两套配置同时存在且优先级不清。
3. API Key 只从环境变量或现有安全配置机制注入。配置示例可用空值占位，不得写入真实 Key、伪造 Key 或将 Key 打入日志/Git。
4. Mock 模式不发起真实模型请求；真实模式在配置缺失时明确失败，不得静默回退到 Mock。
5. 服务公开契约使用项目内部 Request/Result/Options 等类型；DeepSeek 专有类型只能出现在供应商适配器/配置边界内。优先复用现有 Service、DTO 和 AI 调用入口，不为分层而重复造接口。
6. 允许应用层使用 Spring AI 的通用抽象（如 `ChatClient`、`ChatModel`、`ChatOptions`）的前提是它们不造成供应商耦合；若现有服务接口需要独立于 Spring AI，则在适配边界转换为项目内部类型。设计前说明取舍。
7. 不承诺本次已支持其他厂商。目标是隔离 DeepSeek 细节，使未来增加供应商时不必修改 Controller 和业务服务接口。
8. 保持已有同步和流式接口、历史消息、异常映射、超时/有限重试、TraceId、脱敏记录及 usage 统计行为；只在必要位置改造。

- Chat Client API | 聊天客户端 API：[https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html](https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html)
- DeepSeek Chat | DeepSeek 对话模型：[https://docs.spring.io/spring-ai/reference/1.1/api/chat/deepseek-chat.html](https://docs.spring.io/spring-ai/reference/1.1/api/chat/deepseek-chat.html)（若版本化页面不可用，使用 1.1.8 对应源码/Javadoc/发布标签核对）

## 4. 需求分析与实施要求

先输出简短现状摘要：当前模型 Bean 如何创建、配置从哪里读取、DeepSeek 类型出现在哪些层、同步/流式接口依赖哪些服务、现有 Mock 是否存在。逐项标注证据路径，不确定内容标记“未确认”。随后给出最小修改清单。

### 4.1 配置外置

- 定义清晰的应用级配置契约：模式、模型名、Base URL、API Key；Provider 标识仅在实际需要时纳入。
- 推荐环境变量名保持统一，例如 `AI_MODE`、`AI_MODEL`、`AI_BASE_URL`、`AI_API_KEY`；最终名称必须与当前项目规范一致，并写入配置示例和 README。
- Mock 模式允许缺少 Key；真实模式必须校验 Key、模型名和 Base URL。配置错误应尽早、清楚地暴露，但错误信息不能输出 Key。
- 明确配置优先级、默认值、Profile 覆盖方式及运行时是否允许热切换。未实现热切换时，不得声称可动态切换；优先采用应用启动时绑定配置。
- Base URL 只允许从受信任配置源读取，不接受用户请求动态指定；校验 URI 格式，避免将配置变成 SSRF 入口。
- 不把 API Key 提交到 YAML、IDEA 运行配置文件、`.env`、测试快照或日志。`.env` 不会自动被 Spring Boot 读取，除非项目已有明确加载机制。

### 4.2 供应商隔离

- Controller 和应用服务的公开方法签名不得出现 `DeepSeek*`、DeepSeek API/DTO/Options/Response 等供应商专有类型。
- 在供应商适配边界完成项目内部请求/选项与 Spring AI/DeepSeek 类型的转换；供应商响应转换为项目内部统一结果。
- 供应商专有依赖和配置集中在适配层/配置层，不向业务层扩散。
- 优先使用已有 ChatClient/ChatModel 和现有服务接口；只有现有结构无法隔离时才新增必要的 Port/Adapter，不批量重构。
- 对同步与流式分别确认适配接口能表达所需行为；流式类型是否使用 `Flux<String>` 或内部事件模型，以现有 API 协议为准。
- 为未来适配其他供应商保留扩展点，但本次不强制实现第二家 Provider，不为了假想扩展引入工厂注册中心或插件体系。

### 4.3 兼容与复用

- 现有 HTTP 路径、请求/响应结构、错误码、同步/流式语义和会话行为保持不变；任何必要变化先说明并给兼容方案。
- 复用已有超时、有限重试、异常映射、TraceId、脱敏日志、延迟和 usage 统计；避免重复计时、重复日志、重复重试或丢失 metadata。
- Mock 与真实 Provider 使用相同的内部服务契约，确保业务逻辑不需知道当前模式。

## 5. 必须执行的测试

测试必须由本地构建/测试工具真实执行。完整日志写入 `logs\D22`；模型默认只读取摘要、失败用例、首个根因异常及必要堆栈。只有诊断确有需要时才读取指定日志片段。

至少覆盖：
1. 默认 Mock 模式在无 API Key 时启动并返回 Mock 结果，且不发出外部请求。
2. 真实模式配置绑定正确；Key 缺失、空白、非法 URL、未知模式等配置错误有明确结果。
3. 修改模型名/Base URL/Key 只需修改外部配置，不修改 Controller/应用 Service 代码。
4. 服务公开接口、Controller、应用 DTO 不引用 DeepSeek 专有类型；用源码引用扫描/架构测试验证。
5. DeepSeek 专有类型仅存在于受控适配/配置边界；如发现例外，列明理由。
6. 同步与流式路径均可通过相同内部契约完成调用；原有接口回归通过。
7. Provider 异常、超时、重试、TraceId、脱敏记录及可获得 usage 行为没有回归。
8. 配置文件、测试报告、日志、Git diff 无真实密钥或敏感信息。
9. Spring 上下文、构建和本轮相关单元/集成测试执行成功；真实 API 烟雾测试若因无凭据未执行，明确标记“未验证”，不得影响 Mock 测试结果表述。

禁止删测试、降断言、忽略失败或伪造测试结果。
