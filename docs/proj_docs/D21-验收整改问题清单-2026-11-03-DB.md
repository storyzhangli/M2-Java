## 三、项目问题清单

### P1-01：HTTP/AOP 访问日志仍会记录用户原文和模型响应正文

**证据位置**

- `D21/D21_TOKEN_ID_LOGS/src/main/java/com/zl/d21/logging/AccessLogProperties.java`
- `D21/D21_TOKEN_ID_LOGS/src/main/java/com/zl/d21/logging/LogMaskingUtils.java`
- `D21/D21_TOKEN_ID_LOGS/src/main/java/com/zl/d21/logging/CachedBodyAccessLogFilter.java`
- `D21/D21_TOKEN_ID_LOGS/src/main/java/com/zl/d21/logging/ControllerAccessLogAspect.java`
- `D21/D21_TOKEN_ID_LOGS/src/main/resources/application.yml`

**问题事实**

1. `includeRequestBody`、`includeResponseBody`、`includeMethodArgs` 默认均为 `true`。
2. 默认敏感字段列表包含 `token`、`secret`、`password` 等，但没有覆盖聊天正文的 `message`、`content`、`prompt`、`input`、`output`、`reasoning` 等字段。
3. `CachedBodyAccessLogFilter` 会对请求体和响应体调用 `prepareJsonBody()`；字段名未命中敏感列表时，原值会保留。
4. `ControllerAccessLogAspect` 会记录 Controller 方法参数和返回对象；`ChatRequest.message` 与响应对象的 `content` 因字段名不匹配而不会被当前关键字规则遮盖。
5. 异常路径还会将 `ex.getMessage()` 写入 `errorMessage`，异常消息可能包含上游响应片段、URL 或其他不应进入日志的信息。

因此，新增的 `MODEL_CALL` 白名单日志虽然没有 Prompt/Completion 字段，但不能抵消 `ACCESS_LOG` 中已有的原文记录风险。提交内保存的测试输出也能看到 `HTTP_REQUEST`、`HTTP_RESPONSE`、`CONTROLLER_ACCESS` 日志记录了请求体/响应对象。`D21-sensitive-scan.txt` 只证明扫描到的源码命中是占位符/配置/脱敏逻辑，并不能证明运行日志没有用户内容或模型输出。

**整改要求**

- 默认关闭聊天接口请求体、响应体和 Controller 参数/返回对象正文日志；优先使用路径级排除或专门的安全日志策略，不要只扩大黑名单。
- 访问日志只保留明确白名单元数据，例如 requestId、方法、路由模板、状态码、耗时、请求/响应大小；不要保留原始 message/content。
- 异常日志只记录归一化错误码、异常类型和安全上下文；不要直接记录未经净化的异常消息。
- 新增日志安全测试，使用唯一合成标记分别注入用户消息、模型输出、Prompt、API Key、Authorization、Cookie 和异常消息，断言 `ACCESS_LOG`、`MODEL_CALL`、控制台/文件日志中均不存在这些标记。
- 对 SSE 路径继续保持不缓存正文的约束，并测试异步完成/异常/取消场景。

**验收标准**：日志扫描和自动化断言能够证明原文、密钥与敏感异常内容不会出现在任何默认日志通道中，而不只是证明 `MODEL_CALL` DTO 没有这些字段。

### P2-01：将 requestId 复制到 traceId 字段，语义上不是分布式 Trace

**证据位置**

- `D21/D21_TOKEN_ID_LOGS/src/main/java/com/zl/d21/logging/TraceIdFilter.java`
- `D21/D21_TOKEN_ID_LOGS/src/main/java/com/zl/d21/observability/ModelCallObservation.java`
- `D21/D21_TOKEN_ID_LOGS/src/main/java/com/zl/d21/observability/ModelCallRecord.java`
- `docs/evidence/D21/D21-iteration-state.md`

`ModelCallObservation` 将 `capturedRequestId` 同时赋给 `requestId` 和 `traceId`；项目没有启用真正的 Micrometer Tracing / OpenTelemetry Tracer，也没有 Span 创建与父子关系。状态文档虽说明“当前同值、预留分离”，但日志字段 `traceId` 仍容易让使用者误以为这是分布式链路 Trace ID。

**整改要求**

- 若本轮仅做请求关联 ID，保留 `requestId` 或 `correlationId`，`traceId`/`spanId` 在没有 Tracer 时应为 `null`/缺省。
- 只有实际接入 Tracer 并验证跨服务上下文传播、Span 创建和日志关联后，才记录真正的 traceId/spanId。
- 不需要为了本轮强制引入完整观测平台；关键是字段语义真实，文档不能将 Request ID 等同于 Trace。
- 更新测试，不应再断言 `traceId == requestId` 是通用正确行为。

**验收标准**：字段命名、实现、示例日志、知识笔记及费曼口述统一表达 requestId、correlationId、traceId、spanId 的边界。

### P2-02：入站 requestId 没有最大长度限制

**证据位置**：`logging/LogMaskingUtils.java` 的 `sanitizeInboundRequestId()`。

当前实现只执行 `trim()` 和删除非 `[A-Za-z0-9_-]` 字符，没有执行最大长度校验；D21 知识笔记示例却使用 `[A-Za-z0-9._-]{1,64}`。`TraceIdHttpTest` 覆盖了非法字符与生成逻辑，但没有覆盖超长 Header。超长值仍可能进入 MDC、响应头和日志，增加日志体积与资源消耗风险。

**整改要求**

- 定义明确最大长度（例如 64 字符，按项目规范确认），先校验原始长度与格式；超限应拒绝或重新生成，不要无限制地清洗保留。
- 新增空值、超长、CR/LF、特殊字符清洗后为空、合法 ID 的边界测试。
- 更新知识笔记代码示例，使其与真实实现一致。

### P2-03：默认 Mock 运行没有经过 ModelCallRecorder，端到端证据不足

**证据位置**

- `service/MockAiChatService.java`：没有注入或调用 `ModelCallRecorder`。
- `service/DeepSeekAiChatService.java`：真实 DeepSeek 同步/流式路径已接入观测收口。
- `docs/evidence/D21/D21-iteration-state.md`：明确说明真机 Mock 运行期没有 `MODEL_CALL` 行，MODEL_CALL 仅由单元测试 ListAppender 断言。
- `docs/evidence/D21/D21-real-sync-body.json`、`D21-real-stream.sse`：运行结果明确是 `mode=mock`。

当前 68 项测试记录证明组件级测试和既有接口 Mock 回归通过，但不能证明“HTTP 请求 → 服务层 → 模型调用 → MODEL_CALL 终态日志”这条集成链路已经跑通；真实 DeepSeek 也未联网验证。

**整改要求**

- 不调用真实外网的前提下，增加基于可控 Stub/Mock `ChatModel` 的服务层集成测试，经过 `DeepSeekAiChatService` 的真实观测包装方法，分别验证同步成功/异常和流式完成/异常/取消。
- 断言同一请求的响应头 requestId 与 `MODEL_CALL` 日志 requestId 一致。
- 对离线 `MockAiChatService` 明确其是否属于观测范围。若记录，Provider/模式必须标记为 `mock`，Usage 使用 `NOT_SUPPORTED`/`NOT_RETURNED`，不能伪造 Token；若不记录，应在接口/文档中明确 Mock 不是模型调用观测证据。
- 将真实 DeepSeek Usage 作为未验证事项保留，不能以模拟 ChatResponse 的 Usage 测试替代 Provider 实测。

### P2-04：首 Chunk 指标与文档的“首 Token/首个非空输出”口径不一致

**证据位置**：`observability/ModelCallObservation.java`。

当前 `instrument()` 在每次 `ChatResponse` `onNext` 时立即设置 `firstChunkNanos`，并未检查该 chunk 是否包含非空文本/推理增量。知识笔记将首延迟描述为第一个非空输出片段，费曼口述又称“首 Token 延迟”。这三种口径不等价。

**整改要求**

- 若实际记录的是首个 `ChatResponse` 信号，统一命名并描述为 `timeToFirstChunkMs` / TTFC。
- 若目标是用户体验 TTFT，应在首个非空、可展示的文本/推理输出到达时计时，并定义是否包含 reasoning chunk。
- 增加“空 metadata chunk 在前、非空文本 chunk 在后”的测试，确保计时点符合文档口径。

### P2-05：D21 仅实现结构化调用日志与关联字段，不是完整的三支柱观测平台

项目按任务边界未引入 Micrometer Metrics / OpenTelemetry Tracing，当前实现提供单行 JSON 日志、requestId 关联、duration/TTFC/Token 字段；这些字段可以由日志平台后续聚合，但项目本身没有实际 Meter、直方图/分位数、告警规则、Tracer 或 Span。

**整改要求**

- 在项目文档和口述中统一称为“最小结构化调用日志与请求关联能力”，不要说成已经拥有完整 Logs/Metrics/Traces 三支柱。
- 若未来启用指标，单独通过 Micrometer Timer/Counter 记录低基数维度；requestId、traceId、sessionId 不得成为 Metric 标签。
- 若未来启用分布式追踪，需实际验证 Trace/Span 与日志 correlation 的上下文传播。
- 告警阈值应标注为需按 SLO、流量与业务场景设定的示例，不得把 95%、30 秒等值说成普适标准。

## 四、知识笔记整改

### 保留的优点

- 将 Token Usage、Latency、Correlation 分开说明，定义 requestId、traceId、spanId、providerResponseId、conversationId 的不同作用。
- 对 Usage 缺失、部分返回、估算值、Mock 数据有明确区分；明确禁止用字符数冒充 Token。
- 针对 Spring AI 1.1.8 和 DeepSeek 自动观测支持边界作了提醒，没有简单推断“引入 DeepSeek Starter 就必然具备 Metrics/Trace”。
- 有 `System.nanoTime()`、Micrometer Timer、高基数标签、结构化日志与敏感数据风险方面的覆盖。

### 需要修正

1. 5.1 的示例 Filter 限制 ID 为 1–64 字符，但真实项目 `sanitizeInboundRequestId()` 没有长度限制；示例与实现必须一致。
2. 流式计时目前测量第一个 `ChatResponse` chunk，而不是必然测量第一个非空用户可见输出；统一 TTFC/TTFT 定义。
3. 明确当前 D21 只做 requestId 关联，没有真正 Trace/Span；不要把 `requestId` 复制到 `traceId` 字段描述为完整链路追踪。
4. 增加一个“访问日志也属于安全边界”的章节：`MODEL_CALL` 白名单之外，HTTP Body、AOP 参数/返回值、异常消息、框架 DEBUG 日志都必须一起审查。

## 五、费曼口述整改

当前 38 题结构完整，但以下回答必须调整：

1. **问题一**：“不用改代码、不用重新发布”不是可观测性的定义。应用通常需要合适的埋点、上下文传播与配置；可观测性是从输出数据推断内部状态的能力。
2. **问题四、三十七、三十八**：把指标、完整 Trace、告警说成所有最小实现都必须同时具备，并进一步描述成 D21 已经落地。要区分“完整生产方案目标”与“本轮实际交付”：D21 没有 MeterRegistry 指标、Tracer/Span 和告警。
3. **问题九**：前端请求 ID、幂等键、服务端 requestId、业务调用 ID、TraceId、ConversationId 的职责需要重新划分。幂等键不是 TraceId；请求 ID 是否由前端生成并跨重试保持不变，是系统设计约定，不是通用规则。
4. **问题十九**：“每个模型调用响应都会带 Token Usage”错误。Usage 可能缺失、部分返回，取决于 Provider、模型与流式协议；必须判空并标来源。
5. **问题二十**：成本不能简单统一用 `totalTokens × 单价`。至少区分输入/输出价格；缓存命中、推理 Token、模型档位和计费政策也可能有不同价格口径。
6. **问题二十六**：“模型调用占总耗时 70% 以上”没有本项目测量数据支持，应删除或标为假设示例。
7. **问题二十九**：Spring AI 1.1.x 自动观测并不代表所有 Provider 都会产生同样的 Meter/Trace；DeepSeek 的支持情况必须按 1.1.8 官方支持名单和项目实际依赖验证，不可泛化。
8. **问题三十五、三十八**：95%、30 秒、5 分钟、成本增长 20% 等只能作为示例阈值，需要依据 SLO、样本量、流量与业务损失评估。
9. **问题三十**：首个 SSE/ChatResponse chunk 不一定等于首个文本 Token；区分 TTFC 和 TTFT，并说明客户端断开率需要真实客户端取消数据才能统计。
10. **问题三十七、三十八**：账单误差 5%、压测、全量生产日志扫描等是未来验收目标，不是 D21 已有测试证据；口述时应明确“设计目标/尚未验证”。
