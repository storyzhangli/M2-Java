## 四、功能一：模型思考/推理模式

### 4.1 业务要求

1. 在现有聊天/问答入口增加**明确的思考模式开关**，尽量复用已有请求表单或设置面板，不另建独立聊天页面。
2. 后端必须接收并校验模式参数，并由服务端决定最终可用设置；不得仅在前端切换标签却始终以同一参数调用模型。
3. 若项目所用模型 API 与当前 Spring AI 版本支持推理强度，按真实 API 支持范围提供可选等级（例如低/高/最大）。如果版本不支持或映射不一致，应说明限制并采用兼容实现；不得臆造可用枚举或配置项。
4. 未指定参数时，默认行为应保持现有功能兼容，不能因本次迭代让旧客户端请求失败。默认开/关应结合当前项目和官方模型行为确定，并在文档中说明理由；如无明确产品约定，优先让旧请求保持原行为。
5. 普通响应和 SSE 流式响应都要处理；如模型返回独立的 `reasoning_content` 或对应推理字段，必须与最终答案 `content` 分开处理，不得把两种内容混合拼接后当作普通回答。
6. 请求参数要防止用户传入任意模型名称、任意 API 地址、未经允许的供应商或不支持的强度值。模型配置仍由服务端白名单与应用配置控制。
7. 保持现有会话历史、多轮聊天、超时、取消请求、错误处理、工具调用（如有）和 SSE 协议的正确性。
8. 在 UI 中明确区分“启用模型思考模式”和“向用户展示解释信息”这两个概念。**默认不要把模型原始内部推理全文作为普通用户可见的聊天答案、普通业务日志或长期持久化内容。**界面可以显示“正在分析/思考模式已启用”等状态，或展示经设计生成的简洁解释/结论摘要；只有当现有产品已经有明确的受控展示设计时，才按实际需求扩展，并必须经评估后实现。
9. 不得把“开启思考模式”宣传为模型一定正确；回答仍需有不确定性处理与引用验证。

### 4.2 技术实现约束

- 先确认当前依赖是否提供与实际模型 API 对应的强类型选项（例如 Spring AI DeepSeek 的 `Thinking`、`ReasoningEffort` 或当前版本等价类型）。**不得在未核验版本的情况下照搬网上新版本示例。**
- 优先使用项目当前的模型客户端和依赖公开 API；如需低层请求扩展，先解释原因，避免重复维护一套 HTTP 客户端。
- 若需要升级依赖，先证明现有版本无法实现、列出影响范围并尽量选择最小兼容调整；禁止顺手全面升级。
- 对流式输出，检查模型事件/块中最终答案与推理字段如何区分；在 SSE 适配层使用已有事件协议或向后兼容地扩展类型。不要把推理字段误当成最终内容 delta。
- 对会话和工具调用：如果当前模型协议要求在多轮工具调用中回传特定推理字段，按当前官方协议正确保留和转发；不要把推理字段无条件持久化进普通聊天历史，也不要因为移除必要字段而引发 400 错误。
- 在日志中默认记录模式参数、模型标识、耗时、请求 ID、成功/失败和 token 统计（若 API 提供）；不要默认记录完整 Prompt、完整知识库上下文、API Key 或完整原始推理文本。
- 合理控制超时、token 上限、取消/断连行为与错误映射；如果推理模式成本或延迟与普通模式有差别，在指南中说明，具体数据必须实测，不得编造。

### 4.3 建议验收场景

1. 普通模式请求成功，响应内容与旧版本协议兼容。
2. 启用思考模式的非流式请求成功，前端仅展示最终回答/受控解释信息，后端正确区分模型响应字段。
3. SSE 模式下开启与关闭均可正确结束；没有把推理 delta 误拼进最终答案。
4. 缺省、非法值、不支持强度、模型错误、超时、断开连接均有合理处理。
5. 旧版请求 DTO/客户端没有新增参数时仍可工作。
6. 若项目支持多轮或工具调用，验证思考模式下工具调用和后续轮次不因必要字段丢失而失败。
7. 测试可用 Mock/Stub，不应要求 CI 必须持有真实 API Key。真实模型联调作为单独、可选的手工验证，密钥从环境变量读取。

## 五、功能二：引用来源标注

### 5.1 产品行为

1. 对基于知识库检索、数据库查询或其他真实资料生成的答案，显示文本内引用标记（例如 `[1]`）和与其对应的来源列表。
2. 用户点击引用标记或来源条目时，在现有 UI 能力范围内显示来源标题、文档类型、章节/页码/片段位置、相关摘录、有效链接（若数据源确实提供）等元数据。字段应按真实数据能力选择，不得为了凑齐 UI 编造内容。
3. 来源列表应去重、顺序稳定，并与当前这一次回答严格绑定；不能把上一个问题的来源残留到本次答案。
4. 对没有检索结果、引用关联失败、来源数据不完整或回答不依赖检索上下文的场景，清晰说明“未找到可验证的引用来源”或按产品语义不显示来源。不能硬塞默认来源，也不能把模型训练知识当成检索证据。
5. 引用展示不应破坏原有 Markdown、安全过滤、代码块、SSE 流式输出、复制答案等功能。
6. 如当前已有引用或检索源展示，应先修复/复用，不得另建一套互不一致的引用系统。

### 5.2 数据真实性规则（必须遵守）

- **来源唯一可信依据**是实际检索/查询结果及其元数据。模型只可以引用系统分配的来源 ID（如 `S1`、`S2`），最终显示内容由后端根据本轮真实结果进行映射。
- 不允许模型独立生成并直接输出未验证的文件路径、文档 ID、网站 URL、页码、作者、日期或摘录作为事实来源。
- 检索到的来源先由后端生成临时、请求级引用映射，例如 `S1 -> documentId/chunkId/metadata`；发送给模型时提供可用来源编号与对应上下文。模型输出未知编号时，后端应拒绝、删除或标记为未验证，不能映射成其他来源。
- 引用元数据至少应尽可能保留可追溯的 `documentId`、`chunkId` 或等价稳定标识、标题/文件名、来源类型，以及 section/page/url 等实际可用字段。字段名称和存储方式应服从项目已有实体/DTO/数据库设计。
- 不得把向量相似度分数直接展示成“事实可信度”或“模型置信度”。如果显示检索分数，必须标注其含义且确认评分范围、排序和来源确实存在。
- 内容片段、检索结果与模型输出均是不可信输入。引用展示不得执行 HTML/脚本、不渲染危险链接，不允许来源文档中的指令覆盖系统约束。
- 如果已有权限/租户/知识库隔离，引用查询与来源详情也必须使用同一权限边界，禁止前端通过修改 ID 查看无权访问的文档。
- 引用目标若是本地文件，不得直接暴露用户本机绝对路径。对外展示安全的文件名/文档详情/受控下载 URL。
- 答案文本中的标记与结构化 `citations` 数据必须能相互验证。禁止仅靠正则扫描模型自写的 `[1]` 就把任意检索文档当成支持证据。

### 5.3 建议的数据契约

先查现有 DTO/SSE 协议；只有缺少等价字段时才增加必要字段。设计可参考：

```json
{
  "answer": "设备出现过热报警时，应优先检查冷却系统和温度传感器。[1]",
  "citations": [
    {
      "id": "S1",
      "documentId": "真实文档标识",
      "chunkId": "真实片段标识",
      "title": "真实文档标题或文件名",
      "section": "真实章节（如有）",
      "page": null,
      "excerpt": "来自真实检索片段的有限摘录",
      "url": null
    }
  ],
  "thinkingEnabled": true
}
```

这只是**契约示意，不是要求复制的固定结构**。应以项目既有响应模型、命名规范、SSE 消息格式和持久化方式为准；不能把示例中的 ID、标题、摘录或链接写入业务代码伪装成真实来源。

### 5.4 引用生成与展示方案

实施前基于现状选择最小可行设计，至少考虑：

1. 检索层返回真实 Document/Chunk 与元数据。
2. 服务层为本次请求建立引用编号映射，保留来源与上下文的关联。
3. Prompt 明确只允许引用提供的来源编号；上下文不足时应承认不足，不要编造。
4. 模型输出后验证引用编号与本轮来源映射；结构化来源列表由后端组装，而不是完全信任模型输出。
5. 前端使用结构化来源数据渲染引用，不依赖从自然语言中猜测来源详情。
6. 流式场景确定引用出现时机：可以流式输出答案后在结束事件中发送引用列表，或采用项目已有的结构化 SSE 事件；前后端必须使用同一协议。
7. 如当前回答由无检索的普通聊天生成，应与知识库回答区分，避免把“通用模型回答”伪装成“有来源支持的知识库回答”。

### 5.5 建议验收场景

1. 检索到一个或多个片段：答案中的引用编号与来源列表对应。
2. 无检索结果：不生成虚假引用，并返回符合产品语义的提示。
3. 模型输出不存在的引用编号：服务端验证失败并安全处理。
4. 文档标题、章节、页码、链接缺失：仅隐藏缺失字段，不生成占位假数据。
5. 同一文档多个相邻片段或重复片段：根据实际产品策略去重，但不得丢失必要定位信息。
6. 用户无权限的文档：不能被检索、引用或直接查询来源详情。
7. 连续进行两个不同问题：第二个答案的引用不会混入第一个答案的来源。
8. SSE 流式答案结束后引用列表可正确显示；断线、异常、取消请求时状态不会错误残留。
9. Markdown、代码块、中文标点、答案复制和引用点击均不发生破坏。
10. 注入测试：来源文本里包含“忽略之前指令”或伪造引用时，系统仍把它当作普通资料，不服从来源内容中的指令。

## 六、两项功能的交互与兼容性设计

1. **开关作用域**：思考模式是本轮请求设置还是用户偏好设置，应优先服从已有产品交互；本次默认按每次请求显式传参设计，避免无意修改全局模型行为。若实现用户偏好持久化，必须说明存储位置、覆盖优先级与默认策略。
2. **引用作用域**：引用必须属于本轮 answer/requestId；不能全局缓存一个未区分会话的问题来源列表。
3. **SSE 兼容**：先阅读当前后端 Flux/SSE 实现和前端 parser，确认已有事件字段。新加思考状态/引用事件时向后兼容旧的 `content`、`done`、`error` 等事件（若这些事件确实存在）。不可凭空假定协议名称。
4. **响应顺序**：前端不得把结构化引用 JSON 当作普通回答文本显示；也不得因 SSE 结束事件先后顺序产生重复的答案、重复引用或永久 loading。
5. **持久化**：若聊天记录有数据库存储，先评估是否需要记录 `thinkingEnabled` 和 citations 快照。仅保存复现展示所必需的来源元数据；避免持久化完整原始推理字段、敏感提示词或大量知识库全文。迁移须向后兼容。
6. **错误处理**：模型不支持思考模式时，应给出可理解的错误或受控降级；不允许悄悄把参数丢掉却仍显示“已启用”。来源缺失时不得导致整条回答异常，除非项目业务要求引用为强制条件且已有明确错误契约。
7. **性能**：尽量复用一次检索结果，不为展示引用无必要地重复检索。不要承诺速度、token 或费用的改善；如果需要给出指标，必须先定义测量方法并用实测数据说明样本范围。

### 阶段 A：检查与方案

### 阶段 B：编码实现

1. 遵守 D16 现有包结构、命名风格、依赖方向、统一异常、日志、校验、DTO 和测试风格。
2. 只修改完成需求所需的文件。避免大规模重构、重复 Service、无必要抽象、无理由引入新框架或新数据库。
3. 保持 Controller 薄、业务逻辑归属清晰；配置与密钥从环境变量/外置配置读取，禁止硬编码。
4. 对用户输入校验模式参数和推理强度；来源数据与模型生成内容分离存储、分离验证。
5. 前后端同时改动时确保接口与事件格式一致，并更新类型定义、请求封装和展示状态。
6. 所有新增代码补充有意义的单元测试；对跨层行为增加集成测试或可重复的 Mock 测试。
7. 保持已有功能不回归，尤其是普通问答、历史会话、Prompt 模板、流式输出、错误提示和数据持久化。
8. 不把真实 API Key 放进 `.env` 示例、截图或日志；示例只使用明显占位符。检查 `.gitignore` 是否妥当，但不要擅自忽略已有用户文件。

### 阶段 C：测试与验证

按项目实际构建工具执行，不要盲目认定使用某条命令。至少覆盖：

- 编译/构建检查。
- 相关单元测试。
- 两项功能的核心服务测试。
- Controller/DTO 参数兼容测试。
- SSE 事件顺序及异常测试（如项目使用 SSE）。
- 引用 ID 校验、空检索、缺失元数据、重复来源和权限边界测试（如项目具备相应权限机制）。
- 现有相关回归测试。
- 前端 lint/type-check/build（若存在对应脚本）。

真实模型连通性测试应作为单独可选步骤，只有在环境变量已配置且用户授权调用外部服务时才执行。不要为了通过测试而跳过测试、放宽断言、删除失败用例或屏蔽异常。

测试失败时：分析真实原因、修复与本次改动有关的问题，并重新运行受影响测试。对与本次改动无关的既有失败，应记录原始输出、影响范围和判定依据，不得声称“全部通过”。

### 阶段 D：代码审查

完成后检查：

- 是否存在硬编码密钥、敏感日志或不安全 URL。
- 是否把原始 reasoning 内容无意展示/写入日志/持久化。
- 是否把模型自写引用当成可信来源。
- 是否有跨请求、跨会话引用污染。
- 是否破坏现有 SSE 协议、旧请求或历史记录。
- 是否存在空指针、资源未释放、阻塞调用、订阅泄漏、重复检索或异常被吞。
- 是否新增不必要依赖、配置项或数据库迁移。
- 测试是否验证行为而非仅验证非空结果。

### 阶段 E：证据与交付

1. 把实际执行命令及其真实结果保存至 `logs`，日志文件名带日期/时间或 D16 功能标签；严禁把密钥写入日志。

3. 将临时脚本和临时文本放入 `docs\temp_docs`，**绝不自动删除**。
4. 生成下文要求的两份正式 Markdown 文档。
5. 最终报告真实说明：完成的功能、主要变更文件、运行过的命令、测试结果、证据位置、未解决问题、需要用户手工配置的内容以及是否真实调用过外部模型。
6. 给出 Git 分支、工作区状态和 diff 概览。没有执行 commit 就明确说未提交；没有执行测试就明确说未测试。
