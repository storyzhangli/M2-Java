# 费曼口述：AI 大模型——模型调用的失败策略

说话人 1：费曼口述，AI 大模型模型调用的失败策略，共五十道关键问题，分七个阶段，由浅入深讲清模型调用异常、超时控制、重试机制、限流与并发控制、熔断与降级、Spring AI 工程实现，以及企业级系统的可靠性设计。

说话人 1：本次以 Java 后端工程实践为主线，结合 JDK 21、Spring Boot 3.5.x、Spring AI 1.1.x 和 Resilience4j 展开。

说话人 1：先记住一个核心原则：模型调用失败以后，不能简单地认为重新请求一次就能解决问题。首先要判断为什么失败，再决定是重试、等待、限流、熔断、切换模型，还是直接失败。

说话人 1：模型调用的失败策略，本质上是在三个目标之间做平衡：尽可能提高请求成功率，避免故障扩散，同时控制调用成本和业务风险。

## 第一阶段：模型调用失败的基础认知

说话人 1：问题一，大模型 API 调用为什么可能失败？与传统 Java 后端调用数据库、Redis 或 HTTP 服务相比，有哪些特殊性？

说话人 1：答，大模型 API 本质上也是远程服务调用，所以常见的网络故障、连接超时、读取超时、限流和服务端异常，一个都不会少。

说话人 1：但大模型调用还有一些比较特殊的地方。

说话人 1：第一，调用耗时通常不稳定。普通数据库查询可能几十毫秒就能完成，而大模型需要处理输入、执行推理，再生成一段可能很长的内容，响应时间容易受到模型负载、输入长度和输出长度影响。

说话人 1：第二，调用成本更明显。很多模型服务按照输入 Token 和输出 Token 计费。如果请求已经到达供应商，甚至模型已经开始生成，只是客户端发生了超时，这时候重新调用就可能产生额外费用。

说话人 1：第三，模型输出不一定符合业务要求。HTTP 请求成功了，模型也返回了内容，但内容可能不是合法 JSON，可能缺少必填字段，也可能没有正确完成业务任务。

说话人 1：第四，模型服务存在供应商配额、RPM、TPM 等限制，不同模型、不同账户甚至不同 API Key 的配额都可能不一样。

说话人 1：举个制造设备故障助手的例子，用户要求分析 E102 报警。请求可能在网络连接阶段失败，也可能模型服务返回 429，还可能模型正常返回答案，但答案缺少必要的安全操作条件。

说话人 1：所以，不能只把模型调用当成一次普通 HTTP 请求。我们需要同时考虑网络可靠性、模型服务稳定性、生成内容质量和业务执行安全。

说话人 1：问题二，模型调用的失败可以分为哪些类型？

说话人 1：答，我通常把模型调用失败分成五大类，方便后续设计不同的处理策略。

说话人 1：第一类，网络和连接异常。例如 DNS 解析失败、连接被拒绝、连接重置以及网络中断。

说话人 1：第二类，超时异常。例如连接超时、读取超时和整个请求超过业务截止时间。

说话人 1：第三类，供应商返回的 HTTP 错误。例如 400 参数错误、401 认证失败、403 权限不足、429 限流，以及 500、502、503、504 等服务端或网关异常。

说话人 1：第四类，模型响应和内容异常。例如响应结构无法解析、模型返回空内容、结构化 JSON 格式错误，或者模型没有按照要求完成任务。

说话人 1：第五类，业务处理异常。例如模型已经成功返回答案，但后续数据库保存失败、业务数据校验失败，或者工具调用执行失败。

说话人 1：这些异常不能全部使用同一种处理方式。网络暂时中断可能值得重试，认证失败应该检查配置，业务数据不合法则需要修正输入，而不是重复调用模型。

说话人 1：问题三，什么是瞬时故障（Transient Failure）和永久性故障（Permanent Failure）？为什么必须区分两者？

说话人 1：答，瞬时故障可以理解为暂时出现的问题，过一段时间或者经过重新请求，有可能恢复；永久性故障则表示当前请求或配置本身存在问题，单纯重新请求通常无法解决。

说话人 1：例如，网络偶尔抖动、供应商暂时过载、部分 503 服务不可用，可能属于瞬时故障。

说话人 1：而 API Key 写错、模型名称不存在、请求参数不合法、账户没有访问模型的权限，通常属于需要修复配置或请求才能解决的问题。

说话人 1：为什么一定要区分？因为重试应该针对有恢复可能的故障。

说话人 1：如果 API Key 错误还不断重试，只会反复发送无意义请求；如果供应商暂时过载却立刻放弃，又可能损失本来能够成功的请求。

说话人 1：还有一个细节：瞬时和永久不是完全由 HTTP 状态码决定的。例如，403 通常不应该重试，但某些供应商可能会使用特定错误码表示临时访问限制。最终需要结合供应商错误码、异常类型和业务上下文判断。

说话人 1：问题四，HTTP 4xx 和 5xx 状态码分别代表什么？常见的 400、401、403、404、408、429、500、502、503 和 504 应该如何理解？

说话人 1：答，HTTP 状态码可以先分成两大类。

说话人 1：4xx 主要表示请求存在问题，或者当前客户端没有获得所请求资源的访问权限；5xx 主要表示服务器在处理请求时发生了错误。

说话人 1：常见状态码可以这样理解：

| 状态码 | 含义                  | 模型调用中的常见原因       |
| ------ | --------------------- | -------------------------- |
| 400    | Bad Request           | 参数错误、请求格式不合法   |
| 401    | Unauthorized          | API Key 无效或未认证       |
| 403    | Forbidden             | 没有模型访问权限或账户限制 |
| 404    | Not Found             | 模型、接口或资源不存在     |
| 408    | Request Timeout       | 服务端等待请求超时         |
| 429    | Too Many Requests     | 请求频率或配额超限         |
| 500    | Internal Server Error | 供应商内部异常             |
| 502    | Bad Gateway           | 网关收到上游异常响应       |
| 503    | Service Unavailable   | 服务暂时不可用或过载       |
| 504    | Gateway Timeout       | 网关等待上游响应超时       |

说话人 1：这里最重要的是不要把所有 4xx 都理解成永久错误，也不要把所有 5xx 都理解成一定可以重试。

说话人 1：比如，429 要看是否有配额恢复时间；503 可能是暂时过载，但如果已经超过业务总超时预算，也不能无限等待。

说话人 1：另外，408 和 504 的含义也不同。408 表示服务器没有及时收到完整请求，504 表示网关或代理等待上游响应超时。

说话人 1：参考资料：RFC 9110 — HTTP Semantics | HTTP 语义规范：[IETF 官方标准](https://www.rfc-editor.org/rfc/rfc9110.html?utm_source=chatgpt.com)

说话人 1：参考资料：RFC 6585 — Additional HTTP Status Codes | HTTP 扩展状态码规范：[IETF 官方标准](https://www.rfc-editor.org/rfc/rfc6585.html?utm_source=chatgpt.com)

说话人 1：问题五，模型 API 返回 HTTP 200，是否意味着模型调用在业务层一定成功？还可能出现哪些错误？

说话人 1：答，不意味着。HTTP 200 只能说明 HTTP 请求在协议层获得了成功响应，不能直接证明业务任务已经完成。

说话人 1：例如，模型正常返回了 HTTP 200，但响应内容可能是空字符串，可能是 JSON 结构不完整，也可能因为模型触发了特定结束原因，没有完成我们期望的输出。

说话人 1：还有一种情况，模型成功返回了合法 JSON，但字段值不符合业务规则。比如设备 ID 不存在，故障代码与用户请求不匹配，或者必要的安全检查步骤为空。

说话人 1：另外，在工具调用场景中，模型返回了一个工具调用请求，也不代表工具已经成功执行。工具还可能发生权限异常、超时或业务校验失败。

说话人 1：所以，模型调用不能只看 HTTP 状态码，还要检查响应结构、结束原因、内容质量和业务校验结果。

说话人 1：我通常把成功分成三个层次：HTTP 调用成功、模型生成成功、业务处理成功。只有符合当前任务的全部验收条件，才算真正完成。

说话人 1：问题六，为什么不能将所有模型调用异常统一处理为重试？哪些异常应该重试，哪些应该直接失败？

说话人 1：答，因为重试的前提是当前故障有可能通过再次请求恢复，而不是所有错误都满足这个条件。

说话人 1：例如，网络连接偶尔重置、供应商暂时返回 503、部分 502 或 504，可以在确认请求安全且仍有时间预算的情况下重试。

说话人 1：但是，API Key 错误、模型名称不存在、参数格式错误，通常没有重试价值。重新请求一次，错误大概率还是一样。

说话人 1：429 则要单独处理。它通常表示请求受到了限流，需要根据供应商返回的错误信息和 `Retry-After` 等信息决定等待多久，而不是立即再次请求。

说话人 1：还有一种比较特殊的情况：读取超时。客户端不知道模型是否已经完成请求，直接重试可能造成重复计费或重复生成。

说话人 1：所以，失败策略应该先进行异常分类，再决定是否重试。重试不是异常处理的默认动作，而是经过故障判断以后才允许执行的一种恢复手段。

## 第二阶段：超时控制（Timeout）

说话人 1：问题七，什么是连接超时（Connect Timeout）、读取超时（Read Timeout）和整体请求超时（Request Timeout）？它们分别控制什么？

说话人 1：答，这三个超时控制的是一次远程调用中不同阶段的等待时间。

说话人 1：第一，连接超时，控制客户端建立网络连接需要等待多久。例如，Java 应用想调用大模型供应商，但对方服务器无法连接，超过规定时间就应该放弃本次连接。

说话人 1：第二，读取超时，控制连接建立以后，客户端等待服务端返回数据的时间。例如，请求已经发送出去，但模型迟迟没有返回响应数据，就可能触发读取超时。

说话人 1：第三，整体请求超时，控制整个调用最多允许消耗多长时间。它通常需要覆盖连接、发送请求、等待响应、读取数据以及必要的处理时间，具体范围取决于你在哪一层定义这个截止时间。

说话人 1：举个例子，连接超时设置 3 秒，读取超时设置 30 秒，整体请求超时设置 60 秒。那么连接阶段最多等待 3 秒，等待响应数据时最多允许连续 30 秒没有数据，而整个请求不能超过 60 秒。

说话人 1：不过，这些超时并不是简单相加的关系。读取超时可能针对一次读取操作或连续无数据的时间，响应超时也可能只针对等待响应的阶段，整体超时则应该由更外层统一控制。

说话人 1：在 Java 项目中，如果使用 Spring 的 `WebClient` 和 Reactor Netty，可以配置连接超时、读写超时和响应超时。不能只配置一个超时时间，就认为所有阶段都受到了控制。

说话人 1：参考资料：Configuration :: WebClient | WebClient 配置：[Spring Framework 6.2 官方文档](https://docs.spring.io/spring-framework/reference/6.2/web/webflux-webclient/client-builder.html?utm_source=chatgpt.com)

说话人 1：问题八，为什么大模型调用需要根据模型生成时间设置合理的超时策略？超时时间过短或过长分别有什么问题？

说话人 1：答，因为大模型调用的耗时通常比普通的数据库查询更长，而且不同请求之间的耗时差异可能比较大。

说话人 1：例如，用户问一句简单的常识问题，模型可能几秒就能完成；如果用户要求分析大量文档、进行复杂推理或者生成很长的回答，就可能需要几十秒甚至更长时间。

说话人 1：如果超时时间设置得太短，模型还没来得及生成答案，请求就被客户端取消了，导致大量本来能够成功的请求失败。

说话人 1：但如果超时时间设置得太长，也有问题。比如模型供应商已经出现故障，一个请求一直等待几分钟，就会占用连接、任务资源和可能的线程资源。

说话人 1：所以，超时时间不能随便设置一个固定数字，而应该根据模型的历史响应时间、输入 Token 数、预计输出 Token 数、业务允许等待时间以及供应商特性来确定。

说话人 1：我通常会观察不同任务的 P95、P99 响应时间，再结合业务截止时间设置超时，而不是直接用平均响应时间作为标准。

说话人 1：核心就是：超时太短容易误杀正常请求，超时太长则可能让故障请求长期占用资源。

说话人 1：问题九，同步调用与 SSE 流式调用在超时控制方面有什么区别？流式响应为什么还需要考虑连接空闲超时和整体生成时限？

说话人 1：答，同步调用和 SSE 最大的区别在于，完整结果什么时候返回，以及连接在整个过程中是否持续传输数据。

说话人 1：同步调用通常需要等模型生成完整答案。如果模型在规定时间内没有返回完整结果，就可能触发整体请求超时。

说话人 1：SSE 则不同。模型可能已经返回了前几个 Token，后面还要继续生成几十秒。因此，我们不能简单地认为只要第一个 Token 返回了，本次请求就已经成功完成。

说话人 1：对于流式调用，我会重点设置两类限制。

说话人 1：第一，连接空闲超时。控制模型长时间没有产生任何新内容时，系统是否需要认为连接异常。

说话人 1：第二，整体生成时限。即使模型一直有内容返回，也不能允许一个生成任务无限运行。

说话人 1：例如，一次 SSE 请求允许最多生成 120 秒，但连续 20 秒没有收到模型输出，就可以根据业务策略判断是否需要结束请求。

说话人 1：不过，心跳和模型内容必须分开处理。SSE 心跳可以维持 HTTP 连接，但不能因为一直发送心跳，就认为模型生成一直正常。

说话人 1：另外，如果系统还有网关读取超时、SSE 连接超时和模型读取超时，这些配置也要相互协调，不能出现模型还在正常生成，但网关提前断开连接的情况。

说话人 1：问题十，如果模型服务端已经接收到请求并开始生成，但客户端读取超时，服务端是否一定停止了模型计算？可能产生什么问题？

说话人 1：答，不一定。这是模型 API 调用中非常重要的一个问题：客户端超时，不代表供应商已经停止执行。

说话人 1：举个例子，Java 应用向模型供应商发送一个生成请求，模型已经开始推理并产生了部分内容，但由于网络抖动，客户端超过读取超时时间，没有收到后续数据。

说话人 1：这时候客户端可能认为本次调用失败了，但供应商那边可能仍然在继续执行，甚至最终成功生成了完整答案。

说话人 1：如果业务代码立即再调用一次，就有可能产生第二次模型计算，造成重复 Token 费用和重复资源消耗。

说话人 1：如果模型还涉及 Tool Calling，问题会更严重。例如，模型第一次调用工具创建了维修工单，但响应返回之前发生了网络超时。应用重新调用模型以后，可能再次创建一张工单。

说话人 1：所以，遇到读取超时，必须考虑远端执行结果未知的情况。不能直接认定请求一定失败，更不能默认重新调用一定安全。

说话人 1：比较合理的做法是记录 `requestId`、生成任务状态和工具执行状态。对于支持任务查询或取消的供应商，可以利用它们提供的机制进行确认；如果不支持，就需要在业务层控制重试风险。

说话人 1：问题十一，如果模型调用超时，但业务线程仍然等待响应，会对 Java 线程池、连接池和系统吞吐量造成什么影响？

说话人 1：答，首先会造成线程资源被长期占用，尤其是使用阻塞式 HTTP 客户端或者同步调用的场景。

说话人 1：例如，应用线程池只有 100 个工作线程，同时有 100 个请求都在等待大模型响应。如果每个请求都需要等待 60 秒，那么这段时间内线程池可能已经没有多余线程处理新的业务请求。

说话人 1：其次，HTTP 连接资源也可能被占用。模型调用一直没有完成，连接池中的连接就可能长期无法释放，后续请求可能因为没有可用连接而等待。

说话人 1：第三，整个系统吞吐量会下降。用户请求不断进入，但后台线程和连接无法及时释放，最终可能形成请求积压。

说话人 1：所以，超时控制不只是为了让用户早点看到错误，更重要的是限制资源占用时间，保护整个系统。

说话人 1：在 Java 项目中，可以结合有界线程池、连接池超时、请求截止时间、Bulkhead 和合理的并发限制来处理。

说话人 1：如果使用 JDK 21 虚拟线程，也能降低阻塞任务的线程成本，但不能因此忽略模型供应商配额、HTTP 连接数量和其他系统资源限制。

说话人 1：问题十二，如何设计模型调用的总超时时间，并协调连接超时、读取超时、重试等待时间和业务请求截止时间？

说话人 1：答，我会先设置一个最外层的请求截止时间，再根据这个总时间分配各个阶段的时间预算。

说话人 1：例如，用户发起一次模型请求，业务最多允许等待 60 秒。那么这 60 秒不能只用于模型调用，还要考虑排队、连接建立、模型生成、必要的重试等待和结果保存。

说话人 1：假设给一次请求分配：

- 排队和准备：5 秒。
- 连接建立：3 秒。
- 单次模型调用：35 秒。
- 重试与退避：10 秒。
- 结果处理和保存：7 秒。

说话人 1：这只是一个示意预算，真实项目还要根据模型响应分布和任务类型调整。最重要的是，所有阶段加起来不能突破业务整体截止时间。

说话人 1：另外，每次准备重试之前，都应该检查剩余时间。如果本次调用已经耗费 50 秒，只剩下 10 秒，但预计下一次模型调用至少需要 30 秒，那就没有必要继续重试。

说话人 1：所以，我更倾向于使用统一的 Deadline 概念，让每一层都能知道当前请求还剩多少时间，而不是每个组件各自设置一个互不关联的超时。

说话人 1：这样可以避免连接超时、模型超时、重试超时和业务超时互相冲突，最终让系统在明确的时间预算内结束请求。

## 第三阶段：重试机制（Retry）

说话人 1：问题十三，什么是重试机制？为什么重试可以提高模型调用在瞬时故障下的成功率？

说话人 1：答，重试就是第一次调用失败后，在满足一定条件的情况下，再次执行同一个请求。

说话人 1：它之所以有用，是因为部分故障只是暂时性的，不一定意味着服务彻底不可用。

说话人 1：例如，模型供应商某个节点短暂出现网络抖动，第一次调用返回 502，过一小段时间以后，供应商可能已经恢复正常。第二次请求就有机会成功。

说话人 1：再比如，某个网络连接刚好被重置，重新建立连接以后可能就可以正常调用。

说话人 1：所以，重试的目的不是修复永久性错误，而是提高瞬时故障下的请求成功机会。

说话人 1：但重试也有代价。每一次重试都可能增加请求次数、模型费用和等待时间。如果没有合理的次数限制，反而可能加重供应商故障。

说话人 1：因此，重试必须和异常分类、最大次数、等待策略及总超时预算一起设计。

说话人 1：问题十四，哪些模型调用异常适合重试？哪些情况不应该重试？如何结合 HTTP 状态码、供应商错误码和异常类型判断？

说话人 1：答，我一般先按照异常是否具有恢复可能性分类，再结合 HTTP 状态码和供应商返回的具体错误码判断。

说话人 1：例如，连接重置、临时 DNS 故障、部分 502、503 和 504，通常可以在满足时间预算和请求安全条件时考虑重试。

说话人 1：429 则要根据限流原因处理。如果只是暂时的请求频率超限，可以等待供应商建议的时间再尝试；如果是账户额度不足，继续重试通常没有意义。

说话人 1：400 通常意味着参数或请求格式有问题，需要先修复请求；401 通常是认证问题；403 通常是权限或账户限制；404 如果是模型名称错误，也没有重试价值。

说话人 1：这里还要考虑异常类型。比如，读取超时和连接超时虽然都属于超时，但连接超时可能发生在请求尚未送达供应商之前，而读取超时可能发生在供应商已经开始生成之后，后者的执行状态更加不确定。

说话人 1：所以，我会建立一套异常分类策略，而不是只根据 HTTP 状态码判断。

说话人 1：例如，可以定义：

```
MODEL_NETWORK_ERROR      网络异常
MODEL_TIMEOUT           模型超时
MODEL_RATE_LIMITED      请求限流
MODEL_AUTH_ERROR        认证异常
MODEL_INVALID_REQUEST   参数错误
MODEL_UNAVAILABLE       服务不可用
MODEL_OUTPUT_INVALID    输出格式异常
MODEL_BUSINESS_ERROR    业务校验失败
```

说话人 1：每种异常对应不同的恢复策略。特别是对于已经产生外部业务副作用的请求，必须先处理幂等和执行状态，才能考虑重试。

说话人 1：问题十五，什么是最大重试次数？为什么需要限制重试次数？

说话人 1：答，最大重试次数就是一次请求最多允许执行多少次尝试，通常包含第一次调用。

说话人 1：例如，配置 `maxAttempts = 3`，表示总共最多调用三次，而不是第一次加三次重试。

说话人 1：第一次失败后，可以重试第二次；第二次仍然失败，可以再重试第三次；第三次还是失败，就应该停止继续尝试。

说话人 1：为什么要限制？因为如果没有上限，一个请求可能一直占用线程、连接和供应商配额，甚至形成无限重试。

说话人 1：更严重的是，如果大量请求同时失败，又都不断重试，供应商本来已经过载，反而会受到更大的请求压力。

说话人 1：在 Spring AI 项目中，我通常会先从 2 到 3 次总尝试次数开始评估，再根据供应商的错误类型、成功率和整体延迟调整，不能把某个次数当成所有场景的固定标准。

说话人 1：参考资料：Retry | 重试机制：[Resilience4j 官方文档](https://resilience4j.readme.io/docs/retry?utm_source=chatgpt.com)

说话人 1：问题十六，什么是固定间隔重试（Fixed Interval Retry）？它有哪些优点和缺点？

说话人 1：答，固定间隔重试就是每次失败后，都等待相同的时间再发起下一次请求。

说话人 1：例如，设置每次等待 1 秒，第一次失败以后等 1 秒，第二次失败以后仍然等 1 秒，然后继续重试。

说话人 1：这种方式最大的优点就是简单，容易理解，配置也很直观。

说话人 1：但缺点也很明显，如果供应商发生较长时间的过载，客户端每秒都在重试，可能持续给故障服务施加压力。

说话人 1：而且，如果很多客户端同时失败，它们很可能在同一时间再次发起请求，形成周期性的请求洪峰。

说话人 1：因此，固定间隔更适合故障持续时间较短、调用量较小，而且服务端恢复时间相对稳定的场景。对于高并发模型 API，通常更值得评估指数退避和随机抖动。

说话人 1：问题十七，什么是指数退避（Exponential Backoff）？为什么等待时间通常随着重试次数增加？

说话人 1：答，指数退避就是随着重试次数增加，逐渐延长下一次请求前的等待时间。

说话人 1：例如，第一次失败后等待 1 秒，第二次失败后等待 2 秒，第三次失败后等待 4 秒，下一次再根据配置延长。

说话人 1：常见计算形式是：

\\[ delay_n = \min(d_0 \times 2^{n-1}, d\_{\max}) \\]

说话人 1：其中，\\(d_0\\) 是初始等待时间，\\(n\\) 是重试轮次，\\(d\_{\max}\\) 是最大等待时间。

说话人 1：为什么要这样设计？因为如果供应商一直处于过载状态，立即反复请求并不能提高成功率，反而会继续增加压力。

说话人 1：等待时间逐步增加，可以给供应商留出恢复空间，同时减少客户端不必要的请求。

说话人 1：但指数退避也不是越大越好。如果等待时间过长，可能超出用户允许等待的时间，因此还必须结合最大退避时间和总 Deadline。

说话人 1：问题十八，什么是随机抖动（Jitter）？它如何降低大量客户端同时重试造成的请求洪峰？

说话人 1：答，随机抖动就是在原来的退避等待时间基础上增加一定随机性，避免大量请求在同一时间重新发起。

说话人 1：例如，1000 个客户端都在同一秒收到 503，如果每个客户端都严格等 2 秒，那么 1000 个请求很可能在 2 秒之后同时再次打到供应商。

说话人 1：这就形成了所谓的惊群效应。

说话人 1：引入 Jitter 以后，可以让不同客户端的等待时间稍微错开。例如，有的等待 1.5 秒，有的等待 2.2 秒，有的等待 2.8 秒。

说话人 1：这样请求能够分散到一段时间内，避免所有客户端同时恢复请求。

说话人 1：常见的全抖动策略，可以在指数退避计算出的上限范围内随机选择等待时间，例如：

\\[ delay = random(0, \min(d_0 \times 2^n,d\_{\max})) \\]

说话人 1：实际采用哪种 Jitter 算法，要根据框架支持和业务策略选择。关键目的是让重试时间分散，而不是所有请求按照同一节奏反复冲击供应商。

说话人 1：问题十九，固定间隔重试、指数退避和指数退避加随机抖动分别适合什么场景？

说话人 1：答，这三种方式可以按照系统压力和并发规模来选择。

说话人 1：固定间隔重试最简单，适合低并发、故障恢复时间较短的内部服务调用。

说话人 1：指数退避适合调用量较大、供应商可能持续过载的场景，避免请求频繁打到已经发生故障的服务。

说话人 1：指数退避加随机抖动，则更适合大量客户端同时调用同一个外部模型供应商的场景，可以减少集中重试。

说话人 1：例如，制造设备助手可能有几百个用户同时调用同一个模型 API。如果模型服务短暂返回 503，所有应用实例都采用固定 1 秒重试，可能在一秒后形成新的请求洪峰。

说话人 1：换成有上限的指数退避并加入随机抖动，通常更加稳妥。

说话人 1：所以，选择策略要看并发量、供应商限流机制、故障持续时间以及用户允许等待多久，而不是只看哪种算法更复杂。

说话人 1：问题二十，什么是 `Retry-After` 响应头？遇到模型供应商限流时，如何结合服务端建议的等待时间设计重试策略？

说话人 1：答，`Retry-After` 是 HTTP 响应头，服务器可以通过它告诉客户端，建议至少等待多长时间以后再发起后续请求。

说话人 1：它常见于 503 服务不可用，也可以用于 429 请求过多的场景。

说话人 1：例如：

```
HTTP/1.1 429 Too Many Requests
Retry-After: 10
```

说话人 1：表示服务器建议客户端等待 10 秒以后再尝试。

说话人 1：它也可以使用 HTTP 日期格式表达等待时间，而不一定只是秒数。

说话人 1：如果模型供应商返回了这个响应头，我们应该优先考虑服务端提供的等待建议，而不是无视它，马上使用自己设置的 100 毫秒重试。

说话人 1：但是，还要结合业务总超时预算。如果服务端要求等待 60 秒，而用户请求只剩 10 秒有效时间，那么继续等待就没有意义，应该结束请求并告知用户稍后重试。

说话人 1：这里也要区分供应商的配额限制。如果 `429` 实际表示账户余额不足或月度额度耗尽，即使返回了等待时间，也不能盲目认为等待以后一定恢复。

说话人 1：参考资料：RFC 9110 — HTTP Semantics | HTTP 语义规范：[IETF 官方标准](https://www.rfc-editor.org/rfc/rfc9110.html?utm_source=chatgpt.com)

说话人 1：参考资料：RFC 6585 — Additional HTTP Status Codes | HTTP 扩展状态码规范：[IETF 官方标准](https://www.rfc-editor.org/rfc/rfc6585.html?utm_source=chatgpt.com)

说话人 1：问题二十一，为什么重试可能导致请求放大？当模型供应商已经出现故障时，大量客户端同时重试会造成什么后果？

说话人 1：答，因为第一次请求失败以后，原本只需要一次调用的业务，现在可能变成两次、三次甚至更多次调用。

说话人 1：例如，1000 个用户同时发送请求，第一次全部失败。如果每个请求都允许最多重试两次，那么供应商最坏可能接收到 3000 次调用。

说话人 1：如果应用内部还有其他重试层，比如 HTTP 客户端重试两次，业务服务又重试三次，实际请求数量还可能进一步放大。

说话人 1：这就是重试风暴。供应商越忙，客户端越重试；客户端越重试，供应商压力越大，最终形成恶性循环。

说话人 1：对于大模型服务，还可能同时增加 Token 费用、排队时间和并发占用。

说话人 1：所以，重试必须有统一的次数上限，并配合指数退避、随机抖动、全局限流和熔断机制。不能让每一层都自作主张地重试。

说话人 1：问题二十二，如何为重试设置最大等待时间、总耗时预算和重试次数上限，避免重试本身拖垮业务系统？

说话人 1：答，我会同时设置三个限制。

说话人 1：第一，最大尝试次数。例如总共最多尝试 3 次，包含第一次调用。

说话人 1：第二，最大退避时间。例如每次失败后等待时间逐渐增加，但最多不超过 5 秒，防止等待时间无限增长。

说话人 1：第三，整体请求 Deadline。例如用户请求最多允许等待 60 秒，所有调用、排队和退避时间都不能超过这个上限。

说话人 1：举个例子，第一次模型调用失败，等待 1 秒后重试；第二次仍然失败，等待 2 秒再试。如果剩余时间不足以完成下一次合理的调用，就提前停止，不再继续。

说话人 1：此外，Retry 还要配置异常白名单。只允许确定有恢复可能的异常进入重试，认证错误、参数错误和业务校验失败等情况直接结束。

说话人 1：因此，完整的重试策略是：异常分类、次数限制、退避计算、等待上限和总 Deadline 五者配合，而不是单纯设置一个 `maxAttempts` 就结束了。

## 第四阶段：限流与并发控制（Rate Limiting）

说话人 1：问题二十三，什么是模型 API 限流？RPM（Requests Per Minute）和 TPM（Tokens Per Minute）分别代表什么？

说话人 1：答，模型 API 限流，就是模型供应商为了控制服务资源和账户使用量，对一定时间内允许的请求数量或 Token 数量设置上限。

说话人 1：RPM 是 Requests Per Minute，表示每分钟允许发起多少次请求；TPM 是 Tokens Per Minute，表示每分钟允许消耗多少 Token。

说话人 1：比如，某个模型账户的 RPM 是 60，TPM 是 100000。前者限制请求频率，后者限制 Token 使用量。

说话人 1：这两个限制是不同的。假设一个请求只使用 100 Token，但一分钟内连续发起 100 次请求，即使 Token 总量不高，也可能超过 RPM。

说话人 1：反过来，如果一次请求输入了很长的文档，单次就可能消耗大量 Token，即使请求次数不多，也可能触发 TPM 限制。

说话人 1：实际项目中，还要注意供应商的配额可能按照 API Key、账户、组织、模型或者模型系列分别计算，不能假设所有模型共享一个统一限额。

说话人 1：所以，RPM 管请求次数，TPM 管 Token 消耗。企业应用应该同时关注这两类限制，而不是只控制每秒请求数。

说话人 1：问题二十四，为什么模型供应商不仅限制请求次数，还可能限制输入与输出 Token 数量？

说话人 1：答，因为一次模型调用对供应商资源的消耗，不仅取决于调用次数，还取决于每次需要处理多少内容、生成多少内容。

说话人 1：例如，两个用户分别调用一次模型，都是一个请求，但第一个只输入 100 Token，第二个输入了 50000 Token 的技术文档，它们消耗的计算资源可能有很大区别。

说话人 1：另外，模型还需要生成输出内容。输出越长，通常意味着需要执行更多生成步骤，占用更多服务资源。

说话人 1：因此，供应商可能同时控制请求次数和 Token 使用量，以避免某个用户通过少量超长请求占用过多资源。

说话人 1：对我们的 Java 应用来说，不能只做 RPM 限流，还应该在调用前估算输入 Token，设置最大输出 Token，并对长文档、RAG 检索结果和历史消息进行长度控制。

说话人 1：尤其是聊天系统，随着历史不断增加，输入 Token 可能持续上涨。如果没有上下文预算控制，即使用户请求次数没有变化，也可能越来越容易触发 TPM 限制。

说话人 1：问题二十五，当收到 HTTP 429 时，应该如何判断是请求频率超限、Token 配额超限，还是账户额度不足？

说话人 1：答，不能只看到 429 就直接认定是 RPM 超限，因为不同供应商可能把不同类型的限制都映射成 429。

说话人 1：首先检查响应体中的错误代码、错误类型和详细描述。其次检查供应商返回的限流相关响应头，部分供应商会提供请求剩余次数、Token 配额和重置时间等信息。

说话人 1：例如，如果是请求频率超限，可以适当降低调用速率；如果是 Token 使用量超限，可以减少输入长度、控制输出 Token，或者等待配额恢复。

说话人 1：如果是账户余额不足、月度额度耗尽或者账户权限问题，那么单纯增加等待时间可能没有作用，需要处理账户或配额配置。

说话人 1：因此，我会把 429 进一步分类成请求频率限制、Token 限制和账户额度限制，并为不同原因设置不同的处理策略。

说话人 1：还要注意，供应商的错误响应不一定完全统一，不能把某个模型平台的错误码规则直接套用到其他平台。

说话人 1：问题二十六，什么是令牌桶（Token Bucket）和漏桶（Leaky Bucket）？它们如何用于控制模型调用流量？

说话人 1：答，这两个都是比较经典的流量控制算法，可以用来限制 Java 应用向模型供应商发送请求的速度。

说话人 1：先说令牌桶。可以把它想象成一个不断补充令牌的桶，每次请求进入之前，都需要取得一个令牌。

说话人 1：桶中有令牌就允许请求通过，没有令牌就需要等待，或者直接拒绝。

说话人 1：它的特点是允许一定程度的突发流量。例如，系统平时请求比较少，桶中积累了一些令牌，用户突然集中发起请求时，可以在桶容量范围内允许部分请求快速通过。

说话人 1：再说漏桶。可以把它想象成一个固定速度出水的桶，外部请求不断进入桶中，再按照相对稳定的速度向下游发送。

说话人 1：如果进入的速度超过处理能力，多余的请求就会在队列中等待；如果队列满了，就需要拒绝请求或采取其他处理策略。

说话人 1：所以，令牌桶更适合允许一定突发流量，同时控制长期平均请求速率的场景；漏桶更强调以相对稳定的速率处理请求。

说话人 1：实际模型调用时，我会根据供应商 RPM 和 TPM 设计相应的限流机制。如果一个请求的 Token 消耗差异很大，仅靠一个简单的请求令牌桶还不够，可能还需要按预计 Token 数量进行资源预留。

说话人 1：问题二十七，为什么仅依靠供应商限流还不够？Java 应用是否需要建立自己的并发控制和请求排队机制？

说话人 1：答，因为供应商限流属于最后一道外部保护，而我们自己的应用如果不提前控制流量，可能在请求到达供应商之前就已经出现资源问题。

说话人 1：例如，用户突然集中提交 10000 个 AI 请求，如果全部直接转发给模型供应商，供应商可能返回大量 429，但我们的应用也会产生大量等待任务、连接占用和异常处理开销。

说话人 1：因此，应用侧应该提前建立限流和并发控制。

说话人 1：第一，限制单位时间内允许发起的请求数量；第二，限制同时正在执行的模型调用数量；第三，对暂时无法处理的请求进行有界排队；第四，当队列满了，及时拒绝请求，而不是让任务无限堆积。

说话人 1：这里要区分限流和并发控制。限流限制一段时间内允许进入多少请求，并发控制限制同一时间允许执行多少请求，两者解决的是不同问题。

说话人 1：例如，供应商允许每分钟 60 个请求，但单次模型调用可能需要 20 秒，那么即使每分钟请求数量没有超过 60，同时执行的请求也可能很多。

说话人 1：因此，RPM 限制、TPM 限制和并发限制最好配合使用。

说话人 1：问题二十八，如果多个 Java 实例共同使用同一个模型 API Key，如何避免各实例独立限流导致全局请求超过供应商配额？

说话人 1：答，这涉及分布式环境下的全局限流问题。

说话人 1：例如，系统部署了三个 Spring Boot 实例，每个实例自己设置每分钟最多请求 50 次。单独看，每个实例都符合自己的限制，但三个实例合起来就可能达到每分钟 150 次。

说话人 1：如果供应商实际只允许整个 API Key 每分钟 100 次，那么最终还是会触发 429。

说话人 1：所以，多个实例需要共享限流状态，而不是每个实例都独立计算完整配额。

说话人 1：一种做法是使用 Redis 维护全局请求计数或令牌桶，各实例每次调用模型之前，都先向 Redis 申请调用额度。

说话人 1：也可以通过统一的 API Gateway 或模型调用代理集中管理所有请求，由它负责全局限流、Token 预算和请求排队。

说话人 1：不过，分布式限流还要考虑 Redis 故障、各节点时间差、令牌发放精度和瞬时流量。尤其是 TPM，不能只统计请求数量，还要结合输入和输出 Token 的实际或预计消耗进行管理。

说话人 1：如果多个应用实例使用不同 API Key，则还要根据供应商实际配额范围决定限流维度，不能把账户级和 Key 级配额混为一谈。

说话人 1：问题二十九，当模型请求积压时，应该如何设计排队、拒绝、降级和优先级策略？

说话人 1：答，不能让所有请求无限等待，应该有明确的容量上限和过载处理策略。

说话人 1：首先，设置有界队列，限制最多允许多少请求等待。其次，设置排队超时时间，超过业务截止时间的请求就没有必要继续保留。

说话人 1：然后，根据业务优先级分配资源。例如，设备安全相关的紧急故障咨询，优先级可以高于普通闲聊和非紧急知识查询。

说话人 1：如果队列已经满了，可以直接拒绝新请求，并向用户返回明确的服务繁忙提示，而不是继续接收后在内存中积压。

说话人 1：对于允许降级的普通任务，也可以考虑使用更便宜、更快速的模型；如果是需要准确性的核心故障判断，则不能为了追求可用性，随便降低模型能力或跳过关键校验。

说话人 1：所以，处理请求积压的核心是控制进入系统的速度，让有限资源优先服务真正重要的业务，而不是让所有请求都排队等待。

## 第五阶段：熔断、隔离与降级

说话人 1：问题三十，什么是熔断器（Circuit Breaker）？它为什么能够避免持续调用已经发生故障的模型服务？

说话人 1：答，熔断器可以理解成一个自动控制远程调用开关的机制。

说话人 1：正常情况下，模型供应商能够提供服务，应用就正常发送请求。

说话人 1：但如果一段时间内连续出现大量超时、服务端错误，或者响应时间明显变慢，系统就可以判断这个供应商可能已经处于故障状态。

说话人 1：这时候，熔断器会打开，直接拒绝一部分新的模型调用，而不是继续把请求发送给已经无法正常工作的服务。

说话人 1：这样做有两个好处。第一，避免继续浪费线程、连接和等待时间；第二，给供应商留出恢复时间，防止应用不断重试加重故障。

说话人 1：例如，模型供应商连续出现大量 503，熔断器打开后，新的调用可以快速进入降级逻辑，而不用再等待几十秒才发现请求失败。

说话人 1：所以，熔断的重点不是让单次请求重新成功，而是当外部服务整体表现不正常时，暂时停止调用，保护自己的系统。

说话人 1：问题三十一，熔断器的关闭（Closed）、打开（Open）和半开（Half-Open）三种状态分别代表什么？状态如何转换？

说话人 1：答，熔断器主要有三个状态。

说话人 1：第一，Closed，关闭状态。这是正常状态，允许请求继续调用模型服务，同时统计成功率、失败率和响应时间。

说话人 1：如果连续一段时间内的失败率或者慢调用比例达到配置阈值，就会进入第二种状态：Open，打开状态。

说话人 1：Open 状态下，新请求会被快速拒绝，不再正常访问模型供应商，避免持续调用故障服务。

说话人 1：等待一段配置时间以后，就会进入第三种状态：Half-Open，半开状态。

说话人 1：半开状态下，系统只允许少量试探性请求进入。如果这些请求成功，说明供应商可能已经恢复，熔断器就可以重新关闭；如果这些请求仍然失败，就重新打开熔断器，继续等待。

说话人 1：例如，可以设置最近 20 次调用作为统计窗口，失败率达到 50% 时打开熔断器，等待 30 秒以后允许少量请求试探。

说话人 1：这些数字只是配置示例，真正参数要根据请求量、响应时间和供应商恢复情况调整。

说话人 1：Resilience4j 除了这三个主要状态，还有 `METRICS_ONLY`、`DISABLED` 和 `FORCED_OPEN` 等特殊状态，可以用于监控或运维控制。

说话人 1：参考资料：CircuitBreaker | 熔断器：[Resilience4j 官方文档](https://resilience4j.readme.io/docs/circuitbreaker?utm_source=chatgpt.com)

说话人 1：问题三十二，熔断器与重试机制有什么区别？为什么两者可以组合使用，但必须合理控制执行顺序？

说话人 1：答，重试解决的是单次请求失败后，还有没有必要再尝试一次；熔断解决的是远程服务已经表现出持续故障时，要不要暂时停止新的请求。

说话人 1：例如，某次调用因为网络偶发抖动返回 502，可以重试一次；但如果连续 100 次调用中有 80 次失败，就说明可能不是一个简单的瞬时故障了，这时应该考虑熔断。

说话人 1：两者可以组合使用，但执行顺序会影响熔断器统计什么。

说话人 1：如果每次重试都经过熔断器，熔断器会观察每一次实际尝试，故障可能更快触发熔断。

说话人 1：如果熔断器包在整个重试流程外面，那么熔断器主要观察一次业务请求最终成功还是失败，而不会单独统计内部每一次尝试。

说话人 1：这两种方式各有适用场景，必须先想清楚熔断器希望统计的是单次 HTTP 尝试，还是整个业务请求的最终结果。

说话人 1：如果重试配置为最多 3 次、熔断器又设置得非常敏感，就可能出现故障尚未充分统计，或者多个请求同时尝试导致额外压力的问题。

说话人 1：所以，Retry 和 CircuitBreaker 不是简单地同时加上注解就完成了，而是要结合异常分类、统计口径和最大调用次数设计执行顺序。

说话人 1：问题三十三，什么是舱壁隔离（Bulkhead）？如何通过线程池隔离、并发限制和资源池隔离避免模型调用影响其他业务？

说话人 1：答，舱壁隔离的思想来源于船舶设计。船舱之间通过隔板隔开，即使某一个舱室进水，也不会让整个船全部沉没。

说话人 1：放到 Java 系统中，就是把不同类型的业务资源隔离开，避免某个外部服务发生故障时，把整个应用拖垮。

说话人 1：例如，一个 Spring Boot 应用同时提供用户登录、订单查询和 AI 模型调用。如果所有业务都共享同一个线程池，而大模型调用又非常慢，那么大量 AI 请求可能占满线程池，导致用户登录和订单查询也无法正常处理。

说话人 1：解决方式之一，就是给模型调用单独设置并发限制或专用线程池，让它最多占用规定数量的执行资源。

说话人 1：Resilience4j 提供两种主要 Bulkhead 实现。

说话人 1：第一种是 `SemaphoreBulkhead`，通过信号量限制同时进入的调用数量。第二种是 `FixedThreadPoolBulkhead`，使用固定大小的线程池和有界等待队列来隔离任务。

说话人 1：如果是非阻塞响应式调用，信号量隔离也可以发挥作用，不一定必须建立专用线程池。

说话人 1：但是，不管采用哪种方式，都不能认为隔离以后就不需要超时和限流。舱壁主要限制资源占用范围，并不能自动解决模型服务超时或者请求次数超限的问题。

说话人 1：参考资料：Bulkhead | 舱壁隔离：[Resilience4j 官方文档](https://resilience4j.readme.io/docs/bulkhead?utm_source=chatgpt.com)

说话人 1：问题三十四，什么是降级（Fallback）？模型服务不可用时，可以采用哪些降级方案？

说话人 1：答，降级就是当主要服务无法正常提供能力时，让系统切换到一种受控的备用处理方式，而不是让整个业务完全失效。

说话人 1：例如，主模型服务出现故障以后，可以考虑切换到备用模型；如果当前问题是之前处理过的常见问题，也可以返回经过审核的缓存答案；如果业务规则明确，还可以使用规则引擎进行有限处理。

说话人 1：但这些方案不是所有任务都适用。

说话人 1：例如，设备故障助手如果无法调用主模型，也无法查询设备实时状态，就不应该随便返回一段未经验证的维修建议。

说话人 1：对于高风险任务，可能更合理的降级方式是返回明确的暂时不可用提示，并提供人工处理入口。

说话人 1：所以，降级不是简单地让系统一定返回内容，而是在主要能力不可用时，保证返回结果仍然符合业务安全要求。

说话人 1：问题三十五，主模型调用失败后，切换备用模型是否一定能够成功？需要考虑哪些模型能力、输出格式、上下文长度和供应商兼容问题？

说话人 1：答，不一定。备用模型能够调用成功，不代表它一定能够完成主模型原本承担的业务任务。

说话人 1：首先，不同模型的能力可能不一样。主模型能够进行复杂推理，但备用模型可能只适合简单文本生成。

说话人 1：其次，模型的上下文窗口可能不同。原来的 Prompt 包含大量历史消息和 RAG 文档，备用模型可能根本无法接收这么长的输入。

说话人 1：第三，结构化输出能力和工具调用格式可能不同。例如，主模型支持某种严格 JSON Schema，而备用模型可能不能保证生成相同格式。

说话人 1：第四，不同供应商的请求参数、工具定义和错误处理方式也可能存在差异。

说话人 1：因此，不能只准备一个备用 API Key，就认为已经完成模型高可用。

说话人 1：更合理的做法是定义统一的模型调用接口，为不同模型配置对应适配器，并为备用模型建立独立的能力测试集。

说话人 1：切换时还要检查任务是否适合降级。如果备用模型无法满足当前任务的安全和准确率要求，就应该拒绝切换或者要求人工处理。

说话人 1：问题三十六，当模型服务持续不可用时，应该返回缓存结果、受控错误、规则引擎结果，还是转人工处理？如何根据业务风险进行选择？

说话人 1：答，我会根据任务类型、数据时效性和错误后果来决定，而不是认为所有请求都必须找到一个替代模型。

说话人 1：如果是低风险的常见知识查询，可以考虑返回经过审核的缓存结果，但需要检查缓存内容是否过期、是否适用于当前用户和当前设备。

说话人 1：如果是能够通过确定性业务规则完成的任务，例如简单的数值统计，可以直接使用规则引擎或 Java 程序处理。

说话人 1：如果是高风险设备操作建议，而模型和知识库都不可用，就应该返回受控错误，明确说明无法完成判断，并引导用户联系人工技术人员。

说话人 1：如果涉及重要的生产故障，可以将任务保存在数据库中，标记为等待人工处理，等服务恢复以后再继续处理。

说话人 1：所以，降级方案的优先级不是谁最容易实现就选谁，而是看哪种方案在当前故障条件下仍然能够安全地完成业务目标。

## 第六阶段：Spring AI 与 Java 工程实现

说话人 1：问题三十七，在 Spring AI 1.1.x 项目中，模型调用异常可能在哪些环节产生？如何区分模型供应商异常、HTTP 客户端异常、响应解析异常和业务异常？

说话人 1：答，Spring AI 的模型调用不是简单地发出一个 HTTP 请求就结束了，中间实际上经过多个环节，每个环节都可能出现异常。

说话人 1：第一，业务请求阶段。例如用户没有传入必要参数，Prompt 模板变量缺失，或者上下文组装失败。这些属于应用自己的输入和业务处理问题。

说话人 1：第二，HTTP 客户端阶段。例如 DNS 解析失败、连接超时、连接重置、读取超时。这些问题通常发生在 Java 应用与模型供应商之间的网络通信过程中。

说话人 1：第三，模型供应商阶段。例如返回 401、403、429、500、503 等 HTTP 错误。这些异常需要结合供应商返回的错误码和响应体进一步分类。

说话人 1：第四，响应转换阶段。供应商可能已经返回 HTTP 200，但响应 JSON 结构不符合预期，或者某个字段无法正常解析，导致响应转换失败。

说话人 1：第五，业务结果处理阶段。模型正常返回了内容，但是返回的 JSON 不符合业务要求，或者后续保存数据库失败。

说话人 1：所以，我会把这些问题划分为请求构建异常、HTTP 传输异常、供应商调用异常、响应解析异常和业务处理异常。

说话人 1：还有一个重要细节，Spring AI 统一了不同模型的调用接口，但并不意味着所有供应商的底层异常类型完全相同。具体异常包装方式还取决于当前模型适配器和 HTTP 客户端。

说话人 1：因此，不应该只在代码里捕获一个固定的异常类，就认为已经覆盖所有模型调用失败情况。应该针对项目真实使用的模型供应商，编写异常适配和集成测试。

说话人 1：参考资料：Chat Client API | 聊天客户端 API：[Spring AI 1.1 官方文档](https://docs.spring.io/spring-ai/reference/1.1/api/chatclient.html?utm_source=chatgpt.com)

说话人 1：问题三十八，如何在 Java 项目中统一封装模型调用服务，将超时、重试、熔断、限流、异常转换和日志记录集中管理？

说话人 1：答，我不会让每个业务 Service 自己直接调用 `ChatClient`，然后在每个方法里面重复写超时、重试和异常处理。

说话人 1：更合理的方式是建立一个独立的模型调用服务，例如 `ModelInvocationService`，统一管理模型请求的可靠性策略。

说话人 1：业务层只需要提供必要的输入、会话信息和模型选择要求，然后调用统一接口。

说话人 1：模型调用服务内部负责几个工作：第一，根据任务选择模型和调用参数；第二，执行限流和并发控制；第三，调用 Spring AI；第四，对瞬时异常执行有限重试；第五，通过熔断器控制供应商故障；第六，把不同异常转换成统一的业务异常；第七，记录耗时、Token 消耗、重试次数和模型供应商等监控信息。

说话人 1：例如，可以设计这样的接口：

```
public interface ModelInvocationService {

    String call(ModelRequest request);

    Flux<String> stream(ModelRequest request);
}
```

说话人 1：同步调用和流式调用可以由不同实现或者不同的内部执行策略处理，但对外统一异常分类、请求追踪和业务约束。

说话人 1：还有一点，模型调用服务不应该把所有业务逻辑都包进去。会话权限、工单创建和数据库事务应该继续由各自业务模块负责，避免模型调用模块变成一个什么都处理的巨型 Service。

说话人 1：这样，以后从一个模型供应商切换到另一个供应商，或者调整 Retry、CircuitBreaker 参数，都不会要求修改所有业务代码。

说话人 1：问题三十九，Resilience4j 的 Retry、CircuitBreaker、RateLimiter、Bulkhead 和 TimeLimiter 分别解决什么问题？它们如何组合使用？

说话人 1：答，这五个组件分别解决不同类型的可靠性问题，可以把它们理解为模型调用过程中的五道保护措施。

说话人 1：第一，Retry，负责重试。调用出现符合条件的瞬时故障时，在规定次数和时间范围内再次尝试。

说话人 1：第二，CircuitBreaker，负责熔断。当外部模型服务持续失败或响应过慢时，暂时停止发送新请求。

说话人 1：第三，RateLimiter，负责限流，控制一定时间内允许通过多少个请求。

说话人 1：第四，Bulkhead，负责隔离，限制同时执行模型调用的数量，或者把模型调用放到独立的有界线程池中。

说话人 1：第五，TimeLimiter，负责限制异步任务的执行时间，防止任务无限等待。

说话人 1：举个实际例子。一个模型请求进入系统，先通过并发限制和限流检查，再经过熔断器判断当前供应商是否允许调用，然后执行模型请求。如果发生临时网络异常，再按照 Retry 配置进行有限重试，整个过程还受到 Deadline 的限制。

说话人 1：但是，五个组件并不是必须全部采用，也不存在一个适合所有任务的固定执行顺序。例如，同一个会话流式输出和普通同步调用，可能就需要不同的超时与取消方式。

说话人 1：另外，Resilience4j 的 TimeLimiter 主要针对 `Future` 和 `CompletionStage`。如果处理 Reactor 的 `Flux` 和 `Mono`，还应该考虑响应式流的 `timeout()`、取消传播以及 `resilience4j-reactor` 提供的操作符。

说话人 1：所以，在 Spring AI 项目中，需要先确定自己使用的是同步调用还是响应式流，再组合合适的可靠性组件。

说话人 1：参考资料一：Getting Started | Resilience4j 入门：[Resilience4j 官方文档](https://resilience4j.readme.io/docs/getting-started?utm_source=chatgpt.com)

说话人 1：参考资料二：Getting Started with Spring Boot 3 | Resilience4j 与 Spring Boot 3 集成：[Resilience4j 官方文档](https://resilience4j.readme.io/docs/getting-started-3?utm_source=chatgpt.com)

说话人 1：参考资料三：TimeLimiter | 时间限制器：[Resilience4j 官方文档](https://resilience4j.readme.io/docs/timeout?utm_source=chatgpt.com)

说话人 1：问题四十，如果使用 Spring Retry 或 Resilience4j 实现模型调用重试，如何设计异常白名单、重试次数、退避间隔和总耗时限制？

说话人 1：答，首先，我会明确哪些异常可以进入重试，而不是对所有异常一律重试。

说话人 1：例如，部分连接异常、临时服务不可用和符合条件的 429，可以列入重试范围；API Key 错误、请求参数错误和业务校验失败，则直接失败。

说话人 1：然后配置最大尝试次数。例如：

```
RetryConfig retryConfig = RetryConfig.custom()
        .maxAttempts(3)
        .waitDuration(Duration.ofMillis(500))
        .retryOnException(this::isRetryable)
        .build();
```

说话人 1：这里的 `maxAttempts(3)` 表示最多调用三次，包含第一次调用。

说话人 1：实际生产环境还可以进一步使用 `IntervalFunction` 配置指数退避和随机等待，必要时结合自定义间隔策略处理 `Retry-After`。

说话人 1：同时，整个请求还要有最大耗时限制。比如，整个业务请求只有 30 秒预算，就不能因为重试配置允许三次调用，就让三次请求各自都等待 30 秒。

说话人 1：我会在每次尝试之前检查剩余时间，并且只允许在剩余预算足够的情况下继续调用。

说话人 1：另外，Resilience4j 的 Retry 可以通过 `retryOnException`、`ignoreExceptions` 和结果判断等方式定义策略。实际项目应该明确哪些异常计入重试，哪些异常直接忽略。

说话人 1：这比简单地加上 `@Retry` 注解，然后让框架自动处理所有异常要可靠得多。

说话人 1：问题四十一，如何避免 Spring AI、HTTP 客户端、Resilience4j 和业务服务多个层级同时重试，导致实际请求次数远超预期？

说话人 1：答，这个问题叫多层重试叠加，是分布式系统中特别容易忽略的问题。

说话人 1：例如，业务 Service 设置最多调用三次，Resilience4j 又设置最多三次，底层 HTTP 客户端还设置了三次自动重试。

说话人 1：理论上，一次用户请求可能触发多层尝试，实际供应商收到的请求数可能远远超过业务开发人员预期。

说话人 1：所以，我会先梳理完整调用链，确认哪些层启用了自动重试。

说话人 1：第一，检查模型供应商 SDK 和底层 HTTP 客户端是否自带重试；第二，检查 Resilience4j 是否启用了 Retry；第三，检查业务层、网关或者其他调用封装是否还在重复重试。

说话人 1：然后明确一个主要的重试策略入口，通常让统一模型调用层负责决定是否重试，其余层只提供必要的网络错误反馈。

说话人 1：如果底层确实需要保留自动重试，就必须把它计入整体尝试次数和总耗时预算。

说话人 1：最后，通过测试统计一次业务请求实际发送了多少次供应商 HTTP 请求，不能只看业务方法执行了几次。

说话人 1：只有全链路的请求次数能够被准确控制，才算真正解决了重复重试问题。

说话人 1：问题四十二，如何处理模型调用异常并映射为统一业务异常？应该如何区分可重试错误、限流错误、服务不可用和不可恢复错误？

说话人 1：答，我会在模型调用适配层统一处理不同供应商的异常，再转换成系统内部统一的错误类型。

说话人 1：例如，可以设计如下业务异常：

```
public enum ModelErrorCode {

    MODEL_TIMEOUT,

    MODEL_RATE_LIMITED,

    MODEL_UNAVAILABLE,

    MODEL_AUTH_FAILED,

    MODEL_INVALID_REQUEST,

    MODEL_OUTPUT_INVALID,

    MODEL_BUSINESS_ERROR
}
```

说话人 1：不同供应商即使返回不同的异常类和错误码，也可以映射到统一的 `ModelErrorCode`。

说话人 1：比如，供应商 A 返回某个自定义限流错误，供应商 B 返回 HTTP 429，最终都可以映射为 `MODEL_RATE_LIMITED`。

说话人 1：但是，统一异常并不意味着丢弃原始信息。还应该保留 HTTP 状态码、供应商错误码、请求 ID、模型名称和必要的原始异常原因，方便后续排查。

说话人 1：然后，根据统一错误类型决定下一步动作。`MODEL_TIMEOUT` 可以根据超时阶段判断是否重试；`MODEL_RATE_LIMITED` 根据等待建议处理；`MODEL_AUTH_FAILED` 应该检查认证配置；`MODEL_INVALID_REQUEST` 则需要修复请求参数。

说话人 1：最终对前端返回的错误信息应该是安全、明确的业务提示，而不是直接把底层异常堆栈或者 API Key 相关信息暴露出去。

说话人 1：问题四十三，如何为同步模型调用设计失败策略？如何为 `Flux` 流式调用设计异常传递、请求取消、资源释放和部分响应处理？

说话人 1：答，同步调用和流式调用必须分别考虑，因为它们的执行时机和失败发生的位置不一样。

说话人 1：同步调用相对简单。可以使用统一的异常处理机制，根据异常类型判断是否重试、是否降级，以及最终返回什么业务错误。

说话人 1：流式调用则复杂一些，因为 `Flux` 可能已经向前端发送了部分内容，随后才出现异常。

说话人 1：例如，模型已经推送了前面 20 个 Token，突然发生读取超时。此时不能再把整条响应当成一个从未成功过的普通请求处理。

说话人 1：在 Reactor 中，可以使用 `onErrorMap()` 转换异常、使用 `onErrorResume()` 处理异常、使用 `doFinally()` 做资源清理，并通过 `timeout()` 控制流式处理的等待时间。

说话人 1：如果用户主动取消订阅，还要让取消信号尽可能传递到模型客户端，停止不必要的后续计算。

说话人 1：另外，流式调用的重试尤其需要谨慎。假设第一次已经输出了 20 个 Token，发生异常后直接使用 `retryWhen()` 重新订阅，模型可能从头生成一次，导致前端收到重复内容。

说话人 1：所以，如果还没有向前端输出任何内容，可以根据情况重新尝试；一旦已经开始输出，就应该优先考虑发送错误事件、保存部分结果，并标记本次生成失败或部分完成，而不是偷偷从头重试并拼接内容。

说话人 1：这里的关键是：同步失败通常可以围绕完整请求进行恢复，流式失败则必须同时处理已经交付的内容、剩余生成任务和连接生命周期。

说话人 1：问题四十四，如果 SSE 已经向前端推送部分 Token，随后模型调用失败，应该如何通知客户端？为什么不能简单地重新返回一个 HTTP 500？

说话人 1：答，因为 SSE 一旦开始发送响应头和响应体，HTTP 响应就可能已经提交，状态码通常不能再改变。

说话人 1：例如，模型已经生成并发送了：

```
event: token
data: 设备可能存在传感器异常
```

说话人 1：接下来模型调用发生超时。这个时候服务器已经不能正常重新返回一个全新的 HTTP 500 响应，覆盖前面已经发送给浏览器的数据。

说话人 1：正确的方式是设计 SSE 错误事件：

```
event: error
data: {"code":"MODEL_TIMEOUT","message":"模型响应超时"}
```

说话人 1：前端收到后，可以停止当前内容更新，提示用户回答未完整生成，同时保留已经收到的部分内容。

说话人 1：如果后端还保存了请求状态，可以进一步记录生成失败原因和已输出内容，方便用户重试或者后续恢复。

说话人 1：所以，在 SSE 中，HTTP 状态码主要负责连接建立前的错误，连接建立后的业务异常则需要通过事件协议表达。

说话人 1：问题四十五，如果模型调用成功，但后续结构化输出解析、数据校验或数据库保存失败，是否应该重新调用模型？如何确定失败策略？

说话人 1：答，不能把所有后续处理失败都转化为重新调用模型，因为问题可能根本不在模型。

说话人 1：例如，模型已经成功生成了完整 JSON，但是 Java 使用 Jackson 解析时发生异常。如果是代码转换问题，再调用一次模型可能没有任何帮助。

说话人 1：如果是模型输出不符合 Schema，可以考虑一次受控的修复调用，把校验错误反馈给模型，让它重新生成符合要求的内容。但这种方式必须限制次数，还要验证修复后的结果。

说话人 1：如果模型结果已经正确，只是数据库暂时不可用，就应该重试数据库保存，而不是重新调用模型。

说话人 1：如果是业务规则不通过，例如设备编号不存在，也应该进入业务异常处理，而不是无限要求模型重新生成。

说话人 1：所以，我会把模型生成、格式解析、业务校验和数据持久化拆成独立阶段，每个阶段只对自己能够恢复的故障负责。

说话人 1：一句话：哪里失败，就优先修复哪里，不要把模型调用当成所有异常的万能重试入口。

说话人 1：问题四十六，如何确保超时和重试不会导致重复创建工单、重复扣款或重复执行工具？幂等键、请求 ID 和业务事务分别承担什么职责？

说话人 1：答，这涉及模型应用中一个非常重要的边界：模型生成内容和真正执行业务操作是两回事。

说话人 1：例如，用户要求设备助手创建一张维修工单。模型可能通过 Tool Calling 请求调用 `createWorkOrder` 工具。

说话人 1：如果第一次工具调用已经成功创建工单，但后续模型响应超时，系统重新处理请求时就可能再次创建一张工单。

说话人 1：所以，必须让真正产生副作用的业务操作具备幂等能力。

说话人 1：第一，`requestId` 标识一次用户提交，可以防止客户端重复提交同一个请求。

说话人 1：第二，幂等键标识一次具体业务操作。例如，同一个请求中的工单创建操作，可以使用稳定的业务操作 ID，确保重复执行时返回原来的工单结果，而不是再创建一张。

说话人 1：第三，业务事务负责保证数据库内部相关操作的一致性。例如，工单记录和请求执行状态应该尽可能在同一数据库事务中提交。

说话人 1：如果业务操作涉及外部系统，就还要使用对方支持的幂等键、状态查询、Outbox 或补偿机制，不能认为本地数据库事务能够自动保证跨系统 exactly-once。

说话人 1：还有一个重要细节：模型可能在一次交互中提出多个工具调用，因此不能简单地只用一个请求 ID 代替所有工具操作 ID。每个具有副作用的操作都需要独立识别和控制。

说话人 1：所以，模型请求可以重试，但真正的业务操作必须有可靠的幂等边界，不能让模型重试直接演变成重复扣款、重复建单或重复执行设备操作。

## 第七阶段：可靠性、安全与可观测性

说话人 1：问题四十七，如何设计模型调用的日志、指标与链路追踪？应该监控成功率、失败率、超时率、重试次数、熔断状态、Token 消耗和供应商响应时间中的哪些指标？

说话人 1：答，模型调用不能只记录一条“调用失败”的日志，而是应该能够还原整个请求的执行过程。

说话人 1：我一般从日志、指标和链路追踪三个方面设计。

说话人 1：第一，日志。每次模型调用至少记录请求 ID、会话 ID、模型名称、供应商、调用类型、异常分类、重试次数和最终执行状态。

说话人 1：比如，某次请求出现超时，我们应该能够查到它使用了哪个模型、调用了几次、每次等待了多久，以及最后是成功、失败还是被用户取消。

说话人 1：第二，指标。重点监控模型调用成功率、失败率、超时率、429 比例、平均响应时间、P95 和 P99 延迟、重试次数、熔断状态、活跃并发量以及 Token 消耗。

说话人 1：第三，链路追踪。把一次用户请求从 Controller、会话记忆、RAG 检索、模型调用一直到数据库保存的过程关联起来，确认耗时究竟发生在哪个环节。

说话人 1：例如，一个请求总共耗时 15 秒，其中历史读取 100 毫秒、RAG 检索 2 秒、模型调用 12 秒、数据库保存 900 毫秒。通过链路追踪，我们就可以明确主要瓶颈在模型调用，而不是盲目优化 Redis。

说话人 1：另外，还要监控单位请求的输入 Token 和输出 Token，以及每个供应商的调用费用，避免出现调用成功率很高，但费用不断上涨的情况。

说话人 1：还有两个安全要求：不要把 API Key、完整敏感 Prompt 和用户隐私直接写进日志；指标标签也不要直接使用无限增长的 requestId、conversationId，否则可能造成监控系统的高基数问题。

说话人 1：Spring AI 本身提供 Micrometer 可观测性支持，可以配合 Spring Boot Actuator 和 Prometheus 等工具建立监控体系。我们还需要补充业务层的重试、熔断和降级指标。

说话人 1：参考资料：Observability | 可观测性：[Spring AI 官方文档](https://docs.spring.io/spring-ai/reference/1.1/observability/index.html?utm_source=chatgpt.com)

说话人 1：问题四十八，为什么需要区分模型调用失败、模型生成错误和模型业务结果不合格？这三类问题应该采用什么不同的处理方式？

说话人 1：答，因为这三种问题发生在不同阶段，处理方式也完全不同。

说话人 1：第一，模型调用失败。比如网络连接失败、供应商返回 503、请求超时。这种情况下，模型可能根本没有返回可用结果，需要根据异常类型判断是否重试、熔断或者降级。

说话人 1：第二，模型生成错误。这里是模型已经成功执行调用，但输出本身有问题。例如生成的 JSON 格式不完整、内容为空，或者生成过程中提前结束。这时候需要检查模型参数、输出格式约束和生成结果，必要时进行有限的修复调用。

说话人 1：第三，业务结果不合格。比如模型生成了合法 JSON，字段也完整，但里面的设备编号不存在，或者维修操作不满足企业安全规范。

说话人 1：这种情况不能靠重新调用模型直接解决，而应该执行业务规则校验、查询权威数据，必要时要求用户补充信息或者转人工处理。

说话人 1：举个例子，模型返回 HTTP 200，JSON 也解析成功，但建议用户直接重启一台正在执行危险工序的设备。技术调用成功了，格式也正确，但业务结果依然不合格。

说话人 1：所以，我会将整个调用过程拆成三层：传输层判断请求是否成功，模型层判断生成是否有效，业务层判断结果能否真正使用。

说话人 1：HTTP 成功不等于模型生成正确，模型生成正确也不等于业务操作安全。

说话人 1：问题四十九，当主模型和备用模型均不可用时，如何设计最终失败处理、用户提示、任务状态保存和后续恢复机制？

说话人 1：答，如果主模型和备用模型都不可用，就不能再无限尝试切换模型，而应该进入最终失败处理流程。

说话人 1：首先，保存本次请求的执行状态。例如，可以将任务标记为 `FAILED`、`WAITING_RETRY` 或 `NEEDS_HUMAN_REVIEW`，具体状态要根据业务定义。

说话人 1：其次，向用户返回明确提示。例如：“当前模型服务暂时不可用，本次分析尚未完成，请稍后重试。”不能把部分生成内容直接显示成完整答案。

说话人 1：第三，保留必要的请求信息，包括 requestId、模型名称、错误分类、已执行步骤和调用次数，方便后续恢复。

说话人 1：第四，如果业务允许异步恢复，可以把任务放入有界的重试队列，待供应商恢复后再继续处理。

说话人 1：例如，设备故障助手已经保存用户描述，但模型服务持续不可用，可以保留故障任务，提示用户当前无法生成建议，之后再由后台任务恢复分析。

说话人 1：但后台恢复也必须有最大重试次数、任务过期时间和幂等控制，不能让一个失败任务永远留在队列中。

说话人 1：如果涉及高风险业务，而系统暂时无法安全判断，就应该转人工处理，而不是为了保证服务可用，随便返回一份不可靠的模型答案。

说话人 1：最终原则是：模型可以暂时不可用，但业务系统必须明确记录发生了什么、用户应该怎么办，以及任务是否还有恢复机会。

## 第八阶段：综合面试与企业项目架构设计

说话人 1：问题五十，假设你要为制造设备故障问答助手设计生产级模型调用策略，请从超时、重试、指数退避、随机抖动、限流、熔断、隔离、模型切换、降级、幂等和监控几个方面，设计完整方案，并说明如何通过自动化测试和实际运行证据验证可靠性？

说话人 1：答，如果由我负责设计这套系统，我不会只在 `ChatClient.call()` 外面增加几个注解就认为完成了可靠性建设，而是会从请求进入系统到最终业务结果保存，设计一条完整的模型调用保护链路。

说话人 1：先看整体架构，我会把它分为接入层、模型调用控制层、模型适配层、业务处理层和监控层。

说话人 1：第一，接入层。

说话人 1：用户提交设备故障问题以后，系统先完成身份验证、参数校验和请求幂等检查，生成唯一的 requestId，并确认用户是否有权访问当前会话。

说话人 1：同时记录任务状态，避免客户端重复提交造成重复处理。

说话人 1：第二，超时控制。

说话人 1：模型调用统一设置整体 Deadline，并根据连接、读取、模型生成和结果保存分别分配时间预算。

说话人 1：例如，普通故障查询可以设置相对较短的请求时间，复杂设备诊断则可以允许更长的生成时间。流式请求还要单独设置首 Token 等待时间、连续无数据时间和最大生成时长。

说话人 1：所有时间参数都应该由配置管理，并根据真实请求的 P95、P99 耗时调整，而不是写死在业务代码中。

说话人 1：第三，重试策略。

说话人 1：对于网络瞬时异常、部分 502、503 和符合条件的超时，可以允许有限重试。

说话人 1：例如，最多尝试三次，采用指数退避，初始间隔 500 毫秒，之后逐步增加，同时加入随机抖动，最大等待时间设置上限。

说话人 1：如果供应商返回 429，则结合 Retry-After 和剩余请求时间判断是否重试。

说话人 1：如果是 API Key 错误、请求参数错误或者账户权限问题，就直接失败，不再浪费资源重试。

说话人 1：对于已经向前端发送部分 Token 的流式请求，默认不进行从头重试，避免重复输出。出现异常后应该保存部分结果、发送错误事件，并按照业务策略结束或重新创建生成任务。

说话人 1：第四，限流和并发控制。

说话人 1：我会同时考虑 RPM、TPM 和最大并发请求数。

说话人 1：RPM 控制请求频率，TPM 控制 Token 使用量，并发限制控制同时执行的模型任务数量。

说话人 1：如果系统部署多个实例，还需要通过 Redis 或统一网关实现共享配额控制，避免每个实例独立限流，最终突破供应商的全局配额。

说话人 1：对于积压请求，采用有界队列和排队超时。紧急故障请求可以设置更高优先级，普通问答则根据系统负载进行排队或拒绝。

说话人 1：第五，熔断与舱壁隔离。

说话人 1：每个模型供应商可以设置独立熔断器，根据失败率和慢调用比例决定是否打开熔断。

说话人 1：当主模型持续不可用时，熔断器打开，避免继续浪费连接和调用资源。

说话人 1：同时使用 Bulkhead 限制模型调用的最大并发量，避免 AI 请求占满整个 Java 应用的线程资源。

说话人 1：特别是当前项目如果使用 Spring MVC，同步调用的执行线程和流式响应的执行资源应该明确规划，不能让模型请求和普通业务请求完全没有资源隔离。

说话人 1：第六，模型切换和降级。

说话人 1：如果主模型不可用，可以考虑备用模型，但要事先验证备用模型的上下文窗口、工具调用能力、结构化输出能力和实际回答质量。

说话人 1：如果备用模型无法满足当前业务要求，就应该返回受控错误。

说话人 1：对于低风险问题，可以在数据没有过期的情况下使用经过审核的缓存结果；对于能够确定计算的任务，可以切换到规则引擎或者 Java 程序；对于高风险故障操作，则应转人工处理，不能随便生成替代建议。

说话人 1：第七，统一异常与业务幂等。

说话人 1：模型调用层把不同供应商的错误统一转换为业务异常，例如 `MODEL_TIMEOUT`、`MODEL_RATE_LIMITED` 和 `MODEL_UNAVAILABLE`。

说话人 1：如果涉及 Tool Calling，工单创建、订单处理和设备操作等具有副作用的动作，必须使用独立的业务幂等键和请求状态管理，确保模型重试不会重复执行。

说话人 1：第八，可观测性。

说话人 1：记录每次模型调用的 requestId、模型名称、供应商、调用次数、超时阶段、最终状态和耗时。

说话人 1：通过 Micrometer 监控调用成功率、失败率、429 比例、重试次数、熔断状态、并发量、Token 消耗、供应商响应延迟和模型费用。

说话人 1：如果发现某个供应商的 P99 延迟突然上升，并伴随 503 和重试次数增加，就应该能够通过监控快速定位，而不是等用户不断反馈问题。

说话人 1：最后是自动化测试和验收。

说话人 1：我会至少设计以下测试场景：

说话人 1：第一，网络连接失败，验证是否进入正确的异常分类和重试流程。

说话人 1：第二，读取超时，验证远端执行结果未知时不会无条件重复产生业务操作。

说话人 1：第三，供应商连续返回 429，验证限流等待和 Retry-After 处理正确。

说话人 1：第四，连续返回 503，验证熔断器能够打开，并在等待后进行半开探测。

说话人 1：第五，大量并发请求，验证全局限流、线程隔离和有界队列是否生效。

说话人 1：第六，主模型和备用模型同时失败，验证最终错误提示和任务状态保存正确。

说话人 1：第七，Tool Calling 重复执行，验证相同业务操作不会重复创建工单。

说话人 1：第八，流式输出中途断开，验证已经产生的部分内容能够正确处理，连接取消以后不再无条件继续消耗资源。

说话人 1：测试工具方面，可以使用 WireMock 或 MockWebServer 模拟供应商返回 429、503、超时和连接中断；使用真实 Redis 或 Testcontainers 验证分布式限流、请求幂等及状态管理；再结合并发压测验证系统在高负载下的表现。

说话人 1：最终验收不能只看单元测试是否通过，还需要保留集成测试报告、压测结果、关键日志、实际模型调用记录和 Git 提交证据。

说话人 1：只有这些证据能够互相对应，才能证明失败策略确实起到了保护作用。

说话人 1：总结一下，这套架构的核心不是尽可能多地使用 Resilience4j，而是每种故障都有明确的处理规则：能安全重试的有限重试，应该等待的按预算等待，持续故障的及时熔断，资源不足的主动限流，不能安全降级的明确失败，涉及业务副作用的严格幂等。

说话人 1：这才是企业级 AI 模型调用失败策略真正需要解决的问题。

## 本次主题总结：模型调用失败策略的十个核心结论

说话人 1：第一，模型调用失败不能一概而论。网络、超时、限流、认证、服务端、模型输出和业务异常必须分开处理。

说话人 1：第二，超时要分阶段设计。连接超时、读取超时和整体请求截止时间各有不同作用，流式调用还需要处理空闲超时和最大生成时限。

说话人 1：第三，重试只适合具有恢复可能性的故障。认证错误、参数错误和业务校验失败不能简单重复调用。

说话人 1：第四，指数退避能够减少持续故障期间的调用压力，随机抖动可以减少大量客户端同时重试形成的请求洪峰。

说话人 1：第五，RPM、TPM 和并发控制是不同维度。应用侧需要提前控制请求数量、Token 消耗和资源占用，不能完全依赖供应商返回 429 以后再处理。

说话人 1：第六，Retry 解决单次失败后的再次尝试，CircuitBreaker 解决服务持续故障时的调用保护，Bulkhead 负责资源隔离，RateLimiter 负责流量控制，TimeLimiter 负责执行时间限制。

说话人 1：第七，降级不等于随便换一个模型。备用模型必须经过能力和业务适用性验证，高风险场景必要时应该直接转人工。

说话人 1：第八，Spring AI 负责模型调用抽象，但超时、重试、熔断、限流、异常映射和业务幂等仍然需要结合 Java 工程设计。

说话人 1：第九，流式请求尤其需要处理部分响应。如果已经向前端发送 Token，后续发生异常，就不能简单地重新返回 HTTP 500，也不能无条件重新生成并追加内容。

说话人 1：第十，模型调用的可靠性必须通过自动化测试、并发测试、真实存储测试和运行监控进行验证，不能只凭代码配置判断系统已经具备高可用能力。

说话人 1：如果面试官问我，企业级 Java AI 项目应该如何设计模型调用失败策略，我会这样回答：

说话人 1：我会先对模型调用异常进行分类，然后建立统一的模型调用服务，集中处理超时、有限重试、指数退避、随机抖动、限流、熔断和并发隔离。

说话人 1：如果主模型不可用，再根据备用模型的实际能力决定是否切换；如果不能安全降级，就明确失败并保留任务状态。

说话人 1：对于工具调用和业务操作，还必须使用请求 ID、业务幂等键和事务机制，避免模型重试造成重复执行。

说话人 1：最后，通过日志、指标、链路追踪和自动化测试，证明整个系统在网络故障、供应商限流、模型超时和高并发情况下仍然能够按照预定策略运行。

说话人 1：真正的模型调用可靠性，不是保证每次请求都成功，而是保证请求失败时系统知道如何处理，不会因为一次外部模型故障，就把整个业务系统拖垮。
