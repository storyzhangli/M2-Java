# 三、本次迭代的目标、范围与非目标

## 3.1 核心目标

### 目标 A：对话历史持久化

完整保存本次应用中应该保留的用户消息和 AI 回复，使应用重启后仍能够按照会话查询历史。持久化记录应包含足以识别消息归属、角色、顺序、内容和时间的信息，并与用户/会话权限边界关联。

### 目标 B：多轮对话上下文关联

用户在同一会话中继续提问时，系统应按明确策略读取该会话此前相关消息，并将合适的历史上下文加入当前模型请求；不同会话不得串线。上下文应有明确的窗口或 Token 预算，不能无上限地把全部历史消息发送给模型。

### 目标 C：历史展示和可验证性

在现有 API 风格允许的范围内，提供或扩展会话历史查询能力，使开发者可以验证消息是否持久化、会话是否隔离以及多轮上下文是否生效。

## 3.2 本次必须实现

1. 识别或创建会话，获得稳定的 `conversationId`。
2. 保存用户消息。
3. 保存模型成功返回的 AI 消息。
4. 保存失败状态或错误摘要，避免失败调用造成历史状态含糊；具体数据结构按现有项目规范设计。
5. 按 `conversationId` 查询消息，保证顺序稳定。
6. 在下一轮请求中取回同一会话的历史消息，按确定策略组装模型上下文。
7. 对会话归属进行校验，阻止通过猜测或替换 ID 读取其他用户的数据。
8. 对空消息、非法会话 ID、会话不存在、无权访问、模型失败、超时和重复请求进行处理。
9. 为核心业务行为补充自动化测试。
10. 提供两份 D17 技术文档、执行日志、临时资料和证据索引。

## 阶段一：知识覆盖与技术原理分析

先围绕 D17 形成知识清单，至少分析以下内容，并标记“本次必需 / 了解即可 / 不适用”。

### 4.1.1 Chat History 与 Chat Memory 的边界

必须准确区分：

- **Chat History（对话历史）**：完整的、可持久化查询的消息记录，用于历史展示、审计、追踪和会话恢复。
- **Chat Memory（对话记忆/上下文记忆）**：为当前模型调用选择并提供的有限上下文，不等于完整历史记录。
- **Conversation（会话）**：组织多条消息的业务实体，具有归属、状态和时间信息。
- **Conversation ID**：用于定位会话；它本身不是身份认证，也不能替代用户权限校验。
- **Message Window / Context Window**：当前请求允许进入模型上下文的历史消息范围。

不得把一个只保存最近 N 条消息的内存窗口误当成完整历史存储。完整历史应持久化；进入模型的上下文可以受窗口或 Token 预算限制。

### 4.1.2 Spring AI 1.1.x 相关机制

核对当前版本中的：

- `ChatClient` 的消息输入和调用链；
- `ChatMemory`、`ChatMemoryRepository` 的职责；
- `MessageWindowChatMemory` 的窗口行为；
- `MessageChatMemoryAdvisor` 的使用方法及 Conversation ID 参数；
- 当前版本适用的 JDBC 等持久化实现（若项目考虑使用）；
- Advisor 自动写入记忆与业务层手动持久化之间是否会重复保存；
- `Prompt` / `Message` 的角色、顺序及传入方式。

必须根据实际 1.1.x 小版本核对 API。不得仅因某个组件存在就直接选用；要说明它保存的是完整业务历史，还是仅用于模型上下文的记忆窗口。

### 4.1.3 会话与消息数据模型

分析：

- 会话与消息的一对多关系；
- 会话 ID、消息 ID、用户 ID 的生成及关联；
- 消息角色（至少区分 user、assistant；system 是否持久化需说明）；
- 消息顺序的稳定性；
- 时间戳、消息状态和模型元数据；
- 历史分页及排序；
- 软删除/归档是否属于本次范围；
- 数据库索引、唯一约束及外键策略（以项目规范为准）。

### 4.1.4 多轮上下文组装

分析：

- 新会话首轮与已有会话后续轮次的差异；
- 历史消息读取的时间点；
- 将历史消息转成 Spring AI 消息的映射；
- System Prompt 与历史消息的顺序；
- 当前 User Message 是否会被重复加入上下文；
- 上下文窗口按最近 N 条消息、最近 N 轮或 Token 预算控制的优缺点；
- 保留完整问答轮次，避免截断后只留下孤立的 assistant 消息；
- 超长上下文处理及可配置参数；
- 对话历史为空、消息内容为空、历史记录损坏或角色不支持时的处理。

### 4.1.5 持久化一致性与并发

至少分析：

- 用户消息是在调用模型前还是之后保存；
- 模型失败时如何保留用户输入及失败状态；
- assistant 消息何时保存；
- 数据库事务不能长时间包围外部模型 HTTP 调用；
- 同一会话两个并发请求如何保证消息顺序；
- 重试是否会重复插入用户消息或 assistant 消息；
- 请求中断、模型超时和进程重启后如何识别不完整消息；
- 流式输出如何记录完成、失败或中断状态；
- 多实例部署时是否依赖共享持久化存储，而不能依赖单机内存。

分析会话越权、IDOR、用户 ID 伪造、SQL 注入、日志泄露、历史内容敏感信息、删除/保留策略及上下文跨用户污染风险。

## 阶段三：详细需求、数据设计与验收设计

### 4.3.1 建议业务流程（必须结合实际 API 调整）

建议流程如下，最终以 D16 真实接口为准：

```text
客户端提交消息
    ↓
校验请求参数与用户身份
    ↓
检查 conversationId
    ├─ 不存在：创建新会话并生成服务端 conversationId
    └─ 已存在：查询会话并校验当前用户是否拥有访问权
    ↓
为本轮请求生成 requestId / 幂等标识（若现有体系支持）
    ↓
将 user message 持久化为可追踪状态
    ↓
读取同一会话的历史消息
    ↓
按窗口/Token 预算组装历史上下文
    ↓
通过现有 ChatClient / Spring AI 调用模型
    ↓
成功：保存 assistant message，更新会话最后活动时间
失败：保留用户消息，记录失败状态/错误摘要，不伪造 assistant 成功消息
    ↓
返回 conversationId、messageId 和本轮结果
```

外部模型调用不得放在一个长时间持有的数据库事务中。必要时拆分为短事务：保存用户消息、完成模型调用、保存模型响应及更新状态。

### 4.3.2 API 契约

先查现有 API，优先扩展现有聊天接口，不得无理由创建第二套聊天入口。

如现有接口没有会话能力，才考虑采用如下契约，并按项目 API 规范调整。

**聊天请求候选字段：**

| 字段 | 类型 | 规则 |
|---|---|---|
| conversationId | String / UUID | 可选；缺失表示新会话，存在时必须校验归属 |
| message | String | 必填；去除首尾空白后不可为空，并设置合理长度上限 |
| requestId | String | 可选；若系统已有幂等规范则复用，不另造体系 |

**响应候选字段：**

| 字段 | 含义 |
|---|---|
| conversationId | 本次消息所属会话 ID |
| userMessageId | 已保存的用户消息标识（若响应结构适合暴露） |
| assistantMessageId | 已保存的 assistant 消息标识 |
| answer | 模型回答 |
| status | 完成/失败等本轮状态 |

如项目已采用统一响应包装，必须保持现有格式，不得另造一套。

**历史查询 API：**

- 会话列表：仅查询当前用户有权访问的会话，支持分页和合理排序；
- 消息历史：按会话 ID 分页查询，顺序稳定；
- 会话详情：仅在真实业务需要时提供；
- 删除/清空：不作为默认必做功能，除非现有需求明确要求。若实现，必须先做归属鉴权，并定义物理删除/逻辑删除和 ChatMemory 同步规则。

### 4.3.3 数据模型候选方案

在扫描现有 ORM 和数据库后决定是否需要以下两类实体。字段仅为设计候选，不要求照搬。

**Conversation（会话）候选属性：**

- conversation_id：稳定会话标识；
- owner_id / user_id：会话归属；
- title：可选标题，D17 可先使用首条用户消息的安全截断文本或默认标题；
- status：会话状态；
- created_at、updated_at、last_message_at；
- 可选 version：用于乐观并发控制。

**ChatMessage（消息）候选属性：**

- message_id：消息标识；
- conversation_id：所属会话；
- sequence_no 或可保证稳定顺序的排序字段；
- role：user / assistant，system 消息是否持久化需明确；
- content：消息正文；
- status：如 PENDING / COMPLETED / FAILED / INTERRUPTED，按实际调用方式裁剪；
- created_at、completed_at；
- 可选 model_name、provider、token_usage、request_id、error_code、metadata。

**数据设计要求：**

1. 会话与消息必须建立明确关联；
2. 查询必须能够稳定按会话和消息顺序执行；
3. 为核心查询建立适当索引，例如 conversation_id + sequence_no / created_at；
4. 必须防止跨会话、跨用户查询；
5. 避免只依赖 `created_at` 排序而无法处理同毫秒消息；
6. 不得把完整消息正文写入普通 INFO 日志；
7. 如需保存模型 token 统计，字段缺失时允许为空，不得伪造值；
8. 迁移脚本必须可重复部署，并提供向后兼容和回滚说明；
9. 优先复用项目已使用的 MyBatis/MyBatis-Plus/JPA 等数据访问技术；
10. 不得为了 D17 新增数据库或中间件，除非有真实且书面说明的必要性。

### 4.3.4 历史与上下文分层设计

必须给出清晰架构，明确：

- **持久化历史层**：保存可查询的完整对话记录；
- **上下文选择层**：从持久化消息中选取本轮需要的历史；
- **模型请求层**：按 Spring AI 当前版本 API 将 System、历史消息和当前 User Message 组成模型输入；
- **展示层**：按分页查询历史，不影响模型上下文窗口。

优先将持久化消息作为可恢复的事实来源。不要仅依赖进程内 `InMemoryChatMemoryRepository` 实现跨重启历史。

如果采用 Spring AI `ChatMemory` / Advisor，必须回答：

1. 它管理的是历史全集还是模型上下文窗口？
2. 记忆窗口清理是否可能删除用户要求保留的完整历史？
3. Spring AI Advisor 是否会自动保存消息？业务层是否又保存一次？如何避免重复？
4. 会话 ID 是否每次请求明确传入？
5. 发生数据库持久化失败时，模型是否仍然被调用？
6. 历史消息是否会被重复拼入 prompt？

可选方案需对比：

- 从完整历史表读取最近 N 条/最近 N 轮后显式组装 Prompt；
- 使用 Spring AI ChatMemory + 持久化 ChatMemoryRepository；
- 完整历史表与有限 ChatMemory 窗口分离。

根据 D16 真实实现、Spring AI 1.1.x 官方 API、数据库和业务需求选择。**不能把内存 ChatMemory 作为持久化历史的唯一来源，也不能让 Advisor 自动写入与业务层重复写入而不处理一致性。**

### 4.3.5 多轮上下文策略

必须明确并实现一种可解释的上下文策略：

- 初始默认可以按最近 N 条消息或最近 N 个完整问答轮次控制；
- 如果有可靠 Token 计数能力，再增加 Token 预算限制；没有则不要声称精确 Token 控制；
- 尽量保留完整问答轮次，避免只截取 assistant 回复而丢失对应 user 问题；
- System Prompt 不得被历史普通消息覆盖；
- 当前消息只能加入一次；
- 历史消息按稳定顺序传递；
- 不同 conversationId 之间不得共享上下文；
- 会话首次请求不带旧历史；
- 历史为空时按单轮对话处理；
- 窗口大小和 Token 限制（如有）应外部化配置并给出默认值与依据；
- 以后可扩展摘要压缩，但 D17 不默认实现长期语义记忆。

### 4.3.6 权限与隔离

- `conversationId` 是资源定位符，不是授权凭据；
- 当前登录用户 ID 必须来自现有安全上下文或受信任服务端身份来源；
- 不得信任请求体中的 `userId` 来决定会话所有权；
- 每个历史查询、继续对话和删除操作（若存在）都必须验证用户归属；
- 不存在和无权访问的响应应符合项目既有错误策略，避免泄露其他用户资源是否存在；
- 如果 D16 尚无真实认证机制，必须明确当前开发模式的身份边界与风险，不得假装已实现生产级多用户授权；可以使用明确标注的开发身份适配，但不能将其宣传为正式鉴权。

### 4.3.7 并发、幂等与错误恢复

至少设计以下场景：

- 同一会话快速连续提交两条消息；
- 同一用户在两个客户端对同一会话并发发消息；
- 用户请求重试导致同一消息重复提交；
- 保存 user message 成功、模型调用失败；
- 模型返回成功、保存 assistant message 失败；
- 应用重启后恢复历史；
- 超时、限流、模型异常；
- 流式响应期间客户端断开（若 D16 有流式接口）。

不能为“看起来完整”而引入复杂分布式锁。优先根据业务一致性需求使用数据库唯一约束、请求幂等标识、乐观锁或按会话串行化等最小方案，并说明适用边界。

6. 模型调用不能被长数据库事务包围。

14. 性能指标必须先测量基线；没有实测不得宣称性能提升。

## 5.2 必须停止并报告的情况

遇到以下情况不得盲目继续：

- D17 根目录或骨架目录与输入路径不符；
- 根 POM 与子模块关系无法确认；
- 找不到 D16/D16_CoT 基础且无法判断需要继承的能力；
- 数据库类型或现有持久化方案无法确认；
- 当前认证机制不足以定义安全的会话归属；
- 设计会破坏 D16 已有接口或用户数据；
- 数据库迁移存在不可逆风险；
- 同一会话并发/重复请求规则会改变核心业务语义但没有依据；
- 当前版本的 Spring AI API 无法通过官方文档确认；
- 测试失败且根因未明确。

停止时仍需交付已完成的扫描与设计内容，说明阻塞原因、影响范围和需要用户决策的问题。不要擅自猜测关键业务规则。
